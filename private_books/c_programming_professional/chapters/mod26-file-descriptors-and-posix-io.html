Module 26: File Descriptors & POSIX Low-Level I/O

Deep dive into Linux Virtual Filesystem (VFS) internals, file descriptor tables, system calls vs buffered stdio, non-blocking I/O (O_NONBLOCK), close-on-exec (O_CLOEXEC), atomic persistence with fsync/fdatasync, and scatter/gather vectorized I/O (readv/writev).

⏱️ Duration: 55m
🎯 Standard: POSIX.1-2008 / Linux VFS / C11
⚡ Target: Linux x86_64 / Embedded Linux (ARM/MIPS)

26.1 Linux VFS Architecture & Kernel Descriptor Tables

In Unix-like systems, the foundational design maxim is "everything is a file". A File Descriptor (FD) is not a file itself; it is a small, non-negative integer serving as an index into a per-process kernel table.

Linux Kernel VFS Object Relationships
User Process (task_struct)
  └── files_struct (Descriptor Table)
       ├── FD 0 (stdin)  ──▶ [ struct file (Offset, Flags) ] ──▶ [ struct inode ] ──▶ Hardware / TTY
       ├── FD 1 (stdout) ──▶ [ struct file (Offset, Flags) ] ──▶ [ struct inode ] ──▶ Hardware / TTY
       ├── FD 2 (stderr) ──▶ [ struct file (Offset, Flags) ] ──▶ [ struct inode ] ──▶ Hardware / TTY
       └── FD 3 (telemetry.dat) ──▶ [ struct file ] ───────────▶ [ struct inode ] ──▶ Ext4 / NVMe
                                     (f_pos = 1024)                 (i_size = 4096)

Three Kernel Layers of File Abstraction

  1. File Descriptor Table (Per-Process): Maps integer integers (0, 1, 2, 3...) to open file descriptions. Preserved across fork().
  2. Open File Table (System-Wide): Stores current byte offset (f_pos), access status flags (O_RDONLY, O_NONBLOCK, O_APPEND), and reference count.
  3. Inode Table (Filesystem-Wide): Represents the physical storage object on disk, containing file size, disk block extents, permissions, and file type (regular file, socket, pipe, character device).

26.2 System Calls vs. Standard C Buffered I/O

Software engineers often confuse low-level POSIX system calls (open, read, write, close) with ISO C standard library streams (fopen, fread, fwrite, fclose).

Dimension POSIX System Calls (unistd.h) Standard C Library (stdio.h)
Handle Type Integer file descriptor (int fd) Pointer to struct (FILE *fp)
Buffering Unbuffered (Direct kernel syscall) User-space buffered (Typically 4 KB or 8 KB buffer)
Overhead for small writes High (Every write triggers a CPU context switch) Minimal (Aggregates small writes in user-space buffer)
Direct Hardware / Non-blocking Yes (Ideal for epoll, sockets, devices) No (Blocks unexpectedly when buffer drains)

26.3 Atomic Persistence: fsync vs fdatasync

When you invoke write(fd, buf, len), the kernel copies the data from user space into the Linux Page Cache in RAM. The physical write to flash or disk occurs asynchronously seconds later!

Data Loss Hazard: If power is severed immediately after write() or fflush(), unwritten page cache data in RAM evaporates, leaving files corrupted or empty on disk!

To guarantee non-volatile durability, production embedded systems must explicitly flush the page cache:

  • fsync(fd): Flushes all modified dirty file data AND metadata (inode modification time, file size) to physical disk. Forces head/flash commit.
  • fdatasync(fd): Flushes dirty file data, but omits metadata updates unless required to retrieve data (e.g., file size expansion). Significantly faster than fsync() on mechanical storage.

26.4 Scatter/Gather Vectorized I/O (writev / readv)

When transmitting structured packets (e.g. Header + Payload + Checksum), naive programs either concatenate the buffers into a temporary array (costing CPU copies and RAM allocations) or issue multiple write() syscalls (costing multiple kernel transitions).

Vectorized I/O (writev) eliminates both penalties by passing an array of pointers (struct iovec) to the kernel in a single atomic syscall: 

#include <sys/uio.h>

struct iovec iov[3];
iov[0].iov_base = &header;      iov[0].iov_len = sizeof(header);
iov[1].iov_base = payload_data; iov[1].iov_len = payload_size;
iov[2].iov_base = &crc32;       iov[2].iov_len = sizeof(crc32);

/* Single atomic syscall! Zero intermediate buffer copies! */
ssize_t written = writev(fd, iov, 3);

26.5 Industrial Case Study: Database Journal Data Loss Disaster

The Industrial SCADA Power Outage File Truncation Incident

An industrial wastewater treatment facility experienced a sudden power grid failure. The backup generator kicked in within 3 seconds, but the SCADA telemetry logging system failed to restart, reporting corrupted transaction journals.

Root Cause Analysis: The logging daemon wrote critical alarm logs using standard C library calls: 

fprintf(log_fp, "[ALARM] Motor Overheat State at %lu
", timestamp);
fflush(log_fp); /* Flushes stdio buffer into Linux Page Cache ONLY! */

The developers believed fflush() ensured disk persistence. In reality, fflush() simply issues a write() syscall to the Linux kernel page cache. Because the system lost power 500 milliseconds later, the kernel never flushed the dirty pages from volatile DDR RAM to physical eMMC flash memory!

The Fix: All critical configuration and journal commits were updated to invoke fdatasync(fileno(log_fp)), ensuring physical non-volatile storage commit before returning control to the caller.

26.6 Hands-On Lab: Building an Atomic Configuration Writer in C

In this lab, you will write a robust, crash-resilient file persistence engine in C that prevents partial file corruption using the Atomic Write-and-Rename idiom combined with fdatasync().

Production Atomic Writer (atomic_write.c)

#include <stdio.h>
#include <stdlib.h>
#include <string.h>
#include <fcntl.h>
#include <unistd.h>
#include <errno.h>

int atomic_write_file(const char *target_path, const void *data, size_t size) {
    char temp_path[512];
    snprintf(temp_path, sizeof(temp_path), "%s.tmp.%d", target_path, (int)getpid());

    /* 1. Open temporary file with exclusive creation flags */
    int fd = open(temp_path, O_WRONLY | O_CREAT | O_TRUNC | O_CLOEXEC, 0644);
    if (fd < 0) return -1;

    /* 2. Write all data, handling partial writes */
    const char *ptr = (const char *)data;
    size_t remaining = size;
    while (remaining > 0) {
        ssize_t written = write(fd, ptr, remaining);
        if (written <= 0) {
            if (written < 0 && errno == EINTR) continue;
            close(fd);
            unlink(temp_path);
            return -2;
        }
        ptr += written;
        remaining -= (size_t)written;
    }

    /* 3. Flush page cache to physical non-volatile medium */
    if (fdatasync(fd) != 0) {
        close(fd);
        unlink(temp_path);
        return -3;
    }

    /* 4. Close file descriptor */
    if (close(fd) != 0) {
        unlink(temp_path);
        return -4;
    }

    /* 5. Atomic POSIX directory rename: swaps directory entry atomically */
    if (rename(temp_path, target_path) != 0) {
        unlink(temp_path);
        return -5;
    }

    return 0; // Success: File guaranteed durable on disk!
}

int main(void) {
    const char *payload = "DEVICE_ID=42
CALIBRATION_OFFSET=1024
BAUD_RATE=115200
";
    const char *config_file = "device_config.cfg";

    printf("Executing atomic configuration write...
");
    if (atomic_write_file(config_file, payload, strlen(payload)) == 0) {
        printf("Configuration committed durably and atomically to %s
", config_file);
    } else {
        perror("Failed to persist configuration");
        return 1;
    }
    return 0;
}

26.7 Knowledge Verification & Self-Study Quiz

Self-Assessment Check

Q1: What does the O_CLOEXEC flag do when opening a file descriptor with open()?

Explanation: O_CLOEXEC sets the close-on-exec flag atomically, preventing security vulnerabilities where sensitive file descriptors or sockets are accidentally inherited by child processes.

Q2: What is the crucial difference between fflush() and fsync()?

Explanation: fflush() only leaves the user-space C library buffer; data is still vulnerable in volatile kernel RAM until fsync() or fdatasync() forces commit to disk.

Q3: What system call allows transmitting multiple non-contiguous memory buffers in a single atomic I/O operation?

Explanation: writev() consumes an array of struct iovec, gathering disparate memory buffers into a single kernel I/O request without intermediate copies.

Q4: Why does the Atomic Write-and-Rename pattern use rename() instead of overwriting the original file directly?

Explanation: Direct in-place writes leave the original file in a partially overwritten, corrupted state if interrupted; atomic rename guarantees that readers always observe either the old intact file or the new intact file.

Q5: What return value from read() indicates that an end-of-file (EOF) condition has been reached?

Explanation: In POSIX I/O, read() returns 0 on EOF, -1 on error (with errno set), and positive values indicating the number of bytes successfully read.
