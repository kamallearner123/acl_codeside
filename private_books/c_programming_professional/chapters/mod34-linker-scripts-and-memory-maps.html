Module 34: Linker Scripts & Memory Maps

Master bare-metal GNU ld linker script architecture for embedded microcontrollers. Deep dive into MEMORY and SECTIONS directives, VMA vs LMA address translation, copying .data from Flash to SRAM (AT>FLASH), zero-initializing .bss, stack placement (_estack), and custom memory regions.

⏱️ Duration: 60m
🎯 Standard: GNU ld Script Syntax / ELF Object Format
⚡ Target: ARM Cortex-M Flash & SRAM Layouts

34.1 The Linker's Role in Bare-Metal Systems

In a hosted operating system (such as Linux), the OS kernel’s ELF loader (ld-linux.so) allocates virtual memory pages, loads binary sections, and dynamically relocates symbols at runtime.

In a bare-metal microcontroller, there is no operating system and no loader. The silicon powers up directly into physical Flash ROM. The GNU Linker Script (.ld) is the master architectural blueprint that binds compiled object files into physical silicon addresses.

34.2 VMA vs. LMA: The AT>FLASH Directive

One of the most crucial concepts in embedded linker scripts is the distinction between:

  • VMA (Virtual / Execution Memory Address): The memory address where the code expects the data to reside when running (e.g. SRAM: 0x20000000).
  • LMA (Load Memory Address): The physical address where the data is permanently stored in the flashed binary image (e.g. Flash ROM: 0x08040000).

Initialized global variables (such as uint32_t g_timeout = 5000;) must retain their initial value even after power loss. Therefore, their values must be stored in Flash ROM (LMA). However, because they are mutable variables, they must execute in volatile SRAM (VMA). The linker script expresses this dual-address relationship using AT > FLASH: 

.data :
{
  . = ALIGN(4);
  _sdata = .;        /* Create symbol for start of .data in RAM */
  *(.data*)
  . = ALIGN(4);
  _edata = .;        /* Create symbol for end of .data in RAM */
} >RAM AT> FLASH     /* VMA is RAM; LMA is FLASH! */

_sidata = LOADADDR(.data); /* LMA address of .data in Flash */

34.3 Production STM32F4 Linker Script

/* ==============================================================================
 * Production GNU ld Linker Script for STM32F401RETx (512 KB Flash, 96 KB SRAM)
 * ============================================================================== */

ENTRY(Reset_Handler)

/* Highest address of the user mode stack (Top of RAM) */
_estack = ORIGIN(RAM) + LENGTH(RAM);

/* Minimum stack and heap sizes */
_Min_Heap_Size = 0x200;  /* 512 bytes */
_Min_Stack_Size = 0x400; /* 1024 bytes */

MEMORY
{
  FLASH (rx)  : ORIGIN = 0x08000000, LENGTH = 512K
  RAM   (rwx) : ORIGIN = 0x20000000, LENGTH = 96K
}

SECTIONS
{
  /* The startup vector table goes first into FLASH */
  .isr_vector :
  {
    . = ALIGN(4);
    KEEP(*(.isr_vector))
    . = ALIGN(4);
  } >FLASH

  /* Program code and read-only data */
  .text :
  {
    . = ALIGN(4);
    *(.text*)
    *(.glue_7)         /* Glue ARM to Thumb code */
    *(.glue_7t)
    *(.eh_frame)
    KEEP (*(.init))
    KEEP (*(.fini))
    . = ALIGN(4);
    _etext = .;        /* End of text section */
  } >FLASH

  .rodata :
  {
    . = ALIGN(4);
    *(.rodata*)
    . = ALIGN(4);
  } >FLASH

  /* Initialized data sections copied into RAM at startup */
  .data :
  {
    . = ALIGN(4);
    _sdata = .;
    *(.data*)
    . = ALIGN(4);
    _edata = .;
  } >RAM AT> FLASH

  _sidata = LOADADDR(.data);

  /* Uninitialized data section (.bss) zeroed at startup */
  .bss :
  {
    . = ALIGN(4);
    _sbss = .;
    *(.bss*)
    *(COMMON)
    . = ALIGN(4);
    _ebss = .;
  } >RAM

  /* Check that there is enough space left for Stack and Heap */
  ._user_heap_stack :
  {
    . = ALIGN(8);
    PROVIDE ( end = . );
    PROVIDE ( _end = . );
    . = . + _Min_Heap_Size;
    . = . + _Min_Stack_Size;
    . = ALIGN(8);
  } >RAM
}

34.4 Industrial Case Study: The Misaligned Flash DMA HardFault

The 4-Byte Unaligned Flash Sector Corruption

An automotive electronic control unit (ECU) experienced random HardFault crashes immediately following an Over-The-Air (OTA) firmware update in cold weather testing.

Investigation: The developers added a raw binary cryptographic certificate into Flash using a custom linker section: 

.crypto_cert :
{
  *(.crypto_cert)
} >FLASH

The certificate file was 387 bytes (not a multiple of 4). Because the linker section lacked . = ALIGN(4);, the subsequent .text section began on an odd 2-byte boundary (0x08010183).

When the CPU attempted to fetch a 32-bit Thumb-2 instruction from an unaligned address across flash word boundaries, the flash memory controller’s 128-bit prefetch buffer generated a bus error, crashing the ECU!

Resolution: Mandated explicit . = ALIGN(4); before and after every single section declaration in all linker scripts.

34.5 Hands-On Lab: Custom Section for Non-Volatile Bootloader Calibration

In this lab, you will define a custom flash memory region (CALIBRATION_ROM) in a linker script, and place a C configuration structure directly into it using GCC __attribute__((section(".cal_data"))).

1. Linker Script Snippet

MEMORY
{
  FLASH (rx)      : ORIGIN = 0x08000000, LENGTH = 480K
  CAL_ROM (r)     : ORIGIN = 0x08078000, LENGTH = 32K  /* Dedicated calibration sector */
  RAM (rwx)       : ORIGIN = 0x20000000, LENGTH = 96K
}

SECTIONS
{
  /* Standard sections ... */

  .cal_data :
  {
    . = ALIGN(4);
    _scal_data = .;
    KEEP(*(.cal_data))
    . = ALIGN(4);
    _ecal_data = .;
  } >CAL_ROM
}

2. C Source Code (calibration.c)

#include <stdint.h>

typedef struct {
    uint32_t magic_header;
    float    adc_voltage_scale;
    float    temperature_offset;
    uint32_t serial_number;
} device_calibration_t;

/* Explicitly locate this struct into the CAL_ROM sector */
__attribute__((section(".cal_data"), used))
const device_calibration_t g_factory_calibration = {
    .magic_header = 0xC001CAFE,
    .adc_voltage_scale = 3.3005f,
    .temperature_offset = -0.42f,
    .serial_number = 981245
};

34.6 Knowledge Verification & Self-Study Quiz

Self-Assessment Check

Q1: What does the LOADADDR(.data) linker script built-in function return?

Explanation: LOADADDR() returns the Load Memory Address (LMA), which the startup code reads to copy initial values from Flash into RAM.

Q2: Why must the KEEP() directive be applied to the vector table in the linker script (KEEP(*(.isr_vector)))?

Explanation: Because the vector table is referenced by hardware silicon rather than by explicit C code calls, the linker's dead-code elimination (--gc-sections) would discard it without KEEP().

Q3: What represents the initial value of the Main Stack Pointer (MSP) in ARM Cortex-M microcontrollers?

Explanation: On reset, the ARM core hardware loads SP from memory address 0x00000000 and the initial Program Counter (PC) from address 0x00000004.

Q4: What symbol in a linker script represents the current memory location counter?

Explanation: The dot (.) represents the location counter; modifying it advances or aligns memory allocation addresses.

Q5: What section contains global variables that are uninitialized or initialized to zero?

Explanation: The .bss section occupies RAM but zero bytes in the flash binary image; it is zeroed out in RAM by the startup code.
