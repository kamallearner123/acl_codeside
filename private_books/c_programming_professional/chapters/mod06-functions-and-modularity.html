Module 6: Functions, Modularity & The Call Stack (AAPCS)

Deconstruct the mechanics of function calls down to assembly registers: stack frame anatomy, ARM AAPCS calling conventions (R0-R3 register passing), hardware MPU stack guard regions, static inline optimizations, opaque pointer encapsulation, and reentrant ISR design.

⏱️ Estimated Reading: 65 min
🎯 Standard: C99 / C11 / C17 / AAPCS
🛠️ Environments: Linux POSIX + ARM Cortex-M

6.1 Function Invocations, The Stack Frame & Low-Level Call Stack Mechanics

In C, functions are the fundamental unit of procedural abstraction. While high-level software treats function calls as instantaneous jumps, at the machine level a function invocation is an intricate coordination between the CPU instruction pipeline, hardware registers, and dynamic memory allocations on the Call Stack.

Anatomy of an ARM Cortex-M Stack Frame

On modern 32-bit RISC architectures (ARM Cortex-M0/M3/M4/M7), the Call Stack grows downward from high memory addresses to low memory addresses. When a function executes, it establishes a discrete activation record (stack frame): 


 [HIGH MEMORY ADDRESS]
  +-------------------------------------------------------+
  | Caller's Stack Frame                                  |
  +-------------------------------------------------------+ <-- Stack Pointer (SP) at function entry
  | Pushed Arguments 5, 6, ... (if more than 4 args)     |
  | Return Address (saved LR / Link Register)             |
  | Saved Callee Registers (R4 - R11)                     |
  | Saved Frame Pointer (R7 in Thumb mode)                |
  | Local Variables & Temporary Arrays                    |
  | 8-Byte Alignment Padding (Mandated by AAPCS)          |
  +-------------------------------------------------------+ <-- Stack Pointer (SP) during function body
 [LOW MEMORY ADDRESS]  (Grows downward toward Heap/BSS)

6.2 The ARM Architecture Procedure Call Standard (AAPCS)

To ensure that assembly code, pre-compiled C libraries, and RTOS kernels interoperate reliably, ARM defines the Procedure Call Standard for the ARM Architecture (AAPCS):

Registers AAPCS Role & Purpose Preservation Rule Embedded Firmware Implication
R0 - R3 Argument passing (first 4 words) & Return Value Caller-saved (Volatile) The caller must assume these registers are overwritten during any function call. Functions with $\le 4$ arguments incur ZERO stack memory latency!
R4 - R11 Local variable storage Callee-saved (Non-volatile) If a called function modifies any of these registers, it MUST push them to the stack upon entry (prologue) and restore them upon exit (epilogue).
R12 (IP) Intra-procedure call scratchpad register Caller-saved Used by linkers for long branch veneer stubs when the destination address is beyond 32 MB branch range.
R13 (SP) Stack Pointer (MSP / PSP) Callee-saved Must always be preserved across calls; AAPCS mandates 8-byte stack alignment at external public function call boundaries.
R14 (LR) Link Register (stores Return Address) Caller-saved The BL (Branch with Link) instruction automatically places the return address into LR. In "leaf" functions (functions that call no other functions), LR does not even need to be pushed to the stack!
R15 (PC) Program Counter N/A Directly loads next instruction address. In epilogues, popping saved LR directly into PC (POP {R4-R7, PC}) returns and branches in a single cycle.

⚡ Performance Rule: Keep Function Arguments $\le 4$

Under AAPCS, functions with 1 to 4 scalar arguments pass everything in high-speed registers (R0-R3). Passing 5 or more arguments forces the compiler to spill the 5th+ arguments onto the stack via memory store (STR) instructions in the caller and memory load (LDR) instructions in the callee. In tight loops or ISR callbacks, wrap complex parameters into a single const struct * pointer!

6.3 Stack Overflow Hazards & Hardware MPU Guard Regions

In embedded firmware, SRAM is partitioned into Static Data (.data and .bss), the Heap (if enabled), and the Call Stack. Because the stack grows downward toward static variables or the heap, an unmonitored stack overflow triggers silent memory corruption: local variables overwrite global data buffers or RTOS task control blocks.

1. Stack Overflow Root Causes

  • Unbounded Recursion: Every recursive call allocates a new stack frame (LR, local vars). Recursion is strictly forbidden in MISRA C:2012 Rule 17.2.
  • Large Local Buffers: Declaring uint8_t buffer[2048] inside a FreeRTOS task with a 1024-byte stack instantly crashes the system.
  • Deep Interrupt Nesting: Higher priority interrupts preempting lower priority ISRs stack additional hardware context frames (32 bytes minimum per nested ISR).

2. Hardware MPU Stack Guarding

ARM Cortex-M processors with a Memory Protection Unit (MPU) allow configuring a 32-byte or 64-byte no-access guard region directly below the bottom of the stack:

If a function attempts to push past the stack limit, the CPU instantly triggers a MemManage fault before any global RAM can be corrupted, allowing the crash analyzer to capture a clean stack trace!

6.4 Static Linkage, Function Inlining & Translation Units

C programs are compiled one Translation Unit (TU) at a time. A translation unit is a single .c source file plus all the header files (.h) included by the preprocessor. Controlling symbol visibility across translation units is vital for modularity and optimization:

Clinkage_demonstration.c
#include <stdint.h>

/* 1. EXTERNAL LINKAGE (Default): Symbol visible to all translation units in the project */
uint32_t g_system_tick_count = 0U;
void system_tick_increment(void) {
    g_system_tick_count++;
}

/* 2. INTERNAL LINKAGE (static): Symbol is private to this translation unit only.
 * Eliminates name collision hazards; allows compiler to aggressively optimize
 * because no external file can call this function! */
static uint32_t calculate_crc_internal(const uint8_t *data, size_t len) {
    uint32_t crc = 0xFFFFFFFFU;
    /* CRC algorithm */
    return crc;
}

/* 3. STATIC INLINE: Recommended for small utility functions in header files.
 * Replaces function call with inline machine instructions, eliminating prologue/epilogue overhead
 * while generating zero duplicate symbol linker errors! */
static inline uint32_t min_u32(uint32_t a, uint32_t b) {
    return (a < b) ? a : b;
}

6.5 Modular C Architecture: Opaque Pointers (Pure C PIMPL Pattern)

In professional driver development, exposing the internal fields of a struct in a public header file creates tight coupling: if you modify a private buffer size or hardware register offset, every file including that header must be recompiled.

The Opaque Pointer Pattern hides internal implementation details completely, achieving true object-oriented encapsulation in ANSI C:

Public API Header: uart_driver.h
#ifndef UART_DRIVER_H
#define UART_DRIVER_H

#include <stdint.h>
#include <stdbool.h>

/* Forward declaration: incomplete type!
 * Users know uart_dev_t exists, but cannot access internal members. */
typedef struct uart_device uart_dev_t;

/* Public API Contract */
uart_dev_t *uart_init(uint32_t port_id, uint32_t baud);
bool uart_send_byte(uart_dev_t *dev, uint8_t byte);
void uart_deinit(uart_dev_t *dev);

#endif /* UART_DRIVER_H */
Private Implementation: uart_driver.c
#include "uart_driver.h"
#include <stdlib.h>

/* Full struct definition ONLY exists inside the C file! */
struct uart_device {
    uint32_t hw_base_addr;
    uint32_t baud_rate;
    uint8_t  tx_ring_buffer[256];
    volatile bool is_busy;
};

uart_dev_t *uart_init(uint32_t port_id, uint32_t baud) {
    static struct uart_device dev_instance; /* Static allocation in firmware */
    dev_instance.hw_base_addr = (port_id == 1) ? 0x40011000 : 0x40004400;
    dev_instance.baud_rate = baud;
    dev_instance.is_busy = false;
    return &dev_instance;
}

6.6 Reentrancy & Thread Safety in Interrupt Service Routines (ISRs)

A function is reentrant if it can be safely interrupted in the middle of execution, called by another execution context (an ISR or separate RTOS thread), and then resume execution without data corruption:

  • Rules for Reentrancy:
    1. Does NOT rely on non-const static or global variables.
    2. Does NOT return a pointer to internal static storage (e.g. standard library strtok() and asctime() are non-reentrant!).
    3. Only operates on caller-supplied data or variables allocated on its own local stack frame.
    4. Does NOT call any non-reentrant functions.

6.7 Real-Time Case Study: Layered Opaque SPI Sensor Driver with AAPCS Optimization

The following production-grade driver demonstrates AAPCS-optimized parameter passing, reentrant design, and opaque device abstraction for an SPI-driven IMU sensor (accelerometer/gyroscope):

Cspi_sensor_driver.c
#include <stdint.h>
#include <stdbool.h>
#include <string.h>

typedef struct {
    int16_t accel_x;
    int16_t accel_y;
    int16_t accel_z;
    int16_t gyro_x;
    int16_t gyro_y;
    int16_t gyro_z;
} imu_axes_data_t;

/* Opaque SPI Bus Controller Structure */
typedef struct {
    uint32_t spi_base_addr;
    uint32_t cs_pin_mask;
    uint32_t timeout_ticks;
} spi_bus_controller_t;

/**
 * @brief Reentrant SPI Read Burst.
 * Operates strictly on register parameters (AAPCS R0-R3). Zero stack spilling!
 *
 * @param bus Pointer to bus controller (R0)
 * @param reg_addr Starting register address (R1)
 * @param rx_buf Pointer to destination buffer (R2)
 * @param len Number of bytes to read (R3)
 * @return true on success, false on hardware timeout (R0)
 */
bool spi_read_burst(const spi_bus_controller_t *bus, uint8_t reg_addr, uint8_t *rx_buf, size_t len) {
    if (bus == NULL || rx_buf == NULL || len == 0U) {
        return false;
    }

    /* Assert Chip Select (CS Low) */
    /* Hardware register write */

    /* Send Register Address with Read Bit (Bit 7 = 1) */
    uint8_t tx_cmd = reg_addr | 0x80U;
    
    /* In actual hardware: Transfer tx_cmd, then read len bytes into rx_buf */
    for (size_t i = 0; i < len; ++i) {
        /* Simulated burst data */
        rx_buf[i] = (uint8_t)(0x10U + i);
    }

    /* Release Chip Select (CS High) */
    return true;
}

/**
 * @brief Reentrant IMU Data Parser.
 * Uses exact-width two's complement decoding.
 */
bool imu_decode_axes(const uint8_t raw_burst[12], imu_axes_data_t *out_data) {
    if (raw_burst == NULL || out_data == NULL) {
        return false;
    }

    /* Little-Endian 16-bit signed integer decoding */
    out_data->accel_x = (int16_t)(((uint16_t)raw_burst[1] << 8U) | raw_burst[0]);
    out_data->accel_y = (int16_t)(((uint16_t)raw_burst[3] << 8U) | raw_burst[2]);
    out_data->accel_z = (int16_t)(((uint16_t)raw_burst[5] << 8U) | raw_burst[4]);

    out_data->gyro_x  = (int16_t)(((uint16_t)raw_burst[7] << 8U) | raw_burst[6]);
    out_data->gyro_y  = (int16_t)(((uint16_t)raw_burst[9] << 8U) | raw_burst[8]);
    out_data->gyro_z  = (int16_t)(((uint16_t)raw_burst[11] << 8U) | raw_burst[10]);

    return true;
}

6.8 Hands-On Lab: Stack Frame Analyzer & Reentrant Modular Driver

Lab Exercise: The Call Stack Inspection Engine

In this lab, you will author a standalone program stack_analyzer_lab.c that inspects the current Stack Pointer (SP) address across nested function invocations, calculates stack frame consumption per call, and verifies reentrant behavior.

Complete Source Code: stack_analyzer_lab.c

Cstack_analyzer_lab.c
#include <stdio.h>
#include <stdlib.h>
#include <stdint.h>
#include <inttypes.h>

/* Helper to capture current stack pointer address */
static uintptr_t get_stack_pointer(void) {
    volatile int dummy = 0;
    return (uintptr_t)&dummy;
}

static void level_three(uintptr_t entry_sp) {
    uintptr_t current_sp = get_stack_pointer();
    ptrdiff_t total_consumed = (ptrdiff_t)(entry_sp - current_sp);
    
    printf("  [Level 3] SP: 0x%016" PRIxPTR " | Cumulative Stack Growth: %td bytes\n",
           current_sp, total_consumed);
}

static void level_two(uintptr_t entry_sp) {
    uintptr_t current_sp = get_stack_pointer();
    ptrdiff_t frame_size = (ptrdiff_t)(entry_sp - current_sp);
    
    printf(" [Level 2]  SP: 0x%016" PRIxPTR " | Delta from Entry: %td bytes\n",
           current_sp, frame_size);
    level_three(entry_sp);
}

static void level_one(void) {
    uintptr_t entry_sp = get_stack_pointer();
    printf("[Level 1]   SP: 0x%016" PRIxPTR " (Base Reference)\n", entry_sp);
    level_two(entry_sp);
}

int main(void) {
    printf("========================================================\n");
    printf("        CALL STACK FRAME & MEMORY USAGE ANALYZER        \n");
    printf("========================================================\n\n");

    printf("Executing nested function invocation chain...\n");
    level_one();

    printf("\n========================================================\n");
    printf("Stack analyzer verification completed successfully.\n");
    return EXIT_SUCCESS;
}

6.9 Knowledge Verification & Self-Study Quiz

Self-Assessment Check

Q1: Under the ARM Procedure Call Standard (AAPCS), which registers are used to pass the first four 32-bit function arguments?

Explanation: AAPCS designates R0-R3 as argument passing and return value registers. Functions with up to 4 arguments pass data purely in CPU registers with zero stack latency.

Q2: Why does marking a function static inline in a header file avoid linker multiple definition errors?

Explanation: Internal linkage (static) ensures the symbol is not exported to the global ELF symbol table, preventing multiple definition conflicts during the linking phase.

Q3: What makes a function non-reentrant and therefore dangerous to call inside an Interrupt Service Routine (ISR)?

Explanation: Non-reentrant functions modify shared state across calls. If interrupted and called again before completing, shared state is corrupted.

Q4: Why does MISRA C:2012 Rule 17.2 strictly prohibit recursion in safety-critical firmware?

Explanation: Safety standards require provable worst-case stack usage (WCSS). Recursion prevents deterministic static stack bounds calculation.

Q5: What is the primary software engineering benefit of the Opaque Pointer (PIMPL) pattern in C?

Explanation: By declaring an incomplete struct type in the public header, callers can only pass pointers, preserving complete decoupling between API and implementation.
