Module 20: Static Analysis & Automated Code Quality

Deep dive into static analysis theory, Abstract Syntax Trees (AST), Control Flow Graphs (CFG), symbolic execution, GCC/Clang compiler warning enforcement, Cppcheck rule customization, and Clang-Tidy LLVM integration for safety-critical C software.

⏱️ Duration: 50m
🎯 Standard: MISRA C:2012 / CERT C / ISO 26262 ASIL-D
⚡ Target: Linux x86_64 / Cross-Platform Toolchains

20.1 Theoretical Foundations of Static Analysis

Unlike dynamic analysis, which evaluates a single concrete execution path under specific input stimuli, Static Analysis evaluates the complete mathematical state space of a program without running it. It parses C source code into formal structural representations:

Static Analysis Pipeline Architecture
C Source Code (.c) ──▶ [ Lexer & Parser ] ──▶ Abstract Syntax Tree (AST)
                                                     │
                                            Semantic Analysis
                                                     ▼
                                          Control Flow Graph (CFG)
                                                     │
                       ┌─────────────────────────────┴─────────────────────────────┐
                       ▼                                                           ▼
         [ Data Flow & Taint Analysis ]                              [ Symbolic Execution Engine ]
         (Tracks uninitialized variables,                            (Evaluates feasibility of
          null pointer propagation, dead code)                        all branch paths symbolically)
                       │                                                           │
                       └─────────────────────────────┬─────────────────────────────┘
                                                     ▼
                                     [ Defect & MISRA Violation Reports ]

Static Analysis Disciplines

  • Syntactic Pattern Matching: Fast AST traversal checking style, naming conventions, or prohibited constructs (e.g. goto, malloc in embedded loops).
  • Dataflow Analysis: Tracks the propagation of values across variables and registers (detecting variables used before initialization).
  • Taint Analysis: Marks external user or network inputs as "tainted" and verifies they do not reach security-sensitive sinks (such as memcpy lengths or array indices) without bounds checking.
  • Path-Sensitive Symbolic Execution: Represents program variables as mathematical symbols and explores execution paths, proving whether an assertion can ever be violated under any theoretical combination of inputs.

20.2 Compiler Warnings as the First Line of Defense

Before deploying dedicated third-party static analyzers, high-reliability engineering requires configuring the compiler itself as a zero-tolerance static analysis engine.

Production Safety-Critical GCC/Clang Compiler Flags

# ==============================================================================
# Production Safety-Critical Warning Configuration
# ==============================================================================
WARN_FLAGS := -Wall -Wextra -Wpedantic               -Werror               -Wconversion               -Wsign-conversion               -Wshadow               -Wdouble-promotion               -Wstrict-prototypes               -Wundef               -Wformat=2               -Wformat-security               -Wnull-dereference               -Wwrite-strings               -Wcast-align               -Wlogical-op               -Wduplicated-cond               -Wduplicated-branches
Flag Defect Category Caught Why It Matters in Embedded C
-Wconversion Implicit numeric narrowing / signedness conversion Prevents silent truncation of 32-bit registers into 16-bit or 8-bit variables.
-Wshadow Local variable shadowing outer variable Prevents local function parameters from accidentally hiding global configuration structs.
-Wdouble-promotion Implicit promotion of float to double Prevents software emulation of 64-bit doubles on Cortex-M4F single-precision hardware FPUs.
-Wnull-dereference Compile-time provable NULL pointer dereference Catches code paths where a pointer is checked for NULL but dereferenced regardless.

20.3 Cppcheck: Deep Static Analysis & MISRA C Integration

Cppcheck is a dedicated static analysis tool designed specifically for C and C++. Unlike compilers, which stop analyzing when code is syntactically legal C, Cppcheck looks specifically for undefined behavior, resource leaks, and logic flaws.

Automating Cppcheck in Build Pipelines

cppcheck --enable=all          --inconclusive          --error-exitcode=1          --suppress=missingIncludeSystem          --inline-suppr          -I include/          src/

Enforcing MISRA C:2012 with Cppcheck

Cppcheck includes an automated MISRA addon (misra.py). By feeding the MISRA rule table text file, Cppcheck verifies compliance against safety-critical automotive standards: 

cppcheck --addon=misra.py --rule-texts=misra_rules.txt src/

20.4 Clang-Tidy: LLVM AST Matchers & Automated Modernization

Clang-Tidy is an LLVM-based linter and static analysis platform. It provides a modular check framework capable of not only reporting errors, but also applying automated source-level patches (-fix).

20.5 Industrial Case Study: Ariane 5 Flight 501 Numeric Conversion Failure

The $370 Million Float-to-Int Truncation Disaster

On June 4, 1996, the maiden flight of the European Ariane 5 launcher ended in catastrophic destruction 37 seconds after liftoff. The rocket veered sharply off trajectory, causing structural breakup under aerodynamic aerodynamic loads, triggering the onboard automated flight termination system.

Inquiry Board Findings: The failure occurred in the Inertial Reference System (SRI). A software module calculated the horizontal bias (a variable representing the vehicle's horizontal velocity).

The value was represented as a 64-bit IEEE-754 floating-point number. In an unshielded code section, the software attempted to convert this 64-bit float into a 16-bit signed integer. 

/* Conceptual representation of the Ariane 5 truncation defect */
double horizontal_bias = calculate_horizontal_velocity(); /* > 32767.0 on Ariane 5! */
int16_t truncated_bias = (int16_t)horizontal_bias;         /* Hardware Operand Error! */

On the earlier, slower Ariane 4 rocket, the horizontal velocity physically never exceeded 32,767. However, Ariane 5's higher thrust caused the velocity to exceed the range of a 16-bit signed integer. The conversion triggered an unhandled hardware arithmetic overflow exception, causing the primary SRI computer to shut down, followed immediately by the identical backup unit.

How Modern Static Analysis Prevents This: Compiling with -Wconversion or Clang-Tidy’s bugprone-narrowing-conversions flags this line at compile-time as an unsafe loss of precision, halting the build before binary deployment.

20.6 Hands-On Lab: Setting up an Automated Static Analysis Pipeline

In this lab, you will analyze a C telemetry module containing subtle static analysis violations (implicit truncation, uninitialized variables, and shadow variables), and configure Cppcheck and Clang-Tidy to flag every defect automatically.

Defective Code (lab_static.c)

#include <stdio.h>
#include <stdint.h>

static uint32_t g_system_id = 42;

/* Defect 1: Implicit conversion / truncation from uint32_t to uint16_t */
static uint16_t scale_telemetry(uint32_t raw_value) {
    uint16_t scaled = raw_value; /* Truncation without explicit cast */
    return scaled;
}

/* Defect 2: Variable shadowing */
static void process_id(uint32_t g_system_id) {
    printf("Processing ID: %u
", g_system_id);
}

/* Defect 3: Uninitialized variable along error path */
static int read_sensor_voltage(int error_flag, int *out_voltage) {
    int v;
    if (error_flag == 0) {
        v = 3300; // 3.3V
    }
    /* If error_flag != 0, v is uninitialized! */
    *out_voltage = v;
    return 0;
}

int main(void) {
    uint32_t raw = 0x12345678;
    uint16_t s = scale_telemetry(raw);
    process_id(99);

    int volt;
    read_sensor_voltage(1, &volt);
    printf("Scaled: 0x%04X, Volt: %d
", s, volt);
    return 0;
}

Verification Script

# 1. Test Compiler Static Analysis
gcc -Wall -Wextra -Wconversion -Wshadow -Wuninitialized -c lab_static.c
# Compiler immediately reports:
# - warning: conversion from 'uint32_t' to 'uint16_t' may change value [-Wconversion]
# - warning: declaration of 'g_system_id' shadows a global declaration [-Wshadow]
# - warning: 'v' may be used uninitialized [-Wmaybe-uninitialized]

# 2. Test Cppcheck
cppcheck --enable=all --error-exitcode=1 lab_static.c
# Cppcheck reports:
# [lab_static.c:24]: (error) Uninitialized variable: v

20.7 Knowledge Verification & Self-Study Quiz

Self-Assessment Check

Q1: What compiler flag flags implicit type conversions that may alter the numeric value or signedness of an expression?

Explanation: -Wconversion warns whenever an expression undergoes implicit conversion between integers that could alter its value (such as assigning a 32-bit int to a 16-bit short).

Q2: What is the primary difference between an Abstract Syntax Tree (AST) and a Control Flow Graph (CFG)?

Explanation: The AST represents program syntax hierarchy (expressions, declarations, statements), whereas the CFG represents execution graph blocks connected by directed edges representing branch decisions.

Q3: Why is -Wdouble-promotion vital when compiling C code for single-precision ARM Cortex-M4F processors?

Explanation: Without -Wdouble-promotion, writing float x = y * 0.5; implicitly promotes y to double because 0.5 is a 64-bit double literal, destroying DSP algorithm performance.

Q4: What role does Taint Analysis play in secure C development?

Explanation: Taint analysis identifies vulnerability pathways where untrusted external data could influence execution flow or buffer bounds without sanitization.

Q5: What command instructs Clang-Tidy to automatically apply its suggested code fixes?

Explanation: The -fix flag instructs Clang-Tidy to directly rewrite the source code with compiler-verified refactorings and corrections.
