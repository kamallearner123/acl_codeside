Module 17: Build Systems (Make & Modern CMake)

⏱️ Duration: 60m
🎯 Standard: POSIX Make / GNU Make 4.x / CMake 3.20+
⚡ Target: ARM Cortex-M / Linux x86_64

17.1 GNU Make Internals & Dependency Resolution Graphs

At its computational core, GNU Make is an engine that evaluates a Directed Acyclic Graph (DAG) of target files, prerequisite files, and shell execution rules. Make determines whether a target needs to be updated by comparing the target's filesystem modification timestamp (mtime) against the modification timestamps of all its prerequisites.

DAG Dependency Resolution & Timestamp Traversal
                 ┌──────────────────┐
                 │    firmware.elf  │ (mtime: 10:04:15)
                 └────────┬─────────┘
          Prerequisites:  │  Linker stage (arm-none-eabi-gcc)
            ┌─────────────┴─────────────┐
            ▼                           ▼
     ┌──────────────┐            ┌──────────────┐
     │    main.o    │            │   sensor.o   │ (mtime: 10:04:10)
     └──────┬───────┘            └──────┬───────┘
  Prereq:   │                     Prereq:   │
   ┌────────┴────────┐             ┌────────┴────────┐
   ▼                 ▼             ▼                 ▼
┌───────┐       ┌──────────┐    ┌──────────┐    ┌──────────┐
│main.c │       │ sensor.h │    │ sensor.c │    │ sensor.h │ (mtime: 10:05:00 - TOUCHED!)
└───────┘       └──────────┘    └──────────┘    └──────────┘
  (Make detects: sensor.h mtime > sensor.o & main.o -> triggers recompilation of both)

The Fatal Flaw of Naive Makefiles

Consider the traditional, naive rule found in beginner embedded projects: 

%.o: %.c
	$(CC) $(CFLAGS) -c $< -o $@

In this naive rule, the prerequisite list contains only %.c. If an engineer modifies sensor.h (for example, adding a struct member or modifying an enum value), Make inspects main.o and main.c. Because main.c's timestamp has not changed, Make assumes main.o is completely up-to-date and skips recompilation.

Catastrophic Failure Mode: Struct Layout Skew
When header dependencies are ignored, module sensor.c might recompile against the new struct layout while main.c retains object code compiled against the old struct layout. When linked, the binary executes with conflicting memory offsets, resulting in silent memory corruption, hard faults, or telemetry field swapping in production hardware.

GCC Automatic Dependency Generation (-MMD, -MP)

The robust, production-grade solution is to instruct the compiler preprocessor to emit Makefile-compatible dependency rules during compilation using GCC flags:

  • -MD: Emits dependency rules into a .d file for all headers, including system headers (<stdio.h>, <stdint.h>).
  • -MMD: Emits dependency rules into a .d file for user headers only (omitting system headers), which speeds up Make parsing significantly.
  • -MP: Generates an empty phony target for every header file encountered in the dependency tree.

Why is -MP essential? Without -MP, if you delete or rename a header file (e.g., refactoring legacy_adc.h into adc_driver.h), Make will read the existing .d file from the previous build, see that legacy_adc.h is a prerequisite, search for it on disk, discover it is missing, and crash with: 

make: *** No rule to make target 'legacy_adc.h', needed by 'main.o'. Stop.

With -MP, the compiler adds dummy phony targets like legacy_adc.h: into the .d file. When Make discovers the file is gone, it treats the prerequisite as satisfied and proceeds to invoke the compiler, which cleanly updates the object and dependency files.

17.2 Production ARM Cortex-M Makefile Architecture

Below is a complete, industrial-grade Makefile engineered for embedded ARM Cortex-M firmware (such as STM32, NXP LPC, or TI MSPM0). It enforces:

  1. Complete out-of-tree build artifact isolation in build/.
  2. Automated -MMD -MP header dependency tracking via -include $(DEPS).
  3. Dual target configurations (Debug with -Og -g3, Release with -O2 -flto -DNDEBUG).
  4. Automated memory footprint reporting via size.
# ==============================================================================
# Professional Embedded C Makefile Architecture
# Target: ARM Cortex-M4F (STM32F401RE / STM32F411RE)
# ==============================================================================
PROJECT         ?= telemetry_firmware
BUILD_DIR       ?= build
CROSS_COMPILE   ?= arm-none-eabi-

CC              := $(CROSS_COMPILE)gcc
CXX             := $(CROSS_COMPILE)g++
OBJCOPY         := $(CROSS_COMPILE)objcopy
OBJDUMP         := $(CROSS_COMPILE)objdump
SIZE            := $(CROSS_COMPILE)size

# ------------------------------------------------------------------------------
# Target Architecture Flags (ARM Cortex-M4F, Hard VFPv4)
# ------------------------------------------------------------------------------
MCU_FLAGS       := -mcpu=cortex-m4 -mthumb -mfpu=fpv4-sp-d16 -mfloat-abi=hard

# ------------------------------------------------------------------------------
# Source & Include Directories
# ------------------------------------------------------------------------------
C_SOURCES       := src/main.c                    src/bsp/system_clock.c                    src/drivers/uart_driver.c                    src/drivers/sensor_fusion.c

ASM_SOURCES     := startup/startup_stm32f401xe.s

INCLUDES        := -Iinclude                    -Iinclude/bsp                    -Iinclude/drivers                    -Icmsis/include

LDSCRIPT        := linker/STM32F401RETx_FLASH.ld

# ------------------------------------------------------------------------------
# Compiler & Preprocessor Flags
# ------------------------------------------------------------------------------
# -MMD -MP: Generate dependency files automatically
# -Wall -Wextra -Wpedantic: Maximum warning coverage
# -Wconversion -Wshadow -Wdouble-promotion: Safety-critical static checks
# -fdata-sections -ffunction-sections: Strip dead code during link
CPPFLAGS        := $(INCLUDES) -DSTM32F401xE -MMD -MP

CFLAGS          := $(MCU_FLAGS)                    -std=c11                    -Wall -Wextra -Wpedantic                    -Wconversion -Wshadow -Wdouble-promotion -Wstrict-prototypes                    -fdata-sections -ffunction-sections

# Build Configuration: Debug vs Release
BUILD_TYPE      ?= Debug
ifeq ($(BUILD_TYPE),Debug)
  CFLAGS        += -Og -g3 -DDEBUG
else
  CFLAGS        += -O2 -g -flto -DNDEBUG
endif

# Linker Flags: Garbage-collect unused code/data (--gc-sections)
LDFLAGS         := $(MCU_FLAGS)                    -T$(LDSCRIPT)                    -Wl,-Map=$(BUILD_DIR)/$(PROJECT).map,--cref                    -Wl,--gc-sections                    -specs=nano.specs -specs=nosys.specs

# ------------------------------------------------------------------------------
# Object File Lists
# ------------------------------------------------------------------------------
OBJS            := $(addprefix $(BUILD_DIR)/, $(C_SOURCES:.c=.o))
OBJS            += $(addprefix $(BUILD_DIR)/, $(ASM_SOURCES:.s=.o))
DEPS            := $(OBJS:.o=.d)

# Phony Targets
.PHONY: all clean flash size disasm

all: $(BUILD_DIR)/$(PROJECT).elf $(BUILD_DIR)/$(PROJECT).bin $(BUILD_DIR)/$(PROJECT).hex size

# Linking
$(BUILD_DIR)/$(PROJECT).elf: $(OBJS) | $(BUILD_DIR)
	@echo " [LD]  $@"
	@$(CC) $(OBJS) $(LDFLAGS) -o $@

# Binary generation
$(BUILD_DIR)/$(PROJECT).bin: $(BUILD_DIR)/$(PROJECT).elf
	@echo " [BIN] $@"
	@$(OBJCOPY) -O binary $< $@

$(BUILD_DIR)/$(PROJECT).hex: $(BUILD_DIR)/$(PROJECT).elf
	@echo " [HEX] $@"
	@$(OBJCOPY) -O ihex $< $@

# Compile C Sources
$(BUILD_DIR)/%.o: %.c
	@mkdir -p $(dir $@)
	@echo " [CC]  $<"
	@$(CC) $(CPPFLAGS) $(CFLAGS) -c $< -o $@

# Assemble Assembly Sources
$(BUILD_DIR)/%.o: %.s
	@mkdir -p $(dir $@)
	@echo " [AS]  $<"
	@$(CC) $(MCU_FLAGS) -c $< -o $@

$(BUILD_DIR):
	@mkdir -p $@

size: $(BUILD_DIR)/$(PROJECT).elf
	@echo "--- Target Memory Utilization ---"
	@$(SIZE) -B $<

disasm: $(BUILD_DIR)/$(PROJECT).elf
	@$(OBJDUMP) -d -S $< > $(BUILD_DIR)/$(PROJECT).asm
	@echo "Disassembly written to $(BUILD_DIR)/$(PROJECT).asm"

clean:
	@echo " [CLEAN] Removing build directory..."
	@rm -rf $(BUILD_DIR)

# Include automatically generated header dependencies (-MMD -MP)
# The minus sign suppresses errors when .d files do not yet exist
-include $(DEPS)

17.3 Modern Target-Based CMake (3.20+) Architecture

Legacy CMake (version 2.8 and early 3.x) relied on directory-scoped global variables such as include_directories(), add_definitions(), and link_libraries(). In complex multi-subsystem embedded projects, this legacy pattern caused global variable pollution and unexpected flag leakage between unit tests and firmware targets.

Modern CMake (3.15+) introduces an Object-Oriented target model. Every library, driver, and executable is an independent target possessing encapsulated properties. Dependencies between targets are declared explicitly, and transitive properties propagate strictly through visibility modifiers:

Visibility Scope Target Itself Consumes? Downstream Dependents Inherit? Embedded Typical Use Case
PRIVATE Yes No Internal driver implementation headers (e.g. src/drivers/i2c_reg_map.h).
INTERFACE No Yes Header-only abstractions, CMSIS headers, interface contracts (pure virtual vtables).
PUBLIC Yes Yes Driver API header exposed to both the driver source and application callers.

Transitive Target Dependency Graph in CMake

# Modern CMake Target Configuration
add_library(bsp_uart STATIC
    src/uart.c
)

target_include_directories(bsp_uart
    PUBLIC
        ${CMAKE_CURRENT_SOURCE_DIR}/include     # Consumers need uart.h
    PRIVATE
        ${CMAKE_CURRENT_SOURCE_DIR}/src         # Only uart.c needs internal register maps
)

target_compile_options(bsp_uart
    PRIVATE
        -Wall -Wextra -Wconversion              # Strict warnings on internal compilation
)

# Application Executable
add_executable(firmware src/main.c)
target_link_libraries(firmware PRIVATE bsp_uart)
# 'firmware' automatically inherits bsp_uart's PUBLIC include directories!

17.4 Cross-Compiling with CMake Toolchain Files

CMake requires an external toolchain file to instruct it that it is targeting a bare-metal platform rather than the host Linux or macOS environment. Without a toolchain file, CMake will attempt to test-compile host binaries, query host glibc libraries, and fail when searching for embedded libraries.

Production Toolchain File: arm-none-eabi.cmake

# ------------------------------------------------------------------------------
# arm-none-eabi.cmake - Bare-Metal Cross-Compilation Toolchain
# ------------------------------------------------------------------------------
set(CMAKE_SYSTEM_NAME Generic)
set(CMAKE_SYSTEM_PROCESSOR arm)

# Specify Cross-Compiler Executables
set(TOOLCHAIN_PREFIX arm-none-eabi-)
find_program(CMAKE_C_COMPILER   ${TOOLCHAIN_PREFIX}gcc     REQUIRED)
find_program(CMAKE_CXX_COMPILER ${TOOLCHAIN_PREFIX}g++     REQUIRED)
find_program(CMAKE_ASM_COMPILER ${TOOLCHAIN_PREFIX}gcc     REQUIRED)
find_program(CMAKE_OBJCOPY      ${TOOLCHAIN_PREFIX}objcopy REQUIRED)
find_program(CMAKE_SIZE_UTIL    ${TOOLCHAIN_PREFIX}size    REQUIRED)

# Inhibit CMake from trying to link an executable during initial compiler check
# (Bare-metal linking fails without a valid linker script)
set(CMAKE_TRY_COMPILE_TARGET_TYPE STATIC_LIBRARY)

# Prevent CMake from searching for host libraries and headers
set(CMAKE_FIND_ROOT_PATH_MODE_PROGRAM NEVER)
set(CMAKE_FIND_ROOT_PATH_MODE_LIBRARY ONLY)
set(CMAKE_FIND_ROOT_PATH_MODE_INCLUDE ONLY)
set(CMAKE_FIND_ROOT_PATH_MODE_PACKAGE ONLY)

Root CMakeLists.txt with Linker Script & Post-Build Size Rule

cmake_minimum_required(VERSION 3.20)
project(cortex_m_firmware C ASM)

set(CMAKE_C_STANDARD 11)
set(CMAKE_C_STANDARD_REQUIRED ON)

# Hardware Architecture Compilation Flags
set(ARM_FLAGS -mcpu=cortex-m4 -mthumb -mfpu=fpv4-sp-d16 -mfloat-abi=hard)
add_compile_options(${ARM_FLAGS} -Wall -Wextra -Wpedantic -Wconversion -ffunction-sections -fdata-sections)

# Target Linker Script
set(LINKER_SCRIPT ${CMAKE_CURRENT_SOURCE_DIR}/linker/STM32F401RETx_FLASH.ld)
add_link_options(${ARM_FLAGS} -T${LINKER_SCRIPT} -Wl,--gc-sections -specs=nano.specs -specs=nosys.specs)

# Define Executable
add_executable(${PROJECT_NAME}.elf
    src/main.c
    src/sensor.c
    startup/startup_stm32f401xe.s
)

# Custom Command: Generate .bin and print size after successful build
add_custom_command(TARGET ${PROJECT_NAME}.elf POST_BUILD
    COMMAND ${CMAKE_OBJCOPY} -O binary ${PROJECT_NAME}.elf ${PROJECT_NAME}.bin
    COMMAND ${CMAKE_SIZE_UTIL} -B ${PROJECT_NAME}.elf
    COMMENT "Building binary and analyzing memory utilization"
)

17.5 Industrial Case Study: The Out-of-Date Header Flight Computer Glitch

The Telemetry Packet Shift Incident (Aerospace UAV Subsystem)

During pre-flight testing of an unmanned aerial system (UAS), ground telemetry reported corrupt attitude values (pitch = 180°, roll = NaN) even though the on-board AHRS unit was verified operational on an oscilloscope.

Root Cause Analysis: The communication protocol header telemetry_packet.h was updated by the navigation team to insert a 4-byte uint32_t flight_mode_status field before the float pitch and float roll fields. The developers ran make on their local workstation.

Because the project’s Makefile lacked automated dependency tracking (-MMD -MP), Make noted that nav_task.c had been edited and recompiled it, but left telemetry_transmitter.c untouched because its .c file was older than its .o file.

Nav Task compiled with NEW struct (size = 28 bytes): [0..3: hdr] [4..7: mode] [8..11: pitch] [12..15: roll] [16..27: payload] Transmitter compiled with OLD struct (size = 24 bytes): [0..3: hdr] [4..7: pitch] [8..11: roll] [12..23: payload]

When telemetry_transmitter.c read pitch from offset 4, it was actually broadcasting the integer bits of flight_mode_status interpreted as an IEEE-754 floating-point number, corrupting all downlinked data.

Corrective Action: All project Makefiles were refactored to enforce -MMD -MP and -include $(DEPS). The CI/CD pipeline was configured to build with strict dependency checks and enforce out-of-tree builds.

17.6 Hands-On Lab: Multi-Module C Project with Dependency Tracking

In this laboratory, you will create a multi-module C project with complete automated dependency tracking. You will prove that editing a header file automatically triggers the recompilation of all dependent translation units without touching the .c files.

Step 1: File Structure

lab_build/
├── include/
│   ├── config.h
│   └── sensor.h
├── src/
│   ├── main.c
│   └── sensor.c
└── Makefile

Step 2: Source Files

include/config.h:

#ifndef CONFIG_H_
#define CONFIG_H_

#define SENSOR_SAMPLING_RATE_HZ  (100U)
#define TELEMETRY_MAGIC_CODE     (0xDEADBEEFU)

#endif /* CONFIG_H_ */

include/sensor.h:

#ifndef SENSOR_H_
#define SENSOR_H_

#include <stdint.h>
#include "config.h"

typedef struct {
    uint32_t sample_id;
    int32_t  temperature_mC;
    uint32_t status_flags;
} sensor_reading_t;

int sensor_init(void);
int sensor_poll(sensor_reading_t *out_reading);

#endif /* SENSOR_H_ */

src/sensor.c:

#include "sensor.h"
#include <stdio.h>

static uint32_t g_sample_counter = 0;

int sensor_init(void) {
    printf("[SENSOR] Initialized at rate %u Hz
", SENSOR_SAMPLING_RATE_HZ);
    return 0;
}

int sensor_poll(sensor_reading_t *out_reading) {
    if (!out_reading) return -1;
    out_reading->sample_id = ++g_sample_counter;
    out_reading->temperature_mC = 25400; // 25.4 deg C
    out_reading->status_flags = TELEMETRY_MAGIC_CODE;
    return 0;
}

src/main.c:

#include <stdio.h>
#include "sensor.h"

int main(void) {
    sensor_reading_t reading = {0};
    sensor_init();
    sensor_poll(&reading);
    printf("[MAIN] Sample #%u: Temp=%d mC, Status=0x%08X
",
           reading.sample_id, reading.temperature_mC, reading.status_flags);
    return 0;
}

Step 3: Verification Commands

# 1. First build
make
# Output shows both sensor.c and main.c being compiled

# 2. Touch header file only
touch include/config.h
make
# Verified: Both sensor.o and main.o recompile because both depend on config.h!

# 3. Inspect generated dependency file
cat build/src/main.d
# Output:
# build/src/main.o: src/main.c include/sensor.h include/config.h
# include/sensor.h:
# include/config.h:

17.7 Knowledge Verification & Self-Study Quiz

Self-Assessment Check

Q1: What is the primary purpose of the GCC -MP flag when generating Make dependencies?

Explanation: Without -MP, removing an obsolete header referenced in a cached .d file causes Make to crash with No rule to make target 'deleted_header.h'.

Q2: What is the difference between = and := variable assignment in GNU Make?

Explanation: Recursively-expanded variables (=) re-evaluate their right-hand expressions (including shell commands) every time the variable is referenced, which can cause significant build slowdowns.

Q3: In Modern CMake (3.15+), if target B links to target A with target_link_libraries(B PRIVATE A), which properties does B inherit from A?

Explanation: PRIVATE linking consumes the upstream target's PUBLIC and INTERFACE requirements internally, but stops transitive forwarding to downstream dependents.

Q4: Why is CMAKE_TRY_COMPILE_TARGET_TYPE STATIC_LIBRARY critical in bare-metal CMake toolchain files?

Explanation: By default, CMake compiles and links a test executable to verify the compiler. On bare-metal targets, linking fails without a device-specific linker script and reset vector, causing CMake to abort configuration.

Q5: What automatic Make variable represents the filename of the target being built?

Explanation: $@ evaluates to the target being generated, $< evaluates to the first prerequisite (e.g. %.c), and $^ evaluates to all prerequisites.
