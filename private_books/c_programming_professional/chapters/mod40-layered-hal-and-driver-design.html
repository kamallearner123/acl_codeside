Module 40: Layered HAL & Device Driver Design

Architect maintainable, decoupled firmware systems: design clean 4-tier driver stacks, weigh vendor HAL vs LL trade-offs, author port-independent bus interfaces, and implement robust I2C bus hang recovery.

⏱️ Estimated Reading: 60 min
🎯 Standard: C99 / C11 / C17 / MISRA C:2012
🛠️ Environments: Linux POSIX + Bare-Metal ARM

40.1 Architecture of a Production Embedded Driver Stack

In professional firmware development, writing code that directly writes register addresses inside business logic creates unmaintainable, brittle software. If the hardware team switches from an SPI sensor to an I2C sensor, or upgrades the MCU from an STM32F4 to an NXP i.MX RT, tightly coupled code must be rewritten from scratch.

A production-grade firmware architecture partitions software into four strict hierarchical layers, each communicating only with the layers immediately above and below it:

The 4-Layer Embedded Architectural Hierarchy


 +-------------------------------------------------------------------------+
 | Layer 4: APPLICATION & BUSINESS LOGIC                                   |
 | (PID Motor Control, Telemetry Filtering, FSMs, Cloud Sync)              |
 +-------------------------------------------------------------------------+
                                    |
                                    v (Opaque Handles, Abstract Structs)
 +-------------------------------------------------------------------------+
 | Layer 3: MIDDLEWARE & EXTERNAL DEVICE DRIVERS                            |
 | (EEPROM Driver, IMU Filter, Display Engine, Modbus Protocol Stack)      |
 +-------------------------------------------------------------------------+
                                    |
                                    v (Standardized HAL Bus Interfaces: i2c_bus_t, spi_bus_t)
 +-------------------------------------------------------------------------+
 | Layer 2: HARDWARE ABSTRACTION LAYER (HAL) & BUS ABSTRACTION             |
 | (Generic read/write bursts, pin toggling, clock trees, DMA management)  |
 +-------------------------------------------------------------------------+
                                    |
                                    v (MMIO Register Pointers, Bitmasks)
 +-------------------------------------------------------------------------+
 | Layer 1: LOW-LAYER (LL) SILICON REGISTERS                               |
 | (Memory-Mapped I/O Registers: USART1->CR1, TIM2->CCR1, NVIC->ISER)      |
 +-------------------------------------------------------------------------+

40.2 Vendor HALs vs. Bare-Metal Low-Layer (LL) Drivers

Silicon vendors supply official libraries (e.g. STMicroelectronics STM32Cube HAL, NXP MCUXpresso, Microchip Harmony). While vendor HALs accelerate initial prototyping, they present severe architectural liabilities in safety-critical, high-throughput systems:

Architectural Dimension Vendor HAL (e.g. ST HAL) Low-Layer (LL) / Custom Register HAL
Code Footprint (Flash) Heavy (15 KB to 45 KB overhead due to defensive state structs, unused feature checks) Minimal (1 KB to 3 KB; directly inlined machine instructions)
Execution Latency High & Non-deterministic (deep function nesting, parameter pointer dereferencing) Single-cycle deterministic MMIO writes
Blocking Traps Contains busy-wait loops with timeout counters (HAL_GetTick()) that deadlock if SysTick is preempted Strictly non-blocking interrupt/DMA event-driven
MISRA C Compliance Often violates MISRA C:2012 due to macro type punning and implicit conversions Fully certifiable to 100% MISRA C:2012 rules

40.3 Writing Port-Independent Bus Interfaces (Contract Decoupling)

To make a device driver (e.g. an external EEPROM or IMU) completely independent of the MCU, define an abstract bus contract using a C struct of function pointers:

Ci2c_interface.h
#ifndef I2C_INTERFACE_H
#define I2C_INTERFACE_H

#include <stdint.h>
#include <stdbool.h>
#include <stddef.h>

/* Abstract I2C Bus Driver Operations Contract */
typedef struct i2c_bus_ops {
    bool (*write_burst)(void *user_ctx, uint8_t dev_addr, uint8_t reg_addr, const uint8_t *data, size_t len);
    bool (*read_burst)(void *user_ctx, uint8_t dev_addr, uint8_t reg_addr, uint8_t *out_data, size_t len);
} i2c_bus_ops_t;

/* Concrete I2C Bus Instance */
typedef struct {
    const i2c_bus_ops_t *ops;
    void                *user_ctx; /* Pointer to hardware peripheral instance (e.g. I2C1) */
} i2c_bus_t;

#endif /* I2C_INTERFACE_H */

40.4 Real-Time Industrial Case: EEPROM Memory Driver Decoupled from Physical Bus

By consuming the abstract i2c_bus_t interface, the EEPROM memory driver can run on an STM32, an ESP32, an RTOS queue, or inside a host PC unit test with a mock bus!

Cat24c_eeprom.c
#include "i2c_interface.h"

typedef struct {
    i2c_bus_t bus;
    uint8_t   device_i2c_addr;
} at24c_eeprom_t;

bool at24c_read_byte(at24c_eeprom_t *eeprom, uint16_t mem_addr, uint8_t *out_val) {
    if (eeprom == NULL || out_val == NULL || eeprom->bus.ops == NULL) {
        return false;
    }
    /* Address transmission: 8-bit or 16-bit word address */
    return eeprom->bus.ops->read_burst(eeprom->bus.user_ctx,
                                      eeprom->device_i2c_addr,
                                      (uint8_t)mem_addr,
                                      out_val, 1U);
}

40.5 Bus Fault Recovery: Resolving I2C SDA Bus Hangs

In noisy industrial environments, an electrical glitch or reset can interrupt an I2C transaction while a slave device is asserting a 0 (pulling SDA low). Because SDA is held low by the slave, the master cannot generate a START or STOP condition, completely locking up the peripheral!

A production HAL driver includes a Bus Clear Routine: it reconfigures the SCL pin to GPIO Open-Drain and clocks out up to 9 dummy pulses until the slave releases SDA, followed by a valid STOP condition:

Ci2c_bus_recovery.c
void i2c_recover_bus_hang(void) {
    /* 1. Reconfigure SCL & SDA as GPIO Open-Drain Output */
    gpio_set_mode_open_drain(I2C_SCL_PIN);
    gpio_set_mode_open_drain(I2C_SDA_PIN);

    /* 2. Clock out up to 9 pulses to release slave holding SDA low */
    for (int i = 0; i < 9; ++i) {
        if (gpio_read_pin(I2C_SDA_PIN) != 0) {
            break; /* Slave has released SDA! */
        }
        gpio_write_pin(I2C_SCL_PIN, 0);
        delay_microseconds(5);
        gpio_write_pin(I2C_SCL_PIN, 1);
        delay_microseconds(5);
    }

    /* 3. Generate STOP condition */
    gpio_write_pin(I2C_SDA_PIN, 0);
    delay_microseconds(5);
    gpio_write_pin(I2C_SCL_PIN, 1);
    delay_microseconds(5);
    gpio_write_pin(I2C_SDA_PIN, 1);

    /* 4. Restore I2C alternate function hardware mapping */
    reinit_i2c_hardware();
}

40.6 Hands-On Lab: Modular HAL Driver Simulator

Lab Exercise: The Decoupled Sensor HAL Harness

In this lab, you will compile and run a complete modular HAL harness (`sensor_hal_lab.c`) verifying that an ambient temperature sensor driver executes without any hardware dependency by injecting a software mock bus.

Csensor_hal_lab.c
#include <stdio.h>
#include <stdlib.h>
#include <stdint.h>
#include <stdbool.h>

/* Abstract Bus Ops */
typedef struct {
    bool (*read_reg)(uint8_t dev_id, uint8_t reg, uint16_t *out_val);
} mock_bus_ops_t;

/* Mock Bus Implementation */
static bool mock_i2c_read(uint8_t dev_id, uint8_t reg, uint16_t *out_val) {
    if (dev_id != 0x48) return false; /* LM75 Temperature Sensor Address */
    if (reg == 0x00) {
        *out_val = 0x1900; /* Simulated 25.0 C (0x19 = 25) */
        return true;
    }
    return false;
}

int main(void) {
    printf("========================================================\n");
    printf("           MODULAR HAL SENSOR DRIVER LAB                \n");
    printf("========================================================\n\n");

    mock_bus_ops_t bus = { .read_reg = mock_i2c_read };
    uint16_t raw_temp = 0;
    
    if (bus.read_reg(0x48, 0x00, &raw_temp)) {
        float temp_c = (float)(raw_temp >> 8);
        printf("Sensor Read Successful! Temperature: %.2f C\n", temp_c);
    } else {
        printf("Sensor Read Failed!\n");
    }

    printf("\n========================================================\n");
    printf("HAL Verification completed with zero defects.\n");
    return EXIT_SUCCESS;
}

40.7 Knowledge Verification & Self-Study Quiz

Self-Assessment Check

Q1: What is the primary software engineering defect of directly manipulating peripheral registers inside application business logic?

Explanation: Abstracting hardware through HAL interfaces allows unit tests to run with mock drivers on PC development hosts without target hardware.

Q2: How does an I2C bus recovery sequence clear an SDA line held low by an interrupted slave device?

Explanation: Sending up to 9 clock pulses on SCL allows the slave to finish outputting its current byte, releasing the open-drain SDA pull-down.
