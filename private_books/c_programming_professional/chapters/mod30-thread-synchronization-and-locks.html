Module 30: Thread Synchronization & Locks

Deep dive into Linux synchronization primitives: futex(2) mechanics, mutex types (normal, recursive, error-checking), condition variables and the lost wakeup problem, read-write locks (pthread_rwlock_t), deadlock prevention hierarchies, and priority inheritance (PTHREAD_PRIO_INHERIT).

⏱️ Duration: 60m
🎯 Standard: POSIX.1c / Linux futex(2) / ISO 26262
⚡ Target: High-Reliability Concurrent Systems

30.1 Fast Userspace Mutexes: Linux futex(2) Internals

In early Unix kernels, every mutex lock/unlock required an expensive system call into the kernel (costing hundreds of CPU cycles for context switching).

Modern Linux synchronization relies on futex (Fast Userspace Mutex):

  • Uncontended Case (99% of time): An atomic Compare-And-Swap (CAS) instruction updates a 32-bit integer in user space memory. Zero system calls! Execution takes ~10 nanoseconds!
  • Contended Case (Collision): Only when a thread discovers the lock is already held does it invoke futex(FUTEX_WAIT) to put itself to sleep in a kernel wait-queue. Upon release, the holder calls futex(FUTEX_WAKE).

30.2 Condition Variables & The Lost Wakeup Bug

A condition variable (pthread_cond_t) allows a thread to sleep until a specific application condition becomes true.

The Spurious Wakeup Hazard: In POSIX, pthread_cond_wait() may wake up even if NO thread signaled the condition (due to kernel signal interrupts or multi-processor races). Therefore, you must NEVER use an if statement with condition variables! Always use a while loop! 
/* FATAL BUG: Using 'if' can lead to processing empty queue */
if (queue_is_empty()) {
    pthread_cond_wait(&cond, &mutex); /* May wake up spuriously! */
}
item = dequeue(); /* CRASH! Queue might still be empty! */

/* PRODUCTION PATTERN: Mandatory 'while' loop */
while (queue_is_empty()) {
    pthread_cond_wait(&cond, &mutex); /* Re-checks condition upon waking! */
}
item = dequeue(); /* Guaranteed safe! */

30.3 Deadlock Prevention & Coffman's Conditions

A deadlock occurs when two or more threads are permanently blocked waiting for resources held by each other. A deadlock requires four simultaneous conditions (Coffman Conditions):

  1. Mutual Exclusion: Exclusive resource locking.
  2. Hold and Wait: Holding lock A while requesting lock B.
  3. No Preemption: Locks cannot be forcibly confiscated.
  4. Circular Wait: Thread 1 holds A and wants B; Thread 2 holds B and wants A.

The Universal Solution: Strict Lock Ordering Hierarchy. Assign every mutex in your system a strict integer rank. Never acquire a lock with rank N while already holding a lock with rank ≥ N.

30.4 Priority Inversion & Priority Inheritance Mutexes

Priority Inversion occurs when a low-priority thread holds a lock needed by a high-priority real-time thread, but a medium-priority thread preempts the low-priority thread, effectively starving the high-priority thread!

The Solution: Priority Inheritance (PTHREAD_PRIO_INHERIT). When a high-priority thread blocks on a lock held by a low-priority thread, the kernel dynamically boosts the low-priority thread's priority to match the blocked thread until the lock is released. 

pthread_mutexattr_t attr;
pthread_mutexattr_init(&attr);
pthread_mutexattr_setprotocol(&attr, PTHREAD_PRIO_INHERIT);
pthread_mutex_init(&rt_mutex, &attr);

30.5 Industrial Case Study: The Mars Pathfinder Priority Inversion

The 1997 Mars Rover Watchdog Reset Incident

Days after landing on Mars, the Mars Pathfinder spacecraft began experiencing repeated total system resets. The watchdog timer triggered an emergency reboot, threatening the mission.

Root Cause: Three tasks competed on the real-time kernel:

  • High-Priority Task: Attitude control & bus communication (ran periodically).
  • Medium-Priority Task: Long-running communications task (no shared lock).
  • Low-Priority Task: Meteorological data gathering (infrequently acquired shared Information Bus mutex).

The low-priority task acquired the bus mutex. The high-priority task woke up, requested the bus mutex, and blocked. Before the low-priority task could release the lock, the medium-priority task woke up and preempted it!

The high-priority task was starved of CPU time for seconds. The watchdog timer assumed the system was hung and executed a hard reset!

The Fix: JPL engineers remotely uploaded a C patch enabling Priority Inheritance on the Information Bus mutex, permanently resolving the issue.

30.6 Hands-On Lab: Bounded Thread-Safe Blocking Queue in C

In this lab, you will write a complete, bounded blocking queue in C that synchronizes producer and consumer threads using a mutex and two condition variables (not_full and not_empty).

Blocking Queue Implementation (blocking_queue.c)

#include <stdio.h>
#include <stdlib.h>
#include <pthread.h>
#include <unistd.h>

#define QUEUE_CAPACITY 4

typedef struct {
    int data[QUEUE_CAPACITY];
    int head;
    int tail;
    int count;
    pthread_mutex_t lock;
    pthread_cond_t not_empty;
    pthread_cond_t not_full;
} blocking_queue_t;

void bq_init(blocking_queue_t *q) {
    q->head = 0; q->tail = 0; q->count = 0;
    pthread_mutex_init(&q->lock, NULL);
    pthread_cond_init(&q->not_empty, NULL);
    pthread_cond_init(&q->not_full, NULL);
}

void bq_push(blocking_queue_t *q, int value) {
    pthread_mutex_lock(&q->lock);
    while (q->count == QUEUE_CAPACITY) {
        pthread_cond_wait(&q->not_full, &q->lock);
    }
    q->data[q->head] = value;
    q->head = (q->head + 1) % QUEUE_CAPACITY;
    q->count++;
    pthread_cond_signal(&q->not_empty);
    pthread_mutex_unlock(&q->lock);
}

int bq_pop(blocking_queue_t *q) {
    pthread_mutex_lock(&q->lock);
    while (q->count == 0) {
        pthread_cond_wait(&q->not_empty, &q->lock);
    }
    int val = q->data[q->tail];
    q->tail = (q->tail + 1) % QUEUE_CAPACITY;
    q->count--;
    pthread_cond_signal(&q->not_full);
    pthread_mutex_unlock(&q->lock);
    return val;
}

static blocking_queue_t g_q;

void *producer(void *arg) {
    for (int i = 1; i <= 10; i++) {
        bq_push(&g_q, i * 10);
        printf("[PRODUCER] Pushed: %d
", i * 10);
        usleep(50000);
    }
    return NULL;
}

void *consumer(void *arg) {
    for (int i = 1; i <= 10; i++) {
        int v = bq_pop(&g_q);
        printf("  [CONSUMER] Popped: %d
", v);
        usleep(100000);
    }
    return NULL;
}

int main(void) {
    bq_init(&g_q);
    pthread_t p, c;
    pthread_create(&p, NULL, producer, NULL);
    pthread_create(&c, NULL, consumer, NULL);
    pthread_join(p, NULL);
    pthread_join(c, NULL);
    printf("Bounded blocking queue test finished successfully!
");
    return 0;
}

27.7 Knowledge Verification & Self-Study Quiz

Self-Assessment Check

Q1: Why must pthread_cond_wait() always be enclosed within a while loop instead of an if statement?

Explanation: Spurious wakeups occur due to signal delivery or kernel scheduling; re-evaluating the boolean condition inside a while loop guarantees safety before proceeding.

Q2: What is the primary performance benefit of a futex-based mutex over a traditional kernel semaphore in Linux?

Explanation: Futexes avoid entering the kernel unless there is genuine contention between multiple threads, speeding up uncontended execution by orders of magnitude.

Q3: How does Priority Inheritance resolve the priority inversion phenomenon?

Explanation: Temporarily raising the holder's priority prevents intermediate medium-priority threads from preempting it, allowing it to release the lock rapidly.

Q4: What happens if a thread attempts to lock a normal PTHREAD_MUTEX_NORMAL mutex that it already holds?

Explanation: Normal mutexes do not detect re-locking by the same thread; self-deadlock occurs unless configured as PTHREAD_MUTEX_RECURSIVE or ERRORCHECK.

Q5: What is the primary advantage of a Read-Write Lock (pthread_rwlock_t) over a standard Mutex?

Explanation: RW-locks maximize read scalability for data structures that are frequently read but infrequently modified.
