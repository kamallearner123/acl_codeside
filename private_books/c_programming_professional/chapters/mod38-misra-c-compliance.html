Module 38: MISRA C:2012 & MISRA C:2023 Compliance

Master safety-critical C standards mandated across automotive (ISO 26262), aerospace (DO-178C), and medical devices (IEC 62304). Deep dive into MISRA rule classifications (Mandatory, Required, Advisory), essential type models, pointer conversion restrictions, dynamic allocation bans, and formal deviation permits.

⏱️ Duration: 60m
🎯 Standard: MISRA C:2012 (AMD 1-3) / MISRA C:2023
⚡ Target: ISO 26262 ASIL-D & DO-178C Level A Systems

38.1 Why MISRA C is Mandatory in High-Reliability Systems

The ISO C standard is renowned for its expressive power and runtime performance. However, ISO C contains hundreds of undefined, unspecified, and implementation-defined behaviors (such as integer promotion traps, signed overflow, and unsequenced side-effects).

The Motor Industry Software Reliability Association (MISRA) established MISRA C to define a disciplined, mathematically verifiable subset of C that eliminates dangerous language ambiguities without sacrificing low-level hardware control.

MISRA Rule Categorization Hierarchy
1. Mandatory Rules:
   Zero tolerance. Cannot be deviated under any circumstances!
   Example: Rule 9.1 (Uninitialized variables), Rule 22.1 (Freeing reserved memory).

2. Required Rules:
   Must be obeyed unless a formal, documented Engineering Deviation Permit is approved.
   Example: Rule 11.4 (Pointer to integer casting for MMIO registers).

3. Advisory Rules:
   Best-practice engineering recommendations; deviations do not require formal customer sign-off.
   Example: Rule 16.4 (Every switch statement should have a default clause).

38.2 Core Safety Rules in MISRA C:2012

1. Rule 17.7 (Required): Non-Void Return Values Must Be Tested

Every non-void function return value must be checked. If deliberately ignored, it must be explicitly cast to (void): 

/* VIOLATION */
memcpy(dest, src, 16);

/* COMPLIANT */
(void)memcpy(dest, src, 16);

2. Rule 21.3 (Required): Banning Dynamic Memory Allocation

Functions malloc(), calloc(), realloc(), and free() are strictly prohibited after system initialization. Heap fragmentation, unbounded allocation latency, and out-of-memory states cannot be tolerated in hard real-time controllers. All buffers must be statically allocated.

3. Rule 14.4 (Required): Boolean Expressions in Control Flow

The controlling expression of an if, while, or for statement must have explicit boolean type: 

/* VIOLATION: Using integer as boolean */
if (ptr) { ... }
if (count) { ... }

/* COMPLIANT */
if (ptr != NULL) { ... }
if (count > 0U) { ... }

4. Rule 10.4 (Required): Essential Type Model

Both operands of a binary operator must belong to the exact same Essential Type Category: 

uint8_t a = 5U;
uint16_t b = 100U;
/* VIOLATION: Mismatched unsigned types */
uint16_t c = a + b;

/* COMPLIANT: Explicit cast to identical type */
uint16_t c = (uint16_t)a + b;

38.3 Writing Formal Deviation Permits for MMIO

In bare-metal embedded systems, hardware registers exist at physical addresses. Casting an integer literal like 0x40020000UL to a pointer violates Rule 11.4 (conversion between integer and pointer).

To write valid firmware, engineers document a formal MISRA Deviation Record (MDR): 

/*
 * DEVIATION PERMIT: MDR-GPIO-001
 * MISRA Rule: 11.4 (A conversion should not be performed between a pointer to object and an integer)
 * Justification: Hardware peripheral registers on STM32F4 are memory-mapped to fixed physical addresses.
 * Safety Case: Register definitions are verified against the STM32F4 Reference Manual and tested in HIL.
 */
#define GPIOA ((GPIO_TypeDef *)0x40020000UL) /* Deviation Permitted */

38.4 Industrial Case Study: The Toyota Unintended Acceleration Assessment

The NASA Software Analysis of Electronic Throttle Control

Following lawsuits alleging unintended acceleration in consumer vehicles, NASA and independent software safety experts audited the vehicle’s Electronic Throttle Control System (ETCS) C codebase.

Audit Findings: The software failed to adhere to MISRA coding guidelines:

  • Over 2,200 global variables shared across concurrent tasks with inadequate synchronization.
  • Cyclomatic complexity of key throttle angle routines exceeded 50 (safety guidelines mandate ≤ 10).
  • Ignoring function return codes for safety-critical checks.
  • Recursion and unbounded task stack depth risking silent stack overflow into global memory.

The trial resulted in a $1.2 billion settlement, cementing MISRA C compliance as a non-negotiable legal and engineering requirement across the global automotive and aerospace supply chain.

38.5 Hands-On Lab: Refactoring Non-Compliant C Code to 100% MISRA Compliance

In this lab, you will audit a buggy sensor reading function violating 5 MISRA C rules, and refactor it into clean, compliant production code.

1. Non-Compliant Code (dirty_code.c)

#include <stdio.h>

int read_voltage(int *out) {
    if (out) { // MISRA 14.4 Violation: not explicit boolean
        *out = 3300;
        return 1;
    }
    // MISRA 17.4 Violation: function does not exit through single point
}

void process(void) {
    int v;
    read_voltage(&v); // MISRA 17.7 Violation: Return value ignored
}

2. Fully Refactored MISRA C:2012 Compliant Code

#include <stdint.h>
#include <stdbool.h>

typedef enum {
    STATUS_OK = 0,
    STATUS_ERR_NULL_PARAM = 1
} status_code_t;

status_code_t read_voltage(int32_t * const out_milli_volts) {
    status_code_t status = STATUS_ERR_NULL_PARAM;

    if (out_milli_volts != (void *)0) {
        *out_milli_volts = 3300;
        status = STATUS_OK;
    }

    return status; /* Single exit point */
}

void process(void) {
    int32_t voltage_mV = 0;
    status_code_t result = read_voltage(&voltage_mV);
    if (result != STATUS_OK) {
        /* Handled error status defensively */
        voltage_mV = 0;
    }
}

38.6 Knowledge Verification & Self-Study Quiz

Self-Assessment Check

Q1: Under MISRA C:2012, which classification of rule can NEVER be deviated under any circumstances?

Explanation: Mandatory rules permit zero deviations; any codebase violating a Mandatory rule fails compliance automatically.

Q2: Why does MISRA C Rule 21.3 prohibit dynamic memory allocation (malloc/free) in safety-critical systems?

Explanation: Heap allocation is non-deterministic and can fail unpredictably at runtime; deterministic safety requires static memory sizing.

Q3: How must a function call be structured under MISRA Rule 17.7 if its return value is intentionally ignored?

Explanation: Explicitly casting to (void) documents to reviewers and static analyzers that discarding the return value was deliberate.

Q4: Under MISRA Rule 14.4, is if (status) legal if status is an int?

Explanation: MISRA mandates that control expressions evaluate an essentially boolean expression to prevent subtle logical errors.

Q5: What document justifies an intentional deviation from a Required MISRA rule in safety-critical projects?

Explanation: Required rules can be deviated only with formal, signed engineering documentation detailing why the deviation is necessary and why it is safe.
