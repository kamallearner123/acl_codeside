Module 19: Dynamic Analysis & Compiler Sanitizers

Master runtime verification of memory safety, undefined behavior, and concurrency hazards using Valgrind Memcheck, AddressSanitizer (ASan), UndefinedBehaviorSanitizer (UBSan), and ThreadSanitizer (TSan). Understand shadow memory mechanics, redzone insertion, and production triage workflows.

⏱️ Duration: 55m
🎯 Standard: C11 / POSIX / LLVM Compiler-RT
⚡ Target: Linux x86_64 / ARM AArch64 / QEMU

19.1 Dynamic Binary Translation vs. Compiler Instrumentation

Detecting memory corruption, invalid pointer dereferences, and thread race conditions at runtime historically required two distinct engineering philosophies:

Dynamic Verification Approaches Compared
1. Dynamic Binary Translation (Valgrind):
   Unmodified ELF Binary ──▶ [ Valgrind JIT Core ] ──▶ Instruments machine instructions in RAM
                                                      └── Shadow Memory tracking (V-bits & A-bits)
   Overhead: ~10x to 25x execution slowdown; high memory penalty (2x-4x RAM).

2. Compile-Time Instrumentation (Compiler Sanitizers - ASan, UBSan, TSan):
   Source Code (.c) ──▶ [ GCC / Clang -fsanitize=... ] ──▶ Instrumented ELF Binary
                                                           ├── Injects Redzones around buffers
                                                           └── Direct Shadow Memory Lookups
   Overhead: ~1.5x to 2x execution slowdown; minimal runtime penalty.
Capability / Defect Type Valgrind Memcheck AddressSanitizer (ASan) UBSan
Heap Buffer Overflow Yes Yes (Instant SIGSEGV) No
Stack Buffer Overflow No (Cannot see stack layout) Yes (Inserts stack redzones) No
Global / Static Buffer Overflow No Yes (Pads .bss/.data) No
Heap Use-After-Free Yes Yes (Quarantine pool) No
Uninitialized Memory Read Yes (V-bit tracking) Requires MSan (MemorySanitizer) No
Signed Integer Overflow / UB No No Yes

19.2 AddressSanitizer (ASan) Internals & Shadow Memory

AddressSanitizer achieves unprecedented performance through an ingenious mathematical abstraction: Shadow Memory.

In a 64-bit architecture, every 8 bytes of application virtual memory are mapped to exactly 1 byte of shadow memory. The shadow byte encodes the accessibility of those 8 bytes:

  • 0x00: All 8 bytes are valid and unpoisoned.
  • 0x01 .. 0x07: The first k bytes are addressable; the remaining bytes are poisoned redzones.
  • Negative / Special values (e.g., 0xFA, 0xFB, 0xFD): The entire 8-byte chunk is poisoned (Heap redzone, Stack redzone, Freed heap quarantine).

Mathematical Translation Formula

Given any 64-bit application memory address Addr, the corresponding shadow memory byte is located in O(1) time via a fast bit-shift and constant offset addition: 

char *shadow_byte = (char *)((Addr >> 3) + 0x7fff8000);

Compiler Instrumentation Example

When you write an ordinary memory write in C:

*address = 0xAA;

Under -fsanitize=address, GCC/Clang transforms the instruction into:

char *shadow = (char *)(((uintptr_t)address >> 3) + 0x7fff8000);
if (*shadow != 0) {
    if (((uintptr_t)address & 7) >= *shadow) {
        __asan_report_store1(address); /* Traps immediately with backtrace! */
    }
}
*address = 0xAA;

19.3 UndefinedBehaviorSanitizer (UBSan)

C allows undefined behavior (UB) for maximum compiler optimization liberty. When UB occurs, modern compilers (GCC/Clang) assume the path is dead code, often silently omitting safety checks. UBSan instruments the binary to abort or log errors when UB occurs.

Critical Flaws Caught by UBSan (-fsanitize=undefined)

  1. Signed Integer Overflow: Exceeding INT_MAX is undefined in ISO C §6.5.6.
  2. Misaligned Pointer Access: Dereferencing a uint32_t * on an odd byte address (e.g. 0x20000003) triggers bus faults on ARM Cortex-M0/M3/M4.
  3. Shift Out-of-Bounds: Shifting a 32-bit integer by ≥ 32 bits (e.g., 1U << 32).
  4. NULL Pointer Arithmetic: Computing NULL + offset even if not dereferenced.
  5. Type Punning Violations: Violating the strict aliasing rule (ISO C §6.5).

19.4 ThreadSanitizer (TSan) & Concurrency Data Races

A Data Race occurs whenever two threads concurrently access the same shared memory location, at least one of the accesses is a write, and the threads do not use any synchronization (mutexes, atomics, or memory barriers).

ThreadSanitizer (-fsanitize=thread) tracks the happens-before partial order using vector clocks. When TSan detects two conflicting accesses unsynchronized by synchronization primitives, it prints a complete diagnostic listing both threads, their allocation call stacks, and the exact source code lines.

19.5 Valgrind Memcheck & Massif in Production

While ASan is superior for catching buffer overflows in developer builds, Valgrind Memcheck remains indispensable because:

  • It requires zero recompilation (can run on vendor pre-compiled binaries).
  • It detects uninitialized memory reads (passing uninitialized struct padding to network sockets).
  • Valgrind Massif generates visual heap allocation profiles over time, identifying insidious memory leaks that evade simple threshold checks.

19.6 Industrial Case Study: The Heartbleed Vulnerability (CVE-2014-0160)

The OpenSSL Heartbleed Buffer Over-Read Catastrophe

In April 2014, the Heartbleed bug in OpenSSL exposed millions of private encryption keys, passwords, and sessions worldwide. The flaw resided in the TLS Heartbeat extension.

The Defect: The client sends a payload length field (a 16-bit integer up to 65,535 bytes) along with a small 1-byte payload. The server allocated an output buffer and copied the specified length without validating whether the actual received packet contained that many bytes: 

/* Faulty OpenSSL Code */
unsigned int payload = 0;
n2s(p, payload); /* Extracts length from client header (e.g. 64 KB) */
/* ... */
unsigned char *buffer = malloc(1 + 2 + payload + padding);
memcpy(bp, pl, payload); /* pl was only 1 byte! Over-reads 64 KB of heap! */

The server dutifully copied 64 KB of adjacent heap memory—which contained private RSA keys and user credentials—and transmitted it back to the client!

Why Standard Tests Missed It: Reading beyond a heap buffer boundary does not cause a crash unless it hits an unmapped virtual memory page.

How ASan Instantly Prevents It: Because ASan surrounds every heap allocation with poisoned redzones, memcpy reading into the poisoned shadow memory triggers an immediate, unmaskable ASan abort:

==4210==ERROR: AddressSanitizer: heap-buffer-overflow on address 0x602000000041
READ of size 65535 at 0x602000000041 thread T0
    #0 0x7f4b82 in memcpy /usr/include/bits/string3.h:51
    #1 0x7f4b82 in tls1_process_heartbeat ssl/t1_lib.c:2586
=================================================================

19.7 Hands-On Lab: Diagnosing 4 Memory Safety Defects with ASan & UBSan

In this lab, you will compile a diagnostic test suite containing 4 subtle, real-world C bugs. You will use GCC sanitizers to catch all 4 bugs without stepping through a single line in a debugger.

Test Harness (lab_sanitizer.c)

#include <stdio.h>
#include <stdlib.h>
#include <string.h>
#include <limits.h>

static void bug1_heap_uaf(void) {
    char *buf = (char *)malloc(32);
    strcpy(buf, "Safety-Critical");
    free(buf);
    printf("[BUG 1] Read after free: %c
", buf[0]); /* Use-After-Free! */
}

static void bug2_stack_overflow(void) {
    int arr[4] = {10, 20, 30, 40};
    int val = arr[5]; /* Stack Buffer Overflow! */
    printf("[BUG 2] Out of bounds: %d
", val);
}

static void bug3_signed_overflow(void) {
    int max = INT_MAX;
    int result = max + 1; /* Undefined Behavior: Signed Overflow! */
    printf("[BUG 3] Overflow result: %d
", result);
}

static void bug4_unaligned_access(void) {
    char raw_bytes[8] = {1, 2, 3, 4, 5, 6, 7, 8};
    /* Misaligned 32-bit pointer on odd byte boundary */
    int *unaligned_ptr = (int *)&raw_bytes[1];
    printf("[BUG 4] Misaligned value: 0x%08X
", *unaligned_ptr);
}

int main(int argc, char **argv) {
    if (argc < 2) {
        printf("Usage: %s <1|2|3|4>
", argv[0]);
        return 1;
    }
    int choice = atoi(argv[1]);
    switch (choice) {
        case 1: bug1_heap_uaf(); break;
        case 2: bug2_stack_overflow(); break;
        case 3: bug3_signed_overflow(); break;
        case 4: bug4_unaligned_access(); break;
        default: printf("Invalid choice
"); break;
    }
    return 0;
}

Build & Test Commands

# Compile with AddressSanitizer and UndefinedBehaviorSanitizer
gcc -O1 -g -fsanitize=address,undefined -fno-omit-frame-pointer lab_sanitizer.c -o lab_sanitizer

# Test Bug 1: Heap Use-After-Free
./lab_sanitizer 1
# ASan reports: heap-use-after-free on address 0x... freed by thread T0 here: ...

# Test Bug 2: Stack Buffer Overflow
./lab_sanitizer 2
# ASan reports: stack-buffer-overflow on address 0x... in bug2_stack_overflow

# Test Bug 3: Signed Integer Overflow
./lab_sanitizer 3
# UBSan reports: signed integer overflow: 2147483647 + 1 cannot be represented in type 'int'

# Test Bug 4: Misaligned Access
./lab_sanitizer 4
# UBSan reports: load of misaligned address 0x... for type 'int', which requires 4 byte alignment

19.8 Knowledge Verification & Self-Study Quiz

Self-Assessment Check

Q1: Why is AddressSanitizer (ASan) capable of detecting stack buffer overflows while Valgrind Memcheck cannot?

Explanation: Valgrind operates on unmodified binaries and only monitors heap allocation hooks (malloc/free) and system call buffers. It cannot differentiate between adjacent variables inside an allocated stack frame.

Q2: What is the shadow memory scale factor utilized by AddressSanitizer on 64-bit platforms?

Explanation: ASan maps 8 bytes of virtual memory to 1 shadow byte, resulting in a compact shadow memory layout representing exactly 1/8th of the address space.

Q3: Which sanitizer should be deployed to detect multithreaded data races on shared memory without locks?

Explanation: ThreadSanitizer (TSan) instruments memory reads and writes with vector clocks to identify conflicting, unsynchronized accesses between concurrent threads.

Q4: What happens when signed integer overflow occurs in a binary compiled with -fsanitize=undefined?

Explanation: UBSan inserts checks prior to arithmetic operations and intercepts undefined behavior before the CPU or compiler can trigger erroneous execution paths.

Q5: Can AddressSanitizer and ThreadSanitizer be enabled simultaneously in the same GCC build invocation?

Explanation: ASan and TSan cannot be linked into the same executable; developers must execute separate test runs for memory errors (ASan) and concurrency races (TSan).
