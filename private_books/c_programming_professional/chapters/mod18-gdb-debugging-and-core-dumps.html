Module 18: GDB Debugging & Core Dump Analysis

Deep dive into debugger architecture, the Linux ptrace system call, ARM Remote Serial Protocol (RSP) hardware debugging, hardware watchpoints vs software breakpoints, post-mortem Linux core dump analysis, and automated GDB Python scripting.

⏱️ Duration: 65m
🎯 Standard: POSIX ptrace / GDB RSP / DWARF 4 & 5
⚡ Target: Linux x86_64 / ARM Cortex-M (OpenOCD/JTAG)

18.1 Debugger Architecture: ptrace & Remote Serial Protocol

To master debugging, an engineer must understand how the debugger manipulates the target program. On Linux, GDB relies on the ptrace(2) system call. On bare-metal microcontrollers (ARM Cortex-M), GDB communicates across a TCP socket or UART with a debug agent (OpenOCD, J-Link, or pyOCD) using the GDB Remote Serial Protocol (RSP).

Debugger Architectural Paradigms
1. Linux Host Debugging (ptrace):
   [ GDB User Process ] ──ptrace(PTRACE_PEEKTEXT/POKEDATA, pid)──▶ [ Linux Kernel ]
                                                                          │
                                                                   Controls CPU context
                                                                          ▼
                                                                [ Target Process (SIGTRAP) ]

2. Embedded Bare-Metal Remote Debugging (RSP):
   [ arm-none-eabi-gdb ] ──TCP Port 3333 ($vCont?#49)──▶ [ OpenOCD / GDB Server ]
                                                                  │
                                                           SWD / JTAG Bus
                                                                  ▼
                                                      [ ARM Cortex-M Core (DWT/FPB) ]

Linux ptrace Mechanics

When GDB attaches to a target process via ptrace(PTRACE_ATTACH, pid, ...), the kernel suspends the target thread and delivers a SIGSTOP signal. GDB then reads or writes target memory using PTRACE_PEEKDATA and PTRACE_POKEDATA, and inspects or alters CPU register state using PTRACE_GETREGS and PTRACE_SETREGS.

ARM GDB Remote Serial Protocol (RSP)

In embedded systems, the target hardware cannot run a full Linux kernel. Instead, a host-side GDB server (such as OpenOCD) translates GDB's ASCII packets into low-level Serial Wire Debug (SWD) or JTAG register access commands:

  • $g#67: Read all general-purpose registers (R0-R15, xPSR).
  • $m20000000,4#XX: Read 4 bytes from SRAM address 0x20000000.
  • $Z0,08000100,2#XX: Insert a software breakpoint at flash address 0x08000100.

18.2 Hardware Watchpoints vs. Software Breakpoints

One of the most critical low-level distinctions is the difference between a Software Breakpoint and a Hardware Breakpoint / Watchpoint.

Feature Software Breakpoint (break) Hardware Breakpoint (hbreak) Hardware Watchpoint (watch)
Mechanism Replaces instruction opcode with a trap instruction: INT 3 (0xCC) on x86, BKPT (0xBE00) on ARM. Configures silicon comparator registers (ARM FPB: Flash Patch & Breakpoint unit). Configures silicon memory comparators (ARM DWT: Data Watchpoint and Trace).
Flash / ROM Compatible? No (Flash cannot be overwritten without an erase cycle). Yes (Silicon unit intercepts instruction fetch address on bus). Yes (Intercepts data read/write bus transactions).
Quantity Available Virtually unlimited (in RAM). Limited by silicon (Typically 4 to 8 on Cortex-M4). Limited by silicon (Typically 2 to 4 on Cortex-M4).

Using Watchpoints to Catch Silent Memory Corruption

When an unknown bug randomly overwrites a global variable or buffer, stepping through thousands of lines of code is useless. Instead, set a hardware data watchpoint: 

(gdb) watch g_system_state.telemetry_counter
Hardware watchpoint 1: g_system_state.telemetry_counter
(gdb) continue
Continuing.

Hardware watchpoint 1: g_system_state.telemetry_counter
Old value = 14
New value = 3735928559
0x08001a42 in faulty_buffer_copy (src=0x20000100, len=128) at drivers/dma.c:45
45          dest[i] = src[i]; /* Overflow stepped on g_system_state! */

18.3 Memory Inspection, Stack Unwinding & Disassembly

Mastery of GDB requires instant fluency in reading memory and disassembly:

1. The x (Examine Memory) Command

Syntax: x / [RepeatCount] [Format] [UnitSize] [Address]
Format specifiers: x (hex), d (signed dec), u (unsigned dec), s (string), i (instruction).
Unit size: b (byte), h (halfword/16-bit), w (word/32-bit), g (giant/64-bit). 

# Dump 16 32-bit words in hex from peripheral base address
(gdb) x/16xw 0x40020000
0x40020000: 0x00000000 0x00000000 0x00000000 0x00000000
0x40020010: 0x00000000 0x00000000 0x00000000 0x00000000

18.4 Linux Core Dumps & Post-Mortem Analysis

In production Linux deployments (such as embedded gateways, robotics controllers, or telecom boxes), applications run unattended without an attached interactive debugger. When an application crashes via SIGSEGV, SIGBUS, or SIGABRT, the Linux kernel can dump the process’s complete memory address space, register state, and stack traces into an ELF file known as a Core Dump.

Enabling Core Dumps in Linux

# Set maximum core dump size to unlimited (for current shell session)
ulimit -c unlimited

# Configure kernel core dump naming pattern (PID, executable name, timestamp)
sudo sysctl -w kernel.core_pattern="/var/crash/core-%e-%p-%t"

Post-Mortem Investigation Workflow

Once a crash occurs, load the binary executable alongside the generated core dump into GDB:

18.5 GDB Automation & Python Scripting

Modern GDB includes an integrated Python 3 interpreter. Engineers can write Python scripts to inspect complex embedded data structures, automate register validation, and produce clean visualizations of circular ring buffers or RTOS task lists.

Custom Ring Buffer Visualizer in GDB Python

# save as print_ringbuf.py
import gdb

class PrintRingBuffer(gdb.Command):
    """Inspect and pretty-print an embedded circular ring buffer."""
    
    def __init__(self):
        super(PrintRingBuffer, self).__init__("print-ringbuf", gdb.COMMAND_USER)

    def invoke(self, arg, from_tty):
        val = gdb.parse_and_eval(arg)
        head = int(val['head'])
        tail = int(val['tail'])
        capacity = int(val['capacity'])
        buffer_ptr = val['buffer']
        
        count = (head - tail + capacity) % capacity
        print(f"--- RingBuffer [{arg}] ---")
        print(f" Capacity: {capacity} | Head: {head} | Tail: {tail} | Items Pending: {count}")
        
        items = []
        idx = tail
        while idx != head:
            byte_val = int(buffer_ptr[idx])
            items.append(f"0x{byte_val:02X}")
            idx = (idx + 1) % capacity
        print(" Contents: [" + ", ".join(items) + "]")

PrintRingBuffer()

Load and invoke the script directly inside GDB:

(gdb) source print_ringbuf.py
(gdb) print-ringbuf g_uart_rx_buf
--- RingBuffer [g_uart_rx_buf] ---
 Capacity: 128 | Head: 5 | Tail: 2 | Items Pending: 3
 Contents: [0x53, 0x59, 0x4E]

18.6 Industrial Case Study: Subsea Sensor Watchdog HardFault

The Deep-Sea Oceanographic Acoustic Logger Failure

An acoustic hydrophone array operating at 2,000 meters depth suffered sporadic system reboots every 18 to 36 hours. The hardware watchdog triggered an emergency reset, preventing acoustic data loss but corrupting the current flash sector.

Investigation via Embedded Crash Dump: The firmware was equipped with a custom HardFault handler that saved the CPU register frame (R0-R3, R12, LR, PC, xPSR) and Configurable Fault Status Register (CFSR) into a reserved battery-backed SRAM region.

Upon recovery, engineers dumped the fault registers: 

CFSR: 0x00008200 (BFARVALID | PRECISERR - Precise Data Bus Error)
BFAR: 0x20008004 (Bus Fault Address Register - Attempted access at 0x20008004)
PC:   0x0800318C
LR:   0x08003107

Loading the ELF file into arm-none-eabi-gdb: 

(gdb) info line *0x0800318C
Line 142 of "src/hydrophone_dma.c" starts at address 0x8003184 <dma_ping_pong_swap+16>
(gdb) disassemble 0x8003184
0x08003188 <+20>: ldr   r3, [r0, #4]
0x0800318a <+22>: ldr   r2, [r3, #0]
0x0800318c <+24>: str   r1, [r2, #4]  <-- CRASH HERE (BFAR = 0x20008004)

Root Cause: The hydrophone SRAM size was 32 KB (ending at 0x20007FFF). A DMA ping-pong buffer pointer calculation suffered an off-by-one pointer arithmetic overflow during sample rates exceeding 96 kHz, writing to 0x20008004. Because that address was unmapped physical memory, the Cortex-M bus matrix generated an immediate PRECISERR Data Bus Fault.

18.7 Hands-On Lab: Debugging a Real Segfaulting C Daemon

In this lab, you will compile a multi-threaded C program with a latent pointer corruption defect, generate a core dump, and isolate the exact faulting line using GDB.

Faulty C Code (lab_crash.c)

#include <stdio.h>
#include <stdlib.h>
#include <string.h>

typedef struct node {
    int id;
    char tag[16];
    struct node *next;
} node_t;

static node_t *create_node(int id, const char *tag) {
    node_t *n = (node_t *)malloc(sizeof(node_t));
    if (!n) return NULL;
    n->id = id;
    strncpy(n->tag, tag, sizeof(n->tag) - 1);
    n->next = NULL;
    return n;
}

static void print_list(node_t *head) {
    node_t *curr = head;
    while (curr != NULL) {
        printf("Node [%d]: %s
", curr->id, curr->tag);
        curr = curr->next; /* Will crash if curr pointer was corrupted */
    }
}

int main(void) {
    node_t *first = create_node(1, "Alpha");
    node_t *second = create_node(2, "Beta");
    first->next = second;

    /* Simulating a silent heap corruption bug */
    char *corrupter = (char *)second;
    memset(corrupter + sizeof(int) + 16, 0xAA, sizeof(void *)); /* Overwrites second->next with 0xAAAAAAAAAAAAAAAA */

    printf("Traversing list...
");
    print_list(first);

    return 0;
}

Build & Debug Script

# 1. Compile with debugging symbols (-g3) and frame pointers
gcc -O0 -g3 -fno-omit-frame-pointer lab_crash.c -o lab_crash

# 2. Enable core dumps
ulimit -c unlimited

# 3. Execute and trigger crash
./lab_crash
# Output:
# Traversing list...
# Node [1]: Alpha
# Node [2]: Beta
# Segmentation fault (core dumped)

# 4. Load core dump in GDB
gdb -q ./lab_crash core

# 5. Inside GDB:
# (gdb) bt
# #0  print_list (head=0x5555555592a0) at lab_crash.c:23
# #1  main () at lab_crash.c:37
# (gdb) print curr
# $1 = (node_t *) 0xaaaaaaaaaaaaaaaa
# (gdb) x/16xb second
# Displays exact bytes showing how second->next was overwritten with 0xAA!

18.8 Knowledge Verification & Self-Study Quiz

Self-Assessment Check

Q1: Why cannot a standard software breakpoint be set in microcontroller NOR Flash memory without special hardware assistance?

Explanation: Software breakpoints require dynamically patching the opcode at the target address. NOR flash bits cannot be toggled from 0 to 1 without a block erase operation, requiring dedicated hardware comparators (ARM Flash Patch & Breakpoint unit).

Q2: What is the purpose of setting ulimit -c unlimited in Linux?

Explanation: By default on many Linux distributions, the maximum core dump size is set to 0, which silently prevents core file creation when crashes occur.

Q3: What GDB command sequence inspects 8 contiguous 32-bit memory words in hexadecimal starting at pointer ptr?

Explanation: x/8xw specifies: examine (x), 8 elements (8), in hexadecimal format (x), of word unit size (w = 4 bytes).

Q4: What silicon block provides hardware data watchpoints on an ARM Cortex-M4 microcontroller?

Explanation: The Cortex-M DWT contains address comparator registers that continuously monitor data address bus transactions and halt the core when a match occurs.

Q5: When analyzing a multithreaded crash dump in GDB, how do you switch the execution context to thread 3?

Explanation: info threads lists all active threads, and thread <id> switches GDB's inspection context to examine that specific thread's registers and stack trace.
