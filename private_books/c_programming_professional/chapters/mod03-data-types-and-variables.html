Module 3: C Data Types, Variables & Memory Representation

Master the physical realities of memory representation in C: architecture data models (ILP32 vs. LP64), exact-width types, two's complement sign extension, the integer promotion rule trap, IEEE-754 floating-point mechanics, and endianness byte serialization in industrial telemetry protocols.

⏱️ Estimated Reading: 65 min
🎯 Standard: C99 / C11 / C17 / C23
🛠️ Environments: Linux POSIX + ARM Cortex-M

3.1 The Silicon Grid: Bits, Bytes, Words & Architecture Data Models

At the physical layer of digital computing, all data exists as electrical potentials across capacitive cells or transistor gates. When high-level C code declares a variable, the compiler allocates a discrete region of physical memory (or maps it directly into a CPU general-purpose register) governed by the CPU's memory bus width, cache line size, and word architecture.

Unlike interpreted languages or virtual-machine platforms that conceal hardware details, C exposes the naked memory grid. Consequently, understanding how primitive C data types translate into physical memory addresses is the hallmark of a systems and firmware engineer.

Architecture Data Models: LP32, ILP32, LP64 & LLP64

The ISO C standard intentionally avoids mandating exact bit-widths for standard types like short, int, and long. Instead, the standard defines only minimum guarantees:

  • sizeof(char) == 1 (guaranteed to be at least 8 bits).
  • sizeof(short) >= 2 (at least 16 bits).
  • sizeof(int) >= 2 (at least 16 bits, typically 32 bits on 32-bit and 64-bit systems).
  • sizeof(long) >= 4 (at least 32 bits).
  • sizeof(long long) >= 8 (at least 64 bits).
  • Relationship: sizeof(char) <= sizeof(short) <= sizeof(int) <= sizeof(long) <= sizeof(long long).
Data Model short int long Pointers (void*) Target Systems & Architectures
LP32 16 bits 16 bits 32 bits 32 bits Legacy 16-bit Windows 3.1, 8/16-bit Microcontrollers (AVR, 8051)
ILP32 16 bits 32 bits 32 bits 32 bits 32-bit ARM Cortex-M (M0/M3/M4/M7), 32-bit x86, Linux i386
LP64 16 bits 32 bits 64 bits 64 bits Modern 64-bit Linux (x86_64, AArch64), macOS, BSD
LLP64 16 bits 32 bits 32 bits 64 bits 64-bit Microsoft Windows (Win64 API)

⚠️ The Fatal Portability Trap: Assuming sizeof(long) == sizeof(void*)

On a 64-bit Linux server (LP64), sizeof(long) == 8 and sizeof(void*) == 8. Casting a pointer to unsigned long succeeds without truncation. However, on 64-bit Windows (LLP64) or when cross-compiling to a 32-bit Cortex-M target (ILP32), sizeof(long) is only 32 bits! Casting a 64-bit pointer to long on Windows truncates the upper 32 bits of the address, causing catastrophic memory corruption and segmentation faults. Always use uintptr_t when treating pointers as integers.

3.2 Exact-Width Integer Types (<stdint.h> & <inttypes.h>)

Because primitive types vary across architectures, safety-critical embedded standards (e.g., MISRA C:2012 Rule 8.4) prohibit the naked use of short, int, and long in production code. ISO C99 introduced <stdint.h>, formalizing exact-width types that guarantee bit-level determinism across all platforms.

1. Exact-Width Types

Guaranteed to have exactly $N$ bits with two's complement representation and no padding bits:

  • int8_t / uint8_t ($-128$ to $+127$ / $0$ to $255$)
  • int16_t / uint16_t ($-32,768$ to $+32,767$ / $0$ to $65,535$)
  • int32_t / uint32_t ($-2.14 imes 10^9$ to $+2.14 imes 10^9$)
  • int64_t / uint64_t (Full 64-bit integer range)

2. Fast & Least Types

Optimized for CPU register execution vs. memory storage density:

  • int_fastN_t: Fastest type with at least $N$ bits. On a 32-bit ARM, uint_fast8_t is often mapped to a 32-bit register to eliminate sign-extension instructions.
  • int_leastN_t: Smallest type with at least $N$ bits, minimizing Flash/RAM footprint in dense lookup tables.

3. Pointer-Sized & System Types

Specialized integer types for hardware pointers and buffer indexing:

  • uintptr_t / intptr_t: Unsigned/signed integer guaranteed to be the exact same width as a pointer. Essential for memory-mapped I/O (MMIO).
  • size_t: Unsigned integer returned by sizeof; can represent the maximum size of any object in memory.
  • ptrdiff_t: Signed integer resulting from subtracting two pointers.

Formatted Printing with <inttypes.h>

Because exact-width types resolve to different native types across architectures (e.g., uint64_t might be unsigned long on 64-bit Linux, but unsigned long long on 32-bit ARM or Windows), passing them to printf with %lu or %llu causes compiler warnings on cross-platform builds. The ISO C standard solves this via <inttypes.h> stringification macros:

Cinttypes_example.c
#include <stdio.h>
#include <stdint.h>
#include <inttypes.h>

void print_telemetry(uint32_t sensor_id, int16_t temperature, uintptr_t reg_addr) {
    /* PRIu32 expands to "u" or "lu", PRId16 to "d", PRIxPTR to "lx" or "x" */
    printf("Sensor ID: %" PRIu32 " | Temp: %" PRId16 " dC | MMIO Addr: 0x%08" PRIxPTR "\n",
           sensor_id, temperature, reg_addr);
}

3.3 Two's Complement Representation, Sign Extension & Overflow Mechanics

Virtually all modern microprocessors (x86, ARM Cortex-A/R/M, RISC-V) implement signed integers using Two's Complement arithmetic. In two's complement, the most significant bit (MSB) carries a negative weight:

Value(b_{N-1} ... b_0) = -b_{N-1} \cdot 2^{N-1} + \sum_{i=0}^{N-2} b_i \cdot 2^i

Two's Complement 8-Bit Evaluation Example


 Binary Pattern: 1 1 1 1 1 1 1 1
   MSB Bit 7 (Sign):  1 * -2^7  = -128
   Bit 6:             1 *  2^6  =  +64
   Bit 5:             1 *  2^5  =  +32
   Bit 4:             1 *  2^4  =  +16
   Bit 3:             1 *  2^3  =   +8
   Bit 2:             1 *  2^2  =   +4
   Bit 1:             1 *  2^1  =   +2
   Bit 0:             1 *  2^0  =   +1
 ---------------------------------------
   Sum:              -128 + 127 =   -1

 Binary Pattern: 1 0 0 0 0 0 0 0
   MSB Bit 7 (Sign):  1 * -2^7  = -128 (Minimum 8-bit signed value: INT8_MIN)

Sign Extension vs. Zero Extension

When promoting a smaller integer to a larger integer (e.g., casting int16_t to int32_t), the processor must fill the new upper 16 bits:

  • Zero Extension: For unsigned types, the upper bits are simply padded with zeros. In ARM assembly, this is performed in a single cycle via UXTB (Unsigned Extend Byte) or UXTH (Unsigned Extend Halfword).
  • Sign Extension: For signed types, the processor must copy the MSB (sign bit) across all upper bit positions to preserve negative value. In ARM assembly, this is performed via SXTB or SXTH.
Csign_extension_trap.c
#include <stdio.h>
#include <stdint.h>

void inspect_extension(void) {
    int8_t  s_val = -5;              /* 0xFB (binary: 1111 1011) */
    uint8_t u_val = 0xFB;            /* 251  (binary: 1111 1011) */

    int32_t s_promoted = s_val;      /* Sign-extended to: 0xFFFFFFFB (-5) */
    uint32_t u_promoted = u_val;     /* Zero-extended to: 0x000000FB (251) */

    /* Critical trap: casting a signed 8-bit value to uint32_t causes sign extension first! */
    uint32_t dangerous = (uint32_t)s_val; /* Yields 0xFFFFFFFB (4,294,967,291), NOT 0x000000FB! */
    
    printf("s_promoted:  0x%08X\n", s_promoted);
    printf("u_promoted:  0x%08X\n", u_promoted);
    printf("dangerous:   0x%08X\n", dangerous);
}

Signed Overflow (Undefined Behavior) vs. Unsigned Wrap (Defined)

One of the most consequential rules in C language systems engineering is the distinction between signed and unsigned overflow:

  • Unsigned Integer Overflow: By ISO C specification (§6.2.5/9), unsigned integer arithmetic operates strictly modulo $2^N$. It is guaranteed never to overflow; it wraps around deterministically. UINT32_MAX + 1U == 0U. This is valid, standard-compliant behavior widely utilized in hardware ring buffers and timers.
  • Signed Integer Overflow: Under ISO C, signed integer overflow is UNDEFINED BEHAVIOR (UB). The compiler assumes signed overflow can never legally happen. When compiling with optimizations (-O2 or -O3), GCC and Clang will aggressively eliminate code designed to check for signed overflow post-facto:
Cub_signed_overflow_trap.c
#include <stdbool.h>
#include <limits.h>

/* DANGEROUS BUG: The compiler will optimize this entire check away! */
bool bad_check_overflow(int a, int b) {
    /* If a + b overflows, UB occurs.
     * The compiler assumes UB never happens, concludes (a + b < a) is ALWAYS false,
     * and compiles this function down to: "return false;" ! */
    return (a + b < a); 
}

/* DEFENSIVE PRODUCTION PATTERN: Check bounds BEFORE performing arithmetic */
bool safe_add_int32(int32_t a, int32_t b, int32_t *out) {
    if (out == NULL) return false;
    
    if ((b > 0) && (a > (INT32_MAX - b))) {
        return false; /* Positive overflow would occur */
    }
    if ((b < 0) && (a < (INT32_MIN - b))) {
        return false; /* Negative underflow would occur */
    }
    
    *out = a + b;
    return true;
}

3.4 Implicit Conversions & The Integer Promotion Rule (The #1 Embedded Trap)

In C, operands are never evaluated directly at smaller widths than int. Under the Integer Promotion Rule (ISO C §6.3.1.1):

"If an int can represent all values of the original type, the value is converted to an int; otherwise, it is converted to an unsigned int."

This means whenever you execute an operation (+, -, ~, <<, ^) on uint8_t or uint16_t, both operands are silently promoted to a signed 32-bit int before the CPU executes the instruction. This is responsible for severe production firmware bugs.

The Classic Bitwise NOT Trap on Embedded Hardware

Consider toggling an 8-bit GPIO register mask:

Cpromotion_trap.c
#include <stdio.h>
#include <stdint.h>

int main(void) {
    uint8_t status = 0xFE; /* Binary: 1111 1110 */
    
    /* Engineer intends to check if inverting status yields 0x01 */
    if (~status == 0x01) {
        printf("MATCH!\n");
    } else {
        printf("FAILED! Evaluated to: 0x%08X\n", (unsigned int)(~status));
    }
    return 0;
}

Output: FAILED! Evaluated to: 0xFFFFFF01

Root Cause Analysis: status (0xFE) is first promoted to signed 32-bit integer: 0x000000FE. The bitwise NOT (~) operator inverts all 32 bits, producing 0xFFFFFF01. The comparison 0xFFFFFF01 == 0x00000001 fails! To fix this, explicitly cast the result back to (uint8_t)(~status) or mask with 0xFFU.

3.5 Floating-Point Representation (IEEE-754 Single & Double Precision)

Real numbers in embedded firmware (sensor readings, PID control variables, GPS coordinates) are standardized by IEEE-754. In single precision (float, 32 bits) and double precision (double, 64 bits), numbers are decomposed into three fields:

IEEE-754 Single-Precision (32-bit float) Bitfield Structure


  Bit 31:        Sign bit S (0 = positive, 1 = negative)
  Bits 30-23:    Exponent E (8 bits, biased by +127)
  Bits 22-0:     Mantissa / Fraction M (23 bits, implicit leading 1: 1.M)

  Formula: Value = (-1)^S * 2^(E - 127) * (1.M)
Condition Exponent (E) Mantissa (M) Value Represented Firmware Implication
Zero 0 (all 0s) 0 (all 0s) +0.0 or -0.0 Note: +0.0 == -0.0 evaluates to true
Normalized 1 to 254 Any pattern Standard real numbers Full FPU hardware acceleration
Subnormal 0 (all 0s) Non-zero $(-1)^S \cdot 2^{-126} \cdot (0.M)$ Severe performance penalty (up to 100x CPU cycles) without Flush-to-Zero (FTZ)
Infinity 255 (all 1s) 0 (all 0s) $+\infty$ or $-\infty$ Result of division by zero (e.g. 1.0f / 0.0f)
NaN (Not a Number) 255 (all 1s) Non-zero Quiet / Signaling NaN Result of invalid math (0.0f / 0.0f, sqrt(-1.0f)). Any comparison with NaN returns false (even NaN == NaN)!

Hardware FPU vs. Software Emulation on ARM Cortex-M

Microcontrollers like the STM32F4 (Cortex-M4F) and STM32F7 (Cortex-M7) feature an integrated hardware Floating Point Unit (FPU) executing single-precision arithmetic in 1 to 3 cycles. However, Cortex-M0/M0+/M3 lack an FPU; floating-point math on those targets invokes multi-hundred-cycle software emulation routines (__aeabi_fadd, __aeabi_fmul) from libgcc, which can cause real-time deadline violations.

Csafe_float_comparison.c
#include <stdbool.h>
#include <math.h>

#define FLOAT_EPSILON 0.00001f

/* DEFENSIVE: Never compare floating point numbers with == in sensors or control loops */
bool float_is_equal(float a, float b) {
    /* fabs from <math.h> or fabsf for single-precision */
    return fabsf(a - b) < FLOAT_EPSILON;
}

3.6 Endianness Architecture (Little-Endian vs. Big-Endian)

When an integer spans multiple bytes (e.g., a 32-bit word 0x12345678), endianness dictates how those bytes are arranged in physical sequential memory addresses:

  • Little-Endian (ARM Cortex-M default, x86): The Least Significant Byte (LSB) is stored at the lowest memory address. Address 0: 0x78, Address 1: 0x56, Address 2: 0x34, Address 3: 0x12.
  • Big-Endian (Network Byte Order, Motorola, older PowerPC): The Most Significant Byte (MSB) is stored at the lowest memory address. Address 0: 0x12, Address 1: 0x34, Address 2: 0x56, Address 3: 0x78.

Byte-Swapping Primitives: Portable vs. Hardware Accelerated

Serial buses (CAN, Modbus, Ethernet TCP/IP) transmit data in Big-Endian network byte order. When receiving on a Little-Endian Cortex-M MCU, multi-byte values must be flipped. Using GCC built-ins compiles directly to the ARM single-cycle REV machine instruction:

Cbyte_swap_mechanics.c
#include <stdint.h>

/* 16-bit Byte Swap: Compiles to "REV16" on ARM Cortex-M */
static inline uint16_t swap_uint16(uint16_t val) {
    return __builtin_bswap16(val);
}

/* 32-bit Byte Swap: Compiles to "REV" on ARM Cortex-M */
static inline uint32_t swap_uint32(uint32_t val) {
    return __builtin_bswap32(val);
}

/* Runtime Endianness Test Function */
static inline int is_system_little_endian(void) {
    const uint16_t test_val = 0x0001;
    const uint8_t *byte_ptr = (const uint8_t *)&test_val;
    return (*byte_ptr == 0x01); /* Returns 1 if Little-Endian, 0 if Big-Endian */
}

3.7 Real-Time Case Study: Industrial Sensor Packet Parsing & Telemetry

In industrial automation, sensor nodes (e.g. pressure transducers, energy meters) transmit serialized telemetry frames across an RS-485 / Modbus bus. A firmware engineer must parse incoming wire bytes into valid C data types without violating alignment, corrupting sign bits, or triggering undefined behavior:

Cmodbus_packet_parser.c
#include <stdio.h>
#include <stdint.h>
#include <stdbool.h>
#include <string.h>

/* Industrial Telemetry Struct */
typedef struct {
    uint16_t sensor_node_id;
    int16_t  raw_temperature_celsius_scaled; /* Scaled by x10 (e.g. 235 = 23.5 C) */
    uint32_t total_pulse_count;
    float    pressure_psi;
    bool     alarm_active;
} sensor_telemetry_t;

/**
 * @brief Parses raw Big-Endian serial frame into validated telemetry struct.
 * @param wire_buf Raw packet buffer (12 bytes expected).
 * @param buf_len Size of buffer in bytes.
 * @param out_telemetry Pointer to output struct.
 * @return true if parsed cleanly, false on malformed packet.
 */
bool parse_sensor_wire_frame(const uint8_t *wire_buf, size_t buf_len, sensor_telemetry_t *out_telemetry) {
    if (wire_buf == NULL || out_telemetry == NULL || buf_len < 12U) {
        return false;
    }

    /* Extract Node ID (Bytes 0-1, Big-Endian) */
    out_telemetry->sensor_node_id = (uint16_t)(((uint16_t)wire_buf[0] << 8U) | (uint16_t)wire_buf[1]);

    /* Extract Signed Temperature (Bytes 2-3, Big-Endian Two's Complement) */
    uint16_t raw_temp_u16 = (uint16_t)(((uint16_t)wire_buf[2] << 8U) | (uint16_t)wire_buf[3]);
    out_telemetry->raw_temperature_celsius_scaled = (int16_t)raw_temp_u16;

    /* Extract Pulse Count (Bytes 4-7, Big-Endian 32-bit) */
    out_telemetry->total_pulse_count = ((uint32_t)wire_buf[4] << 24U) |
                                      ((uint32_t)wire_buf[5] << 16U) |
                                      ((uint32_t)wire_buf[6] << 8U)  |
                                      ((uint32_t)wire_buf[7]);

    /* Extract Float Pressure (Bytes 8-11, IEEE-754 Single-Precision, Big-Endian)
     * To prevent strict-aliasing violations and unaligned access faults on Cortex-M0,
     * we copy to a temporary 32-bit unsigned integer, byte-swap, and memcpy to float. */
    uint32_t raw_float_bits = ((uint32_t)wire_buf[8]  << 24U) |
                              ((uint32_t)wire_buf[9]  << 16U) |
                              ((uint32_t)wire_buf[10] << 8U)  |
                              ((uint32_t)wire_buf[11]);
    memcpy(&(out_telemetry->pressure_psi), &raw_float_bits, sizeof(float));

    out_telemetry->alarm_active = (out_telemetry->raw_temperature_celsius_scaled > 850); /* > 85.0 C */
    return true;
}

3.8 Hands-On Lab: Architecture Type Width & Memory Layout Inspector

Lab Exercise: The Systems Memory Grid Inspector

In this lab, you will construct a standalone C utility type_memory_inspector.c that inspects platform type sizes, explores IEEE-754 bit representations, dumps raw byte memory layouts in hexadecimal, and verifies endianness.

Complete Source Code: type_memory_inspector.c

Ctype_memory_inspector.c
#include <stdio.h>
#include <stdlib.h>
#include <stdint.h>
#include <stdbool.h>
#include <inttypes.h>
#include <string.h>

/* Dumps raw byte sequence of any memory object */
static void dump_memory_hex(const char *label, const void *ptr, size_t size) {
    const uint8_t *bytes = (const uint8_t *)ptr;
    printf("%-20s [%2zu bytes] @ %p: ", label, size, ptr);
    for (size_t i = 0; i < size; ++i) {
        printf("%02X ", bytes[i]);
    }
    printf("\n");
}

int main(void) {
    printf("========================================================\n");
    printf("     SYSTEMS MEMORY & DATA TYPE ARCHITECTURE INSPECTOR   \n");
    printf("========================================================\n\n");

    /* 1. Architecture Type Width Verification */
    printf("--- [1] ARCHITECTURE TYPE WIDTHS ---\n");
    printf("sizeof(char):        %zu byte  (%zu bits)\n", sizeof(char), sizeof(char) * 8);
    printf("sizeof(short):       %zu bytes (%zu bits)\n", sizeof(short), sizeof(short) * 8);
    printf("sizeof(int):         %zu bytes (%zu bits)\n", sizeof(int), sizeof(int) * 8);
    printf("sizeof(long):        %zu bytes (%zu bits)\n", sizeof(long), sizeof(long) * 8);
    printf("sizeof(long long):   %zu bytes (%zu bits)\n", sizeof(long long), sizeof(long long) * 8);
    printf("sizeof(void *):      %zu bytes (%zu bits)\n", sizeof(void *), sizeof(void *) * 8);
    printf("sizeof(size_t):      %zu bytes (%zu bits)\n", sizeof(size_t), sizeof(size_t) * 8);
    printf("sizeof(uintptr_t):   %zu bytes (%zu bits)\n\n", sizeof(uintptr_t), sizeof(uintptr_t) * 8);

    /* 2. Endianness Memory Dump */
    printf("--- [2] ENDIANNESS & INTEGER MEMORY LAYOUT ---\n");
    uint32_t test_word = 0x12345678U;
    dump_memory_hex("uint32_t 0x12345678", &test_word, sizeof(test_word));
    
    int16_t neg_int16 = -5;
    dump_memory_hex("int16_t -5", &neg_int16, sizeof(neg_int16));

    /* 3. IEEE-754 Floating-Point Breakdown */
    printf("\n--- [3] IEEE-754 FLOATING-POINT DECOMPOSITION ---\n");
    float f_val = -12.375f;
    uint32_t f_bits;
    memcpy(&f_bits, &f_val, sizeof(float));
    dump_memory_hex("float -12.375", &f_val, sizeof(f_val));

    uint32_t sign = (f_bits >> 31) & 0x1;
    uint32_t exp  = (f_bits >> 23) & 0xFF;
    uint32_t mant = f_bits & 0x7FFFFF;

    printf("Float Value: %f\n", f_val);
    printf("  Sign Bit:  %" PRIu32 " (%s)\n", sign, sign ? "Negative" : "Positive");
    printf("  Exponent:  %" PRIu32 " (Biased), %d (True Unbiased)\n", exp, (int)exp - 127);
    printf("  Mantissa:  0x%06" PRIx32 "\n\n", mant);

    printf("========================================================\n");
    printf("Inspection completed successfully with zero defects.\n");
    return EXIT_SUCCESS;
}

3.9 Knowledge Verification & Self-Study Quiz

Self-Assessment Check

Q1: On an ILP32 architecture (e.g. 32-bit ARM Cortex-M), what is the sizeof(long) and sizeof(void*)?

Explanation: Under ILP32 (Integer, Long, Pointer = 32 bits), int, long, and pointers are all 4 bytes (32 bits).

Q2: What happens when evaluating: uint8_t a = 0x80; uint8_t b = 0x80; if (a + b == 0x100) ?

Explanation: Under C's integer promotion rules, uint8_t operands are promoted to signed 32-bit int before addition, so 128 + 128 = 256 (0x100). The comparison succeeds.

Q3: Why is signed integer overflow treated as Undefined Behavior (UB) by the compiler?

Explanation: Leaving signed overflow undefined allows compilers to optimize loops and reorder expressions without emitting defensive CPU check instructions.

Q4: On a Little-Endian system, how is the 32-bit value 0xAABBCCDD stored at memory address 0x20000000?

Explanation: In Little-Endian format, the least significant byte (0xDD) is located at the lowest memory address.

Q5: Why should floating-point numbers never be compared directly with == in control loops?

Explanation: Binary IEEE-754 cannot represent most decimal fractions exactly. Small accumulation errors cause direct equality comparisons to fail unpredictably. Always compare using an epsilon threshold.
