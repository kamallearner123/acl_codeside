Designing & Developing Embedded Systems Projects

A multi-platform engineering guide covering the entire Embedded Systems Development Life Cycle (EDLC) from requirements and hardware co-design to bare-metal & RTOS firmware, HIL verification, and secure production deployment across STM32, Texas Instruments, and ESP32.

Engineering Context & Silicon Constraints: Unlike traditional web or cloud software where execution environments are virtualized and resources are elastic, the Embedded Software Development Life Cycle (SDLC) is governed by physical silicon, PCB board schematics, thermal/power budgets, and hard real-time latency deadlines. In this handbook, we apply the V-Model methodology across three real-world hardware platforms: STM32 (ARM Cortex-M4/M7), Texas Instruments (MSP430 / C2000), and ESP32 (Xtensa / RISC-V).

1. The Embedded SDLC & V-Model Methodology

In safety-critical and high-reliability embedded products (automotive, industrial automation, medical robotics), discovering a bug after manufacturing incurs immense costs (physical recalls, re-spinning PCBs, or safety hazards). The Embedded V-Model provides strict bidirectional traceability between specification phases and verification phases:

The 7 Phases of the Embedded Firmware Lifecycle

  1. Phase 1: Requirements Analysis & Feasibility: Define functional features, timing constraints (e.g., $1\,\text{kHz}$ PID loop, $<10\,\mu\text{s}$ ISR latency), power envelopes ($<2.5\,\mu\text{A}$ in deep sleep), and regulatory safety standards (ISO 26262 ASIL-B/D, IEC 61508).
  2. Phase 2: System Architecture & Hardware/Software Partitioning: Decide what executes in dedicated hardware silicon (timers, DMA, hardware CRC/AES) versus CPU software. Select the MCU (STM32 vs TI vs ESP32) and design clock/power trees.
  3. Phase 3: Detailed Firmware Design: Establish layered software modules (CMSIS $\rightarrow$ HAL/LL $\rightarrow$ BSP $\rightarrow$ App), FreeRTOS task schedules, priority levels, queue sizes, and vector table memory maps (`SCB->VTOR`).
  4. Phase 4: Implementation (Defensive Embedded C): Write MISRA-C:2012 compliant C code using strict fixed-width types (`uint32_t`), atomic register writes (`BSRR`), and `volatile` access to prevent compiler optimization hazards.
  5. Phase 5: Multi-Tier Verification & HIL Testing: Unit tests with Unity/CMock on host PCs, Hardware-in-the-Loop (HIL) automated rigs, logic analyzer bus tracing (CAN, SPI, I2C), and GDB/ST-LINK hardware debugging.
  6. Phase 6: Deployment, Production Flashing & Bring-Up: Automated bed-of-nails flashing scripts, MCU Readout Protection (RDP Level 1/2), dual-bank bootloaders, and fail-safe over-the-air (OTA) updates.
  7. Phase 7: Maintenance, Crash Diagnostics & Field Operations: Non-volatile crash dump logging, post-mortem root cause analysis (RCA), and Cortex-M HardFault exception frame decoding ($R0$–$R3$, $R12$, $LR$, $PC$, $xPSR$).

3. Schematics, Power Delivery & Hardware Bring-Up

Writing reliable firmware is impossible on unstable hardware. Before touching a compiler, embedded engineers must understand the physical board layout and power budgeting:

Power Supply Topology: LDO vs. Buck Converter

  • Low-Dropout Regulators (LDO): Excellent for noise-sensitive analog ADC/DAC rails due to low output ripple and zero switching noise, but poor efficiency when dropping 12V/5V down to 3.3V ($\eta = V_{out} / V_{in}$).
  • Switching Buck Regulators: Up to 95% power efficiency, essential for battery-operated designs and powering ESP32 Wi-Fi bursts (which can spike up to 450mA instantaneous current).
  • Decoupling Matrix: Always place 100nF ceramic X7R capacitors within 2mm of every $V_{DD}$/$V_{SS}$ pin pair, backed by a 4.7µF–10µF bulk tantalum/ceramic capacitor per power rail.

Oscillator Circuitry & Pin Multiplexing

  • HSE (High-Speed External): 8MHz–25MHz crystal for precise CAN bit timings and high-speed USB/Ethernet clock trees. Sizing load capacitors: $C_L = (C_1 \cdot C_2) / (C_1 + C_2) + C_{stray}$.
  • LSE (Low-Speed External): 32.768 kHz tuning-fork crystal providing accurate RTC timekeeping during low-power standby.
  • Hardware Bring-Up Checklist: Verify clean 3.3V rail $\rightarrow$ verify NRST pull-up ($10\text{k}\Omega$) and 100nF capacitor $\rightarrow$ inspect SWD/JTAG debug signals on oscilloscope $\rightarrow$ confirm crystal oscillation $\rightarrow$ flash LED blinky test.

5. Bare-Metal Peripheral Drivers & Nested Interrupts

Understanding register-level bit operations and interrupt controllers is essential before relying on vendor abstraction layers:

// Clean register-level GPIO toggle on STM32 using BSRR (Bit Set/Reset Register)
void GPIOA_Pin5_Toggle(void) {
    if (GPIOA->ODR & (1U << 5)) {
        GPIOA->BSRR = (1U << (5 + 16)); // Atomic Reset without read-modify-write
    } else {
        GPIOA->BSRR = (1U << 5);        // Atomic Set
    }
}

// Low-power interrupt-driven architecture:
void EXTI15_10_IRQHandler(void) {
    if (EXTI->PR & (1U << 13)) {
        EXTI->PR = (1U << 13); // Clear pending bit by writing 1
        g_button_pressed = true;
    }
}

6. High-Throughput Serial Communication with Circular DMA

Traditional character-by-character interrupt UART wastes hundreds of CPU cycles per millisecond. Industrial firmware uses Circular DMA with Idle-Line Detection:

Zero-Copy UART Reception Architecture

1. The DMA controller receives bytes directly from the UART data register into a circular RAM buffer without CPU intervention.
2. When a frame ends, the UART hardware detects that the RX line remained idle for one full byte period ($T_{idle}$).
3. The Idle-Line interrupt fires exactly once per message, allowing the CPU to read the buffer length ($L = \text{BUFFER\_SIZE} - \text{DMA\_NDTR}$) and dispatch the packet immediately.

7. Industrial CAN 2.0B, CAN-FD & RS-485 Modbus

CAN (Controller Area Network) is the gold standard for automotive and industrial automation due to differential noise immunity, hardware arbitration, and automatic retransmission:

// Transmitting telemetry packet over CAN 2.0B on STM32
CAN_TxHeaderTypeDef tx_header;
uint8_t payload[8];
uint32_t tx_mailbox;

tx_header.StdId = 0x205;             // Standard 11-bit ID: Motor Controller
tx_header.RTR = CAN_RTR_DATA;
tx_header.IDE = CAN_ID_STD;
tx_header.DLC = 8;                   // 8 data bytes

payload[0] = (uint8_t)(rpm & 0xFF);
payload[1] = (uint8_t)((rpm >> 8) & 0xFF);
payload[2] = (uint8_t)(current_mA & 0xFF);
payload[3] = (uint8_t)((current_mA >> 8) & 0xFF);
payload[4] = status_flags;

HAL_CAN_AddTxMessage(&hcan1, &tx_header, payload, &tx_mailbox);

8. Real-Time Multitasking with FreeRTOS

Moving from a single-threaded superloop to preemptive multitasking requires clean task separation, queue-based message passing, and deterministic priorities:

// Typical FreeRTOS Multi-Task Industrial Layout
QueueHandle_t sensorQueue;

void vSensorAcquisitionTask(void *pvParameters) {
    SensorData_t data;
    TickType_t xLastWakeTime = xTaskGetTickCount();
    const TickType_t xFrequency = pdMS_TO_TICKS(20); // Exact 50 Hz sampling

    for (;;) {
        vTaskDelayUntil(&xLastWakeTime, xFrequency);
        Read_Analog_Sensors(&data);
        xQueueSend(sensorQueue, &data, 0); // Non-blocking queue send
    }
}

void vTelemetryTask(void *pvParameters) {
    SensorData_t data;
    for (;;) {
        if (xQueueReceive(sensorQueue, &data, portMAX_DELAY) == pdPASS) {
            Publish_MQTT_Telemetry(&data);
        }
    }
}

11. Multi-Tier Verification & Hardware-in-the-Loop (HIL) Testing

In Phase 5 of the SDLC, verification must cover every layer of the firmware stack:

The Embedded Testing Pyramid

  • Unit Testing on Host (PC): Run core algorithms (PID maths, circular buffer pointer manipulation, state machine parsing) in GCC with Unity/CMock by stubbing out hardware registers.
  • Integration & Bus Testing: Use an 8-channel USB Logic Analyzer (Saleae / PulseView) to measure real physical timings: I2C clock stretching, SPI setup/hold times, and CAN differential voltage states.
  • Hardware-in-the-Loop (HIL) Rig: Connect target boards to an automated test fixture that injects sensor voltages, reads PWM duty cycles, and asserts fault conditions to verify watchdog resets.

12. Bootloaders, Production Flashing & Secure OTA

Deploying firmware to the factory floor requires partition maps, secure boot, and protection against intellectual property theft:

Security & Flash Memory Layout

  • Readout Protection (RDP): Setting STM32 Option Bytes to RDP Level 1 disables SWD debug access to prevent firmware dumping from the board.
  • Dual-Bank Flash Partition: Reserving Bank 1 for active firmware and Bank 2 for incoming OTA updates. The bootloader validates CRC32 / RSA signatures before jumping to the new image via `SCB->VTOR`.

14. 4 Real-World Production Capstones

Throughout the course, students build, test, and present four industry-grade embedded projects executing the full V-Model lifecycle:

CAPSTONE 1 • STM32

Industrial CAN Motor Drive & Telemetry Node

Closed-loop PID velocity control of a DC/stepper motor on STM32F4. Quadrature encoder feedback, PWM drive, ADC shunt current sensing, IWDG watchdog, and periodic CAN bus status broadcasting with fault recovery.

CAPSTONE 2 • TI MSP430

Solar Energy Harvesting Sensor Beacon

Battery-less sensor node running on a mini solar panel and supercapacitor. Utilizes MSP430FR5994 FRAM for instant zero-power logging, sub-microamp LPM3.5 sleep, and periodic BLE advertisement bursts.

CAPSTONE 3 • ESP32-S3

Secure Dual-Core Edge Gateway & OTA

Dual-core FreeRTOS application. Core 0 handles high-speed BLE sensor scanning and reception. Core 1 hosts an embedded Web dashboard, publishes MQTT over TLS, and performs rollback-safe OTA firmware downloads.

CAPSTONE 4 • HETEROGENEOUS

Integrated Multi-MCU Smart System

Combines an STM32 real-time controller and an ESP32 wireless hub via a dedicated SPI/DMA packet protocol with CRC verification. Demonstrates industrial command execution, real-time safety shut-offs, and cloud telemetry.
