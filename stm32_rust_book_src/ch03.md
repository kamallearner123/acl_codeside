## 3.1 The Three Rules of Ownership

1. Every value has exactly **one owner**.
2. When the owner goes out of scope the value is **dropped** (cleaned up).
3. Ownership can be **moved** to another owner; the old name can no longer be used.

```rust Move semantics
let a = [1u8, 2, 3, 4];     // arrays of Copy types are Copy - see 3.2
let msg = heapless::String::<16>::new();   // not Copy: it owns its buffer
let other = msg;            // ownership MOVES to `other`
// println!("{}", msg);     // compile error: value used after move
```

In C, two pointers to the same buffer is normal - and the root of double-free and use-after-free bugs. In Rust the compiler tracks who owns what, so those bugs cannot be written.

## 3.2 Copy vs Move

Small plain-data types (`u8`, `bool`, `f32`, arrays of those, tuples of those) implement `Copy`: assignment duplicates them. Types that own a resource do **not**.

| Type | Copy? | Why |
|---|---|---|
| `u32`, `bool`, `f32` | Yes | Just bits |
| `[u8; 4]` | Yes | Array of Copy |
| A GPIO pin in output mode | **No** | It represents exclusive access to hardware |
| A UART driver | **No** | Duplicating it would give two writers to one peripheral |
| `&T` (shared reference) | Yes | |
| `&mut T` | **No** | Exclusive access cannot be duplicated |

## 3.3 Drop: Deterministic Cleanup (RAII)

When a value leaves scope Rust calls its `Drop` implementation. This is how you build "lock released automatically", "chip-select released automatically" and "power domain switched off automatically".

```rust RAII chip-select guard
struct Selected<'a, P: embedded_hal::digital::OutputPin> {
    cs: &'a mut P,
}

impl<'a, P: embedded_hal::digital::OutputPin> Selected<'a, P> {
    fn new(cs: &'a mut P) -> Self {
        let _ = cs.set_low();   // assert CS
        Self { cs }
    }
}

impl<P: embedded_hal::digital::OutputPin> Drop for Selected<'_, P> {
    fn drop(&mut self) {
        let _ = self.cs.set_high();   // always released, even on early return
    }
}
```

Compare with C where an early `return` in the middle of an SPI transaction leaves CS asserted - a classic bug.

## 3.4 Ownership of Hardware

This is where ownership becomes a hardware-safety feature. All peripherals exist exactly once:

```rust Peripherals::take
use stm32f4xx_hal::pac;

let dp = pac::Peripherals::take().unwrap();   // Some(...) the first time, None afterwards
let gpioa = dp.GPIOA.split();                 // consumes dp.GPIOA
let mut led = gpioa.pa5.into_push_pull_output(); // consumes the pin; it cannot be used as input now
```

- `take()` returns the whole set of peripherals **once**. A second call returns `None`, so two modules cannot both "own" the same peripheral.
- `.split()` and `.into_push_pull_output()` **consume** their input. After the call the old handle no longer exists, so you cannot accidentally use `pa5` as an input while it drives an LED.

> [hw] C versus Rust on PA5 | In C, `HAL_GPIO_WritePin(GPIOA, GPIO_PIN_5, ...)` compiles from anywhere in the program, including a timer callback that has no idea an SPI driver configured PA5 as SCK. In Rust only the code that owns the `led` variable can toggle it.

## 3.5 Passing Ownership Around

```rust Functions that take or borrow
fn blink_once(mut led: Pin<'A', 5, Output>, delay: &mut impl DelayNs) -> Pin<'A', 5, Output> {
    led.set_high();
    delay.delay_ms(100);
    led.set_low();
    led            // give ownership back to the caller
}
```

Returning the value is clumsy. The next chapter shows **borrowing**, which lets a function use a value without taking it - the normal way to write Rust.
