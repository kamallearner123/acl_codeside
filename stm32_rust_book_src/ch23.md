## 23.1 The Rust Debugging Toolbox

The hardware is the same as Book 1: ST-LINK over SWD. The host software changes.

| Task | C course | Rust course |
|---|---|---|
| Flash and run | CubeIDE | `cargo run` through `probe-rs` |
| Logging | `printf` over UART or SWO | `defmt` over RTT |
| Breakpoints | CubeIDE GDB | VS Code with probe-rs debugger, or GDB |
| Fault analysis | CFSR, HFSR registers | Same registers, plus a typed `ExceptionFrame` |

## 23.2 `cargo run` with probe-rs

```toml .cargo/config.toml
[build]
target = "thumbv7em-none-eabihf"

[target.thumbv7em-none-eabihf]
runner = "probe-rs run --chip STM32F446RETx"
rustflags = ["-C", "link-arg=-Tlink.x", "-C", "link-arg=-Tdefmt.x"]

[env]
DEFMT_LOG = "debug"
```

```bash Flash, run and see logs
cargo run --release
```

`defmt` messages appear in the terminal with timestamps and file/line.

## 23.3 `defmt` Logging

```rust Efficient logging
use defmt::{info, warn, error};
use defmt_rtt as _;
use panic_probe as _;

info!("temperature = {} dC", temp_dc);
warn!("sensor retry {}", attempt);
error!("bus error: {:?}", defmt::Debug2Format(&err));
```

Format strings are stored on the PC, not in flash, so logs cost only a few bytes each. Set `DEFMT_LOG` to trim levels at compile time.

## 23.4 Breakpoints in VS Code

Install the **probe-rs-debugger** extension. A minimal `launch.json` entry:

```json launch.json
{
  "type": "probe-rs-debug",
  "request": "launch",
  "name": "Debug STM32F446",
  "chip": "STM32F446RETx",
  "coreConfigs": [{
    "programBinary": "target/thumbv7em-none-eabihf/debug/firmware",
    "rttEnabled": true
  }]
}
```

You can set breakpoints, step, watch variables and see RTT output. Build in **debug** profile for accurate variable inspection; release code is optimised and variables may vanish.

## 23.5 GDB and OpenOCD

```bash GDB session
openocd -f interface/stlink.cfg -f target/stm32f4x.cfg      # terminal 1
arm-none-eabi-gdb target/thumbv7em-none-eabihf/debug/firmware   # terminal 2
(gdb) target extended-remote :3333
(gdb) monitor reset halt
(gdb) load
(gdb) break main
(gdb) continue
```

Useful commands: `bt`, `info registers`, `x/16wx 0x20000000`, `monitor reset halt`, `watch variable`.

## 23.6 Panics and Hard Faults

A Rust panic calls the panic handler. With `panic-probe` it prints a message and location over RTT and halts, so you immediately see "index out of bounds at src/main.rs:42". In production configure `panic-reset` or a custom handler that logs to flash and resets.

```rust HardFault handler with exception frame
use cortex_m_rt::{exception, ExceptionFrame};

#[exception]
unsafe fn HardFault(ef: &ExceptionFrame) -> ! {
    defmt::error!("HardFault pc={:#x} lr={:#x}", ef.pc(), ef.lr());
    loop { cortex_m::asm::bkpt(); }
}
```

Look up `pc` in the disassembly (`cargo objdump`) to find the failing instruction. Safe Rust cannot normally cause a hard fault by itself; faults come from `unsafe` code, bad linker placement, DMA misuse or stack overflow.

## 23.7 Stack Overflow Protection

On bare-metal, the stack grows toward your `.bss` and `.data` and silently corrupts them. Use **flip-link**, which places the stack below the static data so overflow hits the bottom of RAM and triggers a hard fault instead:

```toml flip-link as the linker
[target.thumbv7em-none-eabihf]
linker = "flip-link"
```

## 23.8 Logic Analyzer

Use a logic analyzer for what the debugger cannot see: SPI/I2C/UART bytes on the wire, PWM timing, interrupt latency (toggle a GPIO in the ISR and measure). It is the arbiter when software and hardware disagree.
