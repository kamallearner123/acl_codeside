## 14.1 The Problem: Sharing Data with an ISR

In C you made a `volatile` flag and hoped. In Rust the compiler will not let you share a mutable value between `main` and an interrupt handler without an explicit mechanism, because an ISR can run *between any two instructions* of `main`.

```rust Rejected by the compiler
static mut BUTTON_PRESSED: bool = false;     // compiles only with unsafe, and races

#[interrupt]
fn EXTI15_10() { unsafe { BUTTON_PRESSED = true; } }
```

Three safe patterns cover almost every case.

| Pattern | Use for | Cost |
|---|---|---|
| **Atomics** | Flags and counters up to 32 bits | Single instruction, no lock |
| **`critical_section::Mutex<RefCell<T>>`** | Peripherals and structs shared with ISRs | Briefly disables interrupts |
| **RTIC resources / Embassy channels** | Larger designs | Framework-checked, priority-aware |

## 14.2 Atomics for Flags and Counters

```rust AtomicBool and AtomicU32
use core::sync::atomic::{AtomicBool, AtomicU32, Ordering};

static BUTTON_EVENT: AtomicBool = AtomicBool::new(false);
static TICKS: AtomicU32 = AtomicU32::new(0);

#[interrupt]
fn EXTI15_10() {
    BUTTON_EVENT.store(true, Ordering::Release);
}

// main loop
if BUTTON_EVENT.swap(false, Ordering::Acquire) {
    // handle one press - the flag is read and cleared in a single atomic step
}
```

`swap` removes the read-then-clear window that causes lost events in C. Cortex-M0 has no atomic read-modify-write instructions; on M0 use the `portable-atomic` crate with a critical section.

## 14.3 Sharing a Peripheral: `Mutex<RefCell<Option<T>>>`

The ISR needs the button pin to clear the interrupt flag. The pin is created in `main`, so it must be **moved** into a global that both can reach:

```rust EXTI interrupt on PC13
use core::cell::RefCell;
use critical_section::Mutex;
use stm32f4xx_hal::{gpio::{Edge, Input, Pin}, pac::{self, interrupt}, prelude::*};

type Button = Pin<'C', 13, Input>;
static G_BUTTON: Mutex<RefCell<Option<Button>>> = Mutex::new(RefCell::new(None));
static PRESSES: AtomicU32 = AtomicU32::new(0);

#[entry]
fn main() -> ! {
    let mut dp = pac::Peripherals::take().unwrap();
    let mut syscfg = dp.SYSCFG.constrain();
    let gpioc = dp.GPIOC.split();

    let mut button = gpioc.pc13.into_pull_up_input();
    button.make_interrupt_source(&mut syscfg);
    button.trigger_on_edge(&mut dp.EXTI, Edge::Falling);
    button.enable_interrupt(&mut dp.EXTI);

    critical_section::with(|cs| G_BUTTON.borrow(cs).replace(Some(button)));   // move into the global

    unsafe { cortex_m::peripheral::NVIC::unmask(pac::Interrupt::EXTI15_10); } // enable in the NVIC last

    loop { cortex_m::asm::wfi(); }
}

#[interrupt]
fn EXTI15_10() {
    critical_section::with(|cs| {
        if let Some(btn) = G_BUTTON.borrow(cs).borrow_mut().as_mut() {
            btn.clear_interrupt_pending_bit();
        }
    });
    PRESSES.fetch_add(1, Ordering::Relaxed);
}
```

How it works:

- `Mutex` can be shared (`static`) but only gives access inside a **critical section** (`cs` token) - interrupts are disabled for those few instructions.
- `RefCell` provides run-time-checked mutability inside the shared `Mutex`.
- `Option` lets the static start as `None` until `main` fills it - this is the *Rust shape* of "initialise a global peripheral at start-up".
- You cannot reach the pin without going through `critical_section::with`, so a race is impossible.

> [tip] Enable the interrupt last | Configure the peripheral, move it into the global, and unmask the NVIC line as the final step. If the interrupt fires before the global is filled, the handler sees `None` and silently does nothing - safe, but you lose the event.

## 14.4 The Flag-and-Process Pattern Still Applies

The rules from Book 1 do not change: **ISRs are short**. Rust makes the pattern safer, not different.

| ISR does | Main loop does |
|---|---|
| Clear the interrupt flag | Debounce, decide, act |
| Store a timestamp or set an atomic | Print, drive outputs |
| Push a byte to a queue | Parse commands |

```rust heapless queue between ISR and main
use heapless::spsc::{Queue, Producer, Consumer};

static mut RX_Q: Queue<u8, 64> = Queue::new();   // see chapter 16 for the safe split at start-up
// ISR owns `Producer`, main owns `Consumer`: single producer, single consumer, no lock needed
```

`Queue::split()` gives you a `Producer` and a `Consumer`; move the producer into the ISR's global and keep the consumer in `main`. Each half is `Send` but not `Clone`, so there is exactly one writer and one reader by construction.

## 14.5 Priorities and Nested Interrupts

- The NVIC supports 16 priority levels on the F446 (4 bits). Lower number = higher priority.
- Set them with `NVIC::set_priority()` (needs `unsafe` on the raw call).
- A critical section masks **all** configurable interrupts. For long sections prefer RTIC, which uses the BASEPRI register to block only lower-priority handlers.

## 14.6 RTIC in a Nutshell

RTIC (Real-Time Interrupt-driven Concurrency) makes the interrupt model the architecture: tasks are ISRs, shared data are **resources** with compile-time-computed priority ceilings. The compiler proves absence of data races and deadlock **without** a run-time lock for the highest-priority user.

```rust RTIC sketch
#[rtic::app(device = stm32f4xx_hal::pac, dispatchers = [SPI1])]
mod app {
    #[shared] struct Shared { presses: u32 }
    #[local]  struct Local  { button: Button }

    #[init] fn init(cx: init::Context) -> (Shared, Local) { /* configure, return resources */ todo!() }

    #[task(binds = EXTI15_10, shared = [presses], local = [button])]
    fn on_button(mut cx: on_button::Context) {
        cx.local.button.clear_interrupt_pending_bit();
        cx.shared.presses.lock(|p| *p += 1);
    }
}
```

> [warn] Do not call blocking code in an ISR | `delay.delay_ms()` in a handler is the same bug as `HAL_Delay()` in C: it blocks everything of equal or lower priority. Rust does not prevent that; design discipline does.
