## 6.1 Structs: Data with Meaning

A C `uint8_t` could be a duty cycle, a channel number or a temperature. A Rust **newtype** makes the meaning part of the type so they cannot be mixed up.

```rust Newtypes for units
#[derive(Clone, Copy, PartialEq, PartialOrd)]
struct Millivolts(u16);
#[derive(Clone, Copy)]
struct DegC(i16);              // value in 0.1 degree units

impl Millivolts {
    fn from_raw(raw: u16) -> Self { Millivolts(((raw as u32 * 3300) / 4095) as u16) }
}

fn set_threshold(t: DegC) { /* ... */ }
// set_threshold(Millivolts(500));   // ERROR: expected DegC
```

Mixing a voltage with a temperature is now a compile error, at zero run-time cost - a newtype compiles to the bare integer.

## 6.2 Enums That Carry Data

C enums are named integers. Rust enums are **tagged unions**: each variant can hold different data, and `match` forces you to handle all of them.

```rust Protocol commands as an enum
enum Command {
    LedOn,
    LedOff,
    SetPwm { channel: u8, duty: u16 },
    ReadAdc(u8),
    Reboot,
}

fn handle(cmd: Command) {
    match cmd {
        Command::LedOn => led.set_high(),
        Command::LedOff => led.set_low(),
        Command::SetPwm { channel, duty } => pwm_set(channel, duty),
        Command::ReadAdc(ch) => adc_read(ch),
        Command::Reboot => cortex_m::peripheral::SCB::sys_reset(),
    }   // add a new variant and every match that ignores it fails to compile
}
```

## 6.3 State Machines with Enums

```rust Traffic light
#[derive(Clone, Copy, PartialEq)]
enum Light { Green, Yellow, Red, Pedestrian }

impl Light {
    fn duration_ms(self) -> u32 {
        match self { Light::Green => 8000, Light::Yellow => 2000, Light::Red => 6000, Light::Pedestrian => 5000 }
    }
    fn next(self, ped_request: bool) -> Light {
        match (self, ped_request) {
            (Light::Green, _) => Light::Yellow,
            (Light::Yellow, _) => Light::Red,
            (Light::Red, true) => Light::Pedestrian,
            (Light::Red, false) | (Light::Pedestrian, _) => Light::Green,
        }
    }
}
```

This is Book 1's table-driven state machine, but the compiler now proves that every state and every transition is covered. It also runs on your PC under `cargo test` - no hardware needed.

## 6.4 The Type-State Pattern

The HAL uses structs and generics so that **the type of a pin tells you what mode it is in**. Operations that do not make sense are not available.

```rust Type-state in the HAL
let pa5 = gpioa.pa5;                       // Pin<'A', 5>                 - Input<Floating> by default
let mut led = pa5.into_push_pull_output(); // Pin<'A', 5, Output>
led.set_high();                            // exists only for outputs
let btn = gpioc.pc13.into_pull_up_input(); // Pin<'C', 13, Input>
// btn.set_high();                         // ERROR: no method `set_high` for input pins
```

You can build the same for your own hardware:

```rust Your own type-state
struct Disabled; struct Enabled;
struct Sensor<S> { _state: core::marker::PhantomData<S> }

impl Sensor<Disabled> {
    fn enable(self) -> Sensor<Enabled> { /* write enable register */ Sensor { _state: core::marker::PhantomData } }
}
impl Sensor<Enabled> {
    fn read(&mut self) -> u16 { /* ... */ 0 }
}
// Sensor<Disabled> has no `read`: reading before enabling cannot be written.
```

> [tip] Use type-state for sequences that must happen in order | Power-up before configure, configure before start, start before read. In C these are comments in a header. In Rust they are compile errors.

## 6.5 Hardware Abstraction with Structs

Group related pins and peripherals into a struct that represents the board feature, not the chip:

```rust A board support struct
struct Board {
    led: Pin<'A', 5, Output>,
    button: Pin<'C', 13, Input>,
    console: Serial<pac::USART2>,
}

impl Board {
    fn init(dp: pac::Peripherals, clocks: &Clocks) -> Self { /* split GPIO, build serial */ unimplemented!() }
}
```

Application code receives a `Board` and never mentions `GPIOA` or `USART2`; swapping to another board only changes `Board::init`.
