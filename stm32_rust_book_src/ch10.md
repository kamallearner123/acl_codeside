## 10.1 Native vs Cross Compilation

Your PC runs x86-64 (or Apple/ARM64); the NUCLEO-F446RE runs a 32-bit Cortex-M4F. **Cross-compilation** means building code for a different machine than the one doing the build. In C you installed `arm-none-eabi-gcc`; in Rust you add a **target**.

```bash Install the Cortex-M4F target
rustup target add thumbv7em-none-eabihf
rustup target list --installed
```

The name decodes as: `thumbv7em` (Thumb-2 instruction set, ARMv7E-M) - `none` (no operating system) - `eabihf` (embedded ABI, hardware floating point).

## 10.2 Choosing the Right Target

| Core | Example chips | Rust target |
|---|---|---|
| Cortex-M0 / M0+ | STM32F0, G0, L0 | `thumbv6m-none-eabi` |
| Cortex-M3 | STM32F1, L1 | `thumbv7m-none-eabi` |
| Cortex-M4 / M7 without FPU | - | `thumbv7em-none-eabi` |
| Cortex-M4F / M7F with FPU | **STM32F4 (F446)**, L4, F7 | `thumbv7em-none-eabihf` |
| Cortex-M23 | STM32L5 (partly) | `thumbv8m.base-none-eabi` |
| Cortex-M33 | STM32L5, U5, H5 | `thumbv8m.main-none-eabihf` |

> [warn] Match the target to the FPU | Using `thumbv7em-none-eabi` (soft float) on an F4 works but is much slower for `f32`. Using `...eabihf` on a core without an FPU crashes on the first float instruction.

## 10.3 Project Configuration

```toml .cargo/config.toml
[build]
target = "thumbv7em-none-eabihf"

[target.thumbv7em-none-eabihf]
runner = "probe-rs run --chip STM32F446RETx"
rustflags = ["-C", "link-arg=-Tlink.x", "-C", "link-arg=-Tdefmt.x"]

[env]
DEFMT_LOG = "info"
```

With this file, `cargo build` cross-compiles and `cargo run` builds, flashes and starts the program in one command.

```toml Cargo.toml
[package]
name = "blinky"
version = "0.1.0"
edition = "2021"

[dependencies]
cortex-m = { version = "0.7", features = ["critical-section-single-core"] }
cortex-m-rt = "0.7"
stm32f4xx-hal = { version = "0.21", features = ["stm32f446"] }
defmt = "0.3"
defmt-rtt = "0.4"
panic-probe = { version = "0.3", features = ["print-defmt"] }

[profile.dev]
opt-level = "s"        # unoptimised Rust is too slow and large for most firmware
debug = true

[profile.release]
opt-level = "s"
lto = "fat"
codegen-units = 1
debug = true           # debug info lives in the ELF, not in flash
```

> [tip] Pin your versions | HAL crates change their APIs between releases. Commit `Cargo.lock` and note the HAL version in your README so a colleague (or you in a year) gets the same build. The examples in this book target `stm32f4xx-hal` 0.21 and `embedded-hal` 1.0.

## 10.4 What the Compiler Produces

```bash Inspect the result
cargo build --release
cargo size --release -- -A          # section sizes (cargo-binutils)
cargo objdump --release -- -d | less
arm-none-eabi-nm -S --size-sort target/thumbv7em-none-eabihf/release/blinky | tail
cargo bloat --release -n 10         # which functions use the flash
```

The output is an ELF file - the same format as in Book 1 - so your debugger, `addr2line` and logic of reading a map file all still apply.

## 10.5 Why It Just Works

- `core` is pre-compiled for each target and shipped with `rustup target add`.
- `compiler_builtins` supplies helper routines (e.g. 64-bit division) that C gets from `libgcc`.
- LLVM generates the machine code; the linker is `rust-lld`, bundled with Rust.

If you need a target without a pre-built `core` (rare), nightly Rust and `-Z build-std` build `core` from source.

## 10.6 Size and Speed Controls

| Setting | Effect |
|---|---|
| `opt-level = "s"` / `"z"` | Optimise for size |
| `opt-level = 3` | Optimise for speed |
| `lto = "fat"` | Whole-program optimisation, removes unused code |
| `codegen-units = 1` | Better optimisation, slower build |
| `panic = "abort"` | Implicit on `no_std` targets - no unwinding code |
