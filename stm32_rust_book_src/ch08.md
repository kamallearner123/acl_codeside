## 8.1 No Null, No Ignored Errors

C signals "nothing" with `NULL` or `-1` and failure with a status code that is easy to ignore. Rust encodes both in the type, and the compiler warns when you drop a `Result`.

| Concept | C | Rust |
|---|---|---|
| Maybe a value | Pointer that may be `NULL`; magic value | `Option<T>` = `Some(T)` or `None` |
| Success or failure | `HAL_StatusTypeDef`, `errno` | `Result<T, E>` = `Ok(T)` or `Err(E)` |

```rust Option
fn find_start(buf: &[u8]) -> Option<usize> {
    buf.iter().position(|&b| b == 0x7E)
}

match find_start(&rx) {
    Some(i) => process(&rx[i..]),
    None => { /* no frame start yet */ }
}

let idx = find_start(&rx).unwrap_or(0);          // default
if let Some(i) = find_start(&rx) { /* ... */ }  // only the case you care about
```

## 8.2 Result and the `?` Operator

```rust Defining an error type
#[derive(Debug)]
enum SensorError<E> {
    Bus(E),            // the I2C error from the HAL
    WrongChipId(u8),   // device answered, but it is not what we expected
    Timeout,
}

impl<E> From<E> for SensorError<E> {
    fn from(e: E) -> Self { SensorError::Bus(e) }
}
```

```rust Propagating with ?
fn read_temperature<I: embedded_hal::i2c::I2c>(i2c: &mut I) -> Result<i16, SensorError<I::Error>> {
    let mut id = [0u8];
    i2c.write_read(0x76, &[0xD0], &mut id)?;          // `?` returns early on Err
    if id[0] != 0x60 { return Err(SensorError::WrongChipId(id[0])); }
    let mut raw = [0u8; 3];
    i2c.write_read(0x76, &[0xFA], &mut raw)?;
    Ok(((raw[0] as i16) << 4) | (raw[1] as i16 >> 4))
}
```

The `?` replaces the ladder of `if (status != HAL_OK) return status;` you wrote in C - and unlike C you cannot forget it, because an unused `Result` is a warning (and an error if you set `#![deny(unused_must_use)]`).

## 8.3 Handling the Error Is a Design Decision

| Strategy | Use when | Example |
|---|---|---|
| Retry | Transient fault | Re-read after an I2C NACK, up to 3 times |
| Fall back | Degraded mode is acceptable | Use last good reading, raise a warning flag |
| Report | Caller can decide | Return `Err` up to the supervisor |
| Reset | State is unknowable | Let the watchdog reboot into a safe state |
| Panic | Programmer error: the invariant must hold | Index known to be in range |

```rust Policy in one place
match read_temperature(&mut i2c) {
    Ok(t) => { last_good = t; errors = 0; }
    Err(_) if errors < 3 => errors += 1,           // tolerate brief glitches
    Err(e) => { defmt::error!("sensor lost"); enter_safe_state(); }
}
```

## 8.4 `unwrap`, `expect` and Panics

`unwrap()` on `None`/`Err` **panics**. On a PC that prints a message; on a microcontroller it calls your **panic handler**. Choose it deliberately:

| Crate | Behaviour |
|---|---|
| `panic-halt` | Infinite loop - simplest, silent |
| `panic-probe` | Prints the panic message through the probe (with `defmt`) then breaks - ideal in development |
| `panic-reset` | Resets the chip - appropriate for production, together with a logged reason |
| Custom | Put outputs in a safe state, save the message in backup SRAM, then reset |

> [warn] unwrap in production | `unwrap()` is fine in examples and for startup invariants (e.g. `Peripherals::take().unwrap()`). Inside steady-state code every `unwrap` is a possible field reset. Search your code for `unwrap` and `expect` before release and justify each one.

## 8.5 Combinators

```rust Chains instead of nested ifs
let mv = adc.read(&mut pin).ok()                  // Result -> Option
    .map(|raw| (raw as u32 * 3300 / 4095) as u16)
    .filter(|&v| v > 50)                          // reject floor noise
    .unwrap_or(0);
```

Combinators such as `map`, `and_then`, `ok_or`, `map_err` keep error handling short without hiding it.
