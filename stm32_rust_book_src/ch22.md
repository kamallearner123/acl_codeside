## 22.1 Why Rust Firmware Is Easier to Test

In C, logic and hardware access are usually tangled. Rust's traits push you toward separating them, so most of your code can be tested on your PC in milliseconds, without a board.

| Level | Where it runs | What it tests |
|---|---|---|
| Unit tests | Host (`cargo test`) | Pure logic: parsers, filters, state machines |
| Mocked-HAL tests | Host | Drivers against fake I2C/SPI/GPIO |
| On-target tests | Board (`defmt-test`) | Real peripherals, timing |
| Hardware-in-the-loop | Board plus rig | Full system behaviour |

## 22.2 Host-Testable Crates

Put logic in a library crate that is `no_std` only when not testing:

```rust lib.rs of the logic crate
#![cfg_attr(not(test), no_std)]

pub fn fan_percent(temp_dc: i32) -> u8 {
    match temp_dc {
        t if t <= 250 => 0,
        t if t >= 450 => 100,
        t => (((t - 250) * 100) / 200) as u8,
    }
}

#[cfg(test)]
mod tests {
    use super::*;

    #[test] fn off_below_25c()   { assert_eq!(fan_percent(200), 0); }
    #[test] fn full_above_45c()  { assert_eq!(fan_percent(500), 100); }
    #[test] fn linear_midpoint() { assert_eq!(fan_percent(350), 50); }
}
```

Run with `cargo test` in that crate. Because the app crate targets `thumbv7em-none-eabihf`, keep logic in a **separate workspace crate** so the host target applies.

## 22.3 Mocking the Hardware

`embedded-hal-mock` provides fake buses with scripted expectations:

```rust Testing the BME280 driver
use embedded_hal_mock::eh1::i2c::{Mock, Transaction};

#[test]
fn rejects_wrong_chip_id() {
    let expectations = [Transaction::write_read(0x76, vec![0xD0], vec![0x58])];   // 0x58 = BMP280
    let i2c = Mock::new(&expectations);
    let r = Bme280::new(i2c, 0x76);
    assert!(matches!(r, Err(Error::WrongChip(0x58))));
}
```

The test fails if the driver performs a different transaction than expected - it verifies the exact bus protocol.

## 22.4 On-Target Tests with `defmt-test`

```rust Running tests on the MCU
#[defmt_test::tests]
mod tests {
    #[test]
    fn timer_ticks_at_1khz() {
        // configure timer, wait 100 ms, assert tick count is 100 +- 1
    }
}
```

`cargo test` with `probe-rs` as runner flashes the board, runs each test and reports pass or fail over RTT. Use these only for what a host cannot check: clock configuration, interrupts, DMA.

## 22.5 Property and Edge Testing

Many embedded bugs hide at boundaries. Test them deliberately:

- 0 and maximum values (`u16::MAX`, `i16::MIN`).
- Empty and oversized buffers.
- Counter wrap-around (`u32::MAX` to 0).
- Malformed frames: short, long, wrong checksum.

## 22.6 Continuous Integration

A minimum useful pipeline, run on every push:

1. `cargo fmt --check`
2. `cargo clippy --all-targets -- -D warnings`
3. `cargo test` in the logic crates
4. `cargo build --release --target thumbv7em-none-eabihf`
5. `cargo size` and a check that flash usage stays under a budget

Optionally add a self-hosted runner with a board attached for hardware-in-the-loop tests.
