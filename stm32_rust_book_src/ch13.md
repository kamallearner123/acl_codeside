## 13.1 Your First Rust Firmware: Blink

Everything so far leads to this: a `no_std` program that blinks LD2 (PA5) on the NUCLEO-F446RE.

```rust src/main.rs - blinky
#![no_std]
#![no_main]

use cortex_m_rt::entry;
use defmt_rtt as _;
use panic_probe as _;
use stm32f4xx_hal::{pac, prelude::*};

#[entry]
fn main() -> ! {
    let dp = pac::Peripherals::take().unwrap();

    let rcc = dp.RCC.constrain();
    let clocks = rcc.cfgr.sysclk(84.MHz()).freeze();

    let gpioa = dp.GPIOA.split();
    let mut led = gpioa.pa5.into_push_pull_output();

    let mut delay = dp.TIM5.delay_us(&clocks);

    loop {
        led.toggle();
        delay.delay_ms(500u32);
        defmt::info!("tick");
    }
}
```

Walk through it using what you learned:

| Line | Concept |
|---|---|
| `Peripherals::take().unwrap()` | Ownership: the singleton can be claimed once (chapter 3) |
| `dp.RCC.constrain()` | `RCC` is moved into a typed clock configurator |
| `.freeze()` | Locks in the clock tree and returns a `Clocks` value that proves "clocks are configured" |
| `gpioa.pa5.into_push_pull_output()` | Type-state: PA5 is now an output pin (chapter 6) |
| `dp.TIM5.delay_us(&clocks)` | A timer takes ownership as a delay source; needs `&clocks` to know the frequency |

> [hw] Compare with CubeMX | Book 1 used CubeMX to generate `SystemClock_Config()` and `MX_GPIO_Init()`. Here the clock and pin setup is **ordinary code in 10 lines**, checked by the type system. There is no generator and no "user code begin" region to protect.

## 13.2 Reading a Button

```rust Button on PC13 (active low)
let gpioc = dp.GPIOC.split();
let button = gpioc.pc13.into_pull_up_input();     // B1 has an external pull-up; this is harmless
let mut led = gpioa.pa5.into_push_pull_output();

loop {
    if button.is_low() {      // pressed
        led.set_high();
    } else {
        led.set_low();
    }
}
```

`is_low()` and `is_high()` come from the `embedded-hal` `InputPin` trait; `set_high()` and `toggle()` from `OutputPin`/`StatefulOutputPin`. In embedded-hal 1.0 these return a `Result`, but on STM32 GPIO the error type is `Infallible`, so the HAL provides infallible wrappers.

## 13.3 Pin Modes Are Types

| C (HAL) | Rust method | Resulting type |
|---|---|---|
| `GPIO_MODE_OUTPUT_PP` | `into_push_pull_output()` | `Pin<'A', 5, Output>` |
| `GPIO_MODE_OUTPUT_OD` | `into_open_drain_output()` | `Pin<.., OutputOpenDrain>` |
| `GPIO_MODE_INPUT` + pull-up | `into_pull_up_input()` | `Pin<.., Input>` |
| `GPIO_MODE_AF_PP` | `into_alternate::<AF>()` | `Pin<.., Alternate<AF>>` |
| `GPIO_MODE_ANALOG` | `into_analog()` | `Pin<.., Analog>` |

The mode conversion consumes the old pin and returns a new one. You cannot hold a pin in two modes at once, and you cannot use an `Alternate` pin to read a level.

```rust Output speed and initial level
let mut cs = gpioa.pa4
    .into_push_pull_output_in_state(PinState::High)   // idle high BEFORE it becomes an output
    .speed(Speed::VeryHigh);
```

This is the Rust form of the tip from Book 1: set the initial level before switching to output so relays and chip-selects do not glitch.

## 13.4 PAC vs HAL

You can bypass the HAL and use register access from the PAC - for example to set a bit that the HAL does not expose:

```rust Raw register through the PAC (dp.GPIOA not yet split)
dp.GPIOA.bsrr.write(|w| w.bs5().set_bit());      // set PA5 - atomic BSRR write
let level = dp.GPIOA.idr.read().idr5().bit_is_set();
```

The closures give you **named fields** instead of magic masks: `w.bs5()` is bit 5 of BSRR, and the compiler checks the field exists. The PAC wraps the volatile access, so this needs no `unsafe`. After `GPIOA.split()` the register block is owned by the HAL; use the PAC only for peripherals you have not handed to it.

## 13.5 Splitting Pins Across Modules

Because ownership is explicit you can hand individual pins to the code that needs them:

```rust Ownership through function arguments
fn run_traffic_light(
    mut red: impl OutputPin, mut yellow: impl OutputPin, mut green: impl OutputPin,
    mut delay: impl DelayNs,
) -> ! { /* ... */ loop {} }

run_traffic_light(
    gpiob.pb0.into_push_pull_output(),
    gpiob.pb1.into_push_pull_output(),
    gpiob.pb2.into_push_pull_output(),
    delay,
);
```

`run_traffic_light` knows nothing about STM32 - it works with any pins that implement `OutputPin` - and nobody else can touch PB0-PB2 afterwards.
