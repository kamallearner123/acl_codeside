## 25.1 From Programs to Products

A blinking LED fits in `main.rs`. A product needs boundaries: who owns which peripheral, how modules communicate, and what happens when something fails.

## 25.2 Workspace Layout

```text Cargo workspace
firmware/
  Cargo.toml              # [workspace]
  app/                    # binary: wires everything together, #![no_main]
  bsp/                    # board support: pins, clocks, peripheral setup
  drivers/
    tmp102/               # reusable, generic over embedded-hal
    fan/                  # PWM wrapper with Percent type
  logic/                  # pure no_std crate: control law, state machine, protocol
  tests-host/             # integration tests that run on a PC
```

Dependencies flow **downward**: `app` depends on everything, `logic` depends on nothing hardware-related. The compiler enforces the architecture - `logic` literally cannot call a HAL function.

## 25.3 Choosing a Concurrency Model

| Model | Strength | Use when |
|---|---|---|
| Super-loop plus ISR flags | Simplest | Small devices, few activities |
| **RTIC** | Priority-based, compile-time race freedom, tiny overhead | Real-time control, deterministic latency |
| **Embassy** | `async`/`await`, many tasks, rich drivers | Connectivity, many concurrent I/O tasks |
| RTOS (FreeRTOS, Zephyr) | Mature ecosystem and tools | Existing RTOS codebase or certification |

```rust Embassy-style tasks
#[embassy_executor::task]
async fn sensor_task(mut i2c: I2c<'static>, tx: Sender<'static, NoopRawMutex, Reading, 4>) {
    let mut ticker = Ticker::every(Duration::from_millis(500));
    loop {
        if let Ok(t) = read_temp(&mut i2c).await { tx.send(Reading(t)).await; }
        ticker.next().await;
    }
}
```

Each task owns its peripheral; tasks communicate over **channels**, so no shared mutable state exists.

## 25.4 Message Passing Over Shared State

| Instead of | Prefer |
|---|---|
| Global `temperature` variable | A channel carrying `Reading` values |
| Global `fan_target` | A `Signal` or watch containing the latest target |
| Flags polled everywhere | A typed `enum Event` handled in one place |

## 25.5 State Machines

Model device behaviour as an enum and one transition function:

```rust State machine in the logic crate
#[derive(Clone, Copy, PartialEq)]
pub enum State { Init, Running, Degraded, Fault }

pub enum Event { SensorOk(i16), SensorFailed, Reset }

pub fn step(s: State, e: &Event, fails: &mut u8) -> State {
    match (s, e) {
        (State::Fault, Event::Reset) => { *fails = 0; State::Init }
        (State::Fault, _) => State::Fault,
        (_, Event::SensorOk(_)) => { *fails = 0; State::Running }
        (_, Event::SensorFailed) => {
            *fails = fails.saturating_add(1);
            if *fails >= 5 { State::Fault } else { State::Degraded }
        }
        (s, Event::Reset) => s,
    }
}
```

The compiler warns if you forget a state or event, and the whole machine is unit-testable.

## 25.6 Reliability Features

- **Watchdog**: enable the independent watchdog (IWDG); feed it only when all critical tasks have reported alive.
- **Panic policy**: development uses `panic-probe`; production logs a reason code to backup registers and resets.
- **Fail-safe outputs**: define the safe state for each actuator (fan on full, heater off) and apply it on fault.
- **Bounded everything**: queues, strings and retry counts have fixed maximum sizes (`heapless`).
- **Versioned configuration**: store settings with a version and checksum in flash.

## 25.7 Memory Budget

Track flash and RAM per release with `cargo size --release` and `cargo bloat`. Set a budget (for example 70 percent of flash) in CI so regressions are caught early.
