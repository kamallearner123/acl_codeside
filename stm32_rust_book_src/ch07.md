## 7.1 Traits: Shared Behaviour

A **trait** is an interface: a set of methods a type promises to implement. You have used the C version - a struct of function pointers - but traits are resolved at compile time and can be fully inlined.

```rust Defining and implementing a trait
trait Sensor {
    type Error;
    fn read_mv(&mut self) -> Result<u16, Self::Error>;
}

struct Potentiometer { /* adc, pin */ }
impl Sensor for Potentiometer {
    type Error = core::convert::Infallible;
    fn read_mv(&mut self) -> Result<u16, Self::Error> { Ok(1650) }
}
```

## 7.2 Generics and Monomorphization

```rust A function generic over any sensor
fn log_reading<S: Sensor>(s: &mut S) -> Option<u16> {
    s.read_mv().ok()
}
```

The compiler generates a separate, specialised copy of `log_reading` for each concrete `S` (**monomorphization**). No function pointer, no virtual call: it is as fast as a hand-written version. The price is flash size if you instantiate it for many types.

| Dispatch | Syntax | Speed | Flash |
|---|---|---|---|
| Static | `fn f<T: Trait>(t: T)` / `impl Trait` | Fastest, inlinable | One copy per type |
| Dynamic | `&mut dyn Trait` | Indirect call | One copy; needs a vtable |

On Cortex-M prefer generics; use `dyn` when you need a heterogeneous collection or want to cut code size.

## 7.3 `embedded-hal`: The Trait Library for Hardware

`embedded-hal` 1.0 defines traits such as `OutputPin`, `InputPin`, `I2c`, `SpiDevice`, `DelayNs`. Any HAL (STM32, nRF, RP2040...) implements them; any driver crate is written against them.

```rust A driver written once, usable on every chip
use embedded_hal::digital::OutputPin;

struct StatusLed<P: OutputPin> { pin: P, on: bool }

impl<P: OutputPin> StatusLed<P> {
    fn new(pin: P) -> Self { Self { pin, on: false } }
    fn toggle(&mut self) -> Result<(), P::Error> {
        self.on = !self.on;
        if self.on { self.pin.set_high() } else { self.pin.set_low() }
    }
}

// On STM32:
let mut led = StatusLed::new(gpioa.pa5.into_push_pull_output());
```

This is the key idea behind the Rust embedded driver ecosystem: **one driver for a BME280 works on any microcontroller**, because it only needs "something that implements `I2c`".

## 7.4 Trait Bounds as Documentation

```rust Bounds say what the driver needs
fn init_display<SPI, DC, RST, D>(spi: SPI, dc: DC, rst: RST, delay: &mut D)
where
    SPI: embedded_hal::spi::SpiDevice,
    DC: embedded_hal::digital::OutputPin,
    RST: embedded_hal::digital::OutputPin,
    D: embedded_hal::delay::DelayNs,
{ /* ... */ }
```

Reading the `where` clause tells you the hardware requirements without opening the source - and prevents passing the wrong kind of object.

## 7.5 Mocking for Tests

Because drivers depend on traits, you can substitute a fake in tests:

```rust A fake pin for host tests
#[derive(Default)]
struct FakePin { history: Vec<bool> }
impl embedded_hal::digital::ErrorType for FakePin { type Error = core::convert::Infallible; }
impl embedded_hal::digital::OutputPin for FakePin {
    fn set_low(&mut self) -> Result<(), Self::Error> { self.history.push(false); Ok(()) }
    fn set_high(&mut self) -> Result<(), Self::Error> { self.history.push(true); Ok(()) }
}

#[test]
fn toggles() {
    let mut led = StatusLed::new(FakePin::default());
    led.toggle().unwrap(); led.toggle().unwrap();
    assert_eq!(led.pin.history, vec![true, false]);
}
```

The crate `embedded-hal-mock` provides ready-made fakes for I2C, SPI and GPIO with expected-transaction checking (chapter 22).
