## 1.1 Where C Firmware Actually Breaks

If you finished the STM32 + C course you can already build working firmware. The bugs that remain in shipped C products are rarely about registers - they are about **memory and state**:

| C failure | Typical symptom in the field |
|---|---|
| Pointer outlives its data (dangling pointer to a stack buffer) | Random corruption, works in Debug, fails in Release |
| Buffer index out of bounds | Silent overwrite of a neighbouring variable; HardFault much later |
| Shared mutable state between `main` and an ISR | Torn reads, lost updates, impossible-to-reproduce glitches |
| Unchecked return value (`HAL_I2C_Master_Transmit` ignored) | Device appears to work until the bus has a bad day |
| Use of an uninitialised variable | Different behaviour at every power-up |
| Two pieces of code configure the same peripheral | Last writer wins; nobody knows who |

These are **classes** of bug. Rust's goal is to make the whole class impossible to compile rather than hard to find.

## 1.2 What Rust Changes

| C habit | Rust mechanism | Chapter |
|---|---|---|
| "Who frees this?" convention | **Ownership** - exactly one owner, freed automatically | 3 |
| Passing pointers around | **Borrowing** - shared `&T` or exclusive `&mut T`, checked at compile time | 4 |
| Dangling pointers | **Lifetimes** - a reference cannot outlive its data | 5 |
| `#define` flags and magic ints | **Enums and structs** that carry meaning | 6 |
| Function pointers and macros | **Traits and generics** with zero run-time cost | 7 |
| `-1` / `NULL` / ignored status codes | **`Option` and `Result`** that must be handled | 8 |
| Global peripherals everywhere | **Singleton peripherals** you must own to use | 13 |
| Volatile flag shared with ISR | **Critical sections and `Mutex`** | 14 |

```rust The same bug in C-thinking and Rust
fn longest_reading() -> &i32 {   // does not compile
    let readings = [10, 42, 7];
    &readings[1]                  // reference to a local that dies here
}
```

The C equivalent `int *f(void) { int a[3]={10,42,7}; return &a[1]; }` compiles (perhaps with a warning) and fails at run time. Rust refuses to build it. That one compile error is the entire pitch.

## 1.3 What Rust Does Not Change

> [warn] Rust is not magic | Wrong clock settings, a missing pull-up, a mistimed I2C transaction or a bad CAN bit rate are **hardware** problems. Rust will happily compile them. You still need the reference manual, a logic analyzer and the debugging discipline from Book 1.

- The same silicon: Cortex-M4F, same registers, same peripherals, same datasheet.
- The same performance model. Rust generates code comparable to optimised C; there is no garbage collector and no runtime.
- The same toolchain ideas: compile, link with a linker script, flash over SWD.
- `unsafe` still exists - you will meet it at the hardware boundary, but it is **small, visible and reviewable**.

## 1.4 The Embedded Rust Ecosystem Map

| Layer | Crate | Role |
|---|---|---|
| Core support | `cortex-m`, `cortex-m-rt` | Intrinsics, vector table, start-up code (replaces `startup_stm32f446xx.s`) |
| PAC | `stm32f4` (e.g. `stm32f4::stm32f446`) | Register access generated from the vendor SVD file |
| HAL | `stm32f4xx-hal` | Safe, typed peripherals: GPIO, timers, UART, I2C, SPI, ADC |
| Traits | `embedded-hal` 1.0 | Hardware-independent interfaces for drivers |
| Concurrency | RTIC or Embassy | Interrupt-driven task frameworks |
| Tooling | `probe-rs`, `defmt`, `cargo` | Flash, debug, logging, build |

Compare with Book 1: the **PAC** is like CMSIS register headers, the **HAL crate** is like STM32 HAL - but it expresses pin modes and ownership in the type system.

## 1.5 When to Choose Rust, When to Stay with C

| Choose Rust when | Stay with C when |
|---|---|
| Safety, security or long maintenance life matters | A vendor middleware stack (e.g. a certified protocol stack) is mandatory |
| The team will own the code for years | The product is a tiny one-off with a deadline next week |
| Concurrency (ISRs, DMA, tasks) is non-trivial | The team has no time to learn - then plan the learning first |
| You want host-side unit tests of firmware logic | The chip has no usable Rust support |

Mixed projects are normal: Rust can call C and C can call Rust through `extern "C"`.
