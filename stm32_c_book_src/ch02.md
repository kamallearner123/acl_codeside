## 2.1 The ST Software Stack

ST provides several layers. Knowing which one is which prevents a lot of confusion:

| Layer | What it is | Use it when |
|---|---|---|
| **CMSIS** | ARM core headers + ST device header (`stm32f4xx.h`) with register structs | Register-level code, always present |
| **HAL** (Hardware Abstraction Layer) | Portable C API: `HAL_GPIO_WritePin`, `HAL_UART_Transmit` | Most application work; quick, portable across families |
| **LL** (Low-Layer) | Thin, fast, header-style register helpers | Timing-critical paths, small code size |
| **STM32CubeMX** | GUI that configures pins, clocks, peripherals and **generates** init code | Start of every project |
| **STM32CubeIDE** | Eclipse-based IDE: editor, GCC toolchain, debugger, CubeMX built in | Daily development |

This book uses **HAL generated by CubeMX** for most examples, and drops to registers or LL where it teaches something.

## 2.2 Creating a Project in STM32CubeIDE

1. *File → New → STM32 Project*, pick the **Board Selector** tab and choose **NUCLEO-F446RE**.
2. Name the project, keep **C** as language and **Executable** as type.
3. Answer **Yes** to "Initialize all peripherals with their default mode" - this configures LD2, B1 and USART2 for you.
4. CubeIDE opens the `.ioc` file - the CubeMX configurator.

The `.ioc` file is the single source of truth for hardware configuration. Commit it to version control; the generated C code can always be regenerated from it.

## 2.3 CubeMX: Pinout, Clock Tree and Peripherals

The configurator has four tabs worth knowing:

- **Pinout & Configuration** - click a pin and pick its function (e.g. `PA6 → TIM3_CH1`). Peripherals are enabled in the left tree. Conflicts show in orange/red.
- **Clock Configuration** - the clock tree. Choose HSE (bypass) or HSI, set the PLL and see APB1/APB2 frequencies. Setting HCLK to 180 MHz is a one-line entry.
- **Project Manager** - project name, toolchain, **Code Generator** options, heap/stack size.
- **Power Consumption Calculator** - optional estimates for battery designs.

> [hw] Clock for the F446RE Nucleo | Set **RCC → High Speed Clock (HSE) = BYPASS Clock Source**, then in the Clock Configuration tab select HSE as PLL source, enter `180` in HCLK and let CubeMX solve the dividers. Verify APB1 = 45 MHz and APB2 = 90 MHz.

### Recommended code-generator options

- *Generate peripheral initialization as a pair of .c/.h files per peripheral* - keeps `main.c` readable.
- *Keep user code when re-generating* - **must be ticked** (it is by default).
- *Delete previously generated files when not re-generated* - keeps the tree clean when you disable a peripheral.

## 2.4 Anatomy of the Generated Project

```text Project tree
Core/
  Inc/    main.h  gpio.h  usart.h  stm32f4xx_hal_conf.h  stm32f4xx_it.h
  Src/    main.c  gpio.c  usart.c  stm32f4xx_it.c  stm32f4xx_hal_msp.c
          system_stm32f4xx.c  syscalls.c  sysmem.c
Drivers/
  CMSIS/  device and core headers
  STM32F4xx_HAL_Driver/   the HAL source
Startup/  startup_stm32f446retx.s
STM32F446RETX_FLASH.ld    linker script
firmware.ioc              CubeMX configuration
```

The key files:

- **main.c** - `main()` calls `HAL_Init()`, `SystemClock_Config()`, the `MX_xxx_Init()` functions, then your loop.
- **stm32f4xx_it.c** - interrupt handlers (`SysTick_Handler`, `EXTI15_10_IRQHandler`, ...). Most just call the matching HAL handler.
- **stm32f4xx_hal_msp.c** and `xxx.c` - MSP = MCU Support Package: enables peripheral clocks and configures GPIO alternate functions for each peripheral.
- **stm32f4xx_hal_conf.h** - which HAL modules are compiled in.

```c Generated main() - simplified
int main(void)
{
  /* USER CODE BEGIN 1 */
  /* USER CODE END 1 */

  HAL_Init();                 /* Flash prefetch, SysTick 1 ms, NVIC grouping */
  SystemClock_Config();       /* the clock tree you drew in CubeMX            */

  MX_GPIO_Init();             /* pins                                         */
  MX_USART2_UART_Init();      /* peripherals                                  */

  /* USER CODE BEGIN 2 */
  /* USER CODE END 2 */

  while (1)
  {
    /* USER CODE BEGIN 3 */
    /* USER CODE END 3 */
  }
}
```

## 2.5 The USER CODE Rule

CubeMX regenerates the files every time you save the `.ioc`. Anything **outside** the `USER CODE BEGIN/END` markers is overwritten.

```c Right and wrong places for your code
/* WRONG: this line vanishes the next time the .ioc is saved */
HAL_UART_Transmit(&huart2, (uint8_t *)"hi\r\n", 4, 100);
MX_USART2_UART_Init();

/* RIGHT: inside a USER CODE section */
/* USER CODE BEGIN 2 */
HAL_UART_Transmit(&huart2, (uint8_t *)"hi\r\n", 4, 100);
/* USER CODE END 2 */
```

> [warn] Do not edit generated lines | If you must change generated behaviour, change it in the `.ioc` file. Editing outside user sections works - until you next touch CubeMX, and then your work silently disappears.

### Good habits for larger projects

Keep your own logic out of `main.c`. Create `app.c`/`app.h` (or one pair per feature, such as `sensor.c`, `console.c`) and call into them from user sections: `app_init();` in `USER CODE 2` and `app_poll();` in `USER CODE 3`. Your code stays testable, and the generated files stay boring.

## 2.6 HAL Conventions You Will See Everywhere

| Convention | Example | Meaning |
|---|---|---|
| Handle structs | `UART_HandleTypeDef huart2;` | Holds peripheral instance, config and state |
| Return type | `HAL_StatusTypeDef` | `HAL_OK`, `HAL_ERROR`, `HAL_BUSY`, `HAL_TIMEOUT` |
| Blocking calls | `HAL_UART_Transmit(&h, buf, n, timeout)` | Wait until done or timeout (ms) |
| Interrupt calls | `HAL_UART_Receive_IT(...)` | Return immediately, callback when finished |
| DMA calls | `HAL_UART_Receive_DMA(...)` | Hardware moves data, callback on completion |
| Callbacks | `HAL_UART_RxCpltCallback()` | `__weak` functions you override in your own code |
| Time base | `HAL_GetTick()`, `HAL_Delay(ms)` | 1 ms SysTick counter |

```c Checking HAL return codes
HAL_StatusTypeDef st = HAL_I2C_IsDeviceReady(&hi2c1, 0x76 << 1, 3, 100);
if (st != HAL_OK) {
    Error_Handler();          /* or log and recover - never ignore errors */
}
```

## 2.7 Build, Flash and Run

- **Build:** hammer icon (Ctrl+B). Check the Console for `0 errors`, and the Build Analyzer for memory.
- **Run/Debug:** green bug icon (F11) creates a debug configuration that uses the on-board ST-LINK, flashes the ELF and halts at `main()`. Press F8 to resume.
- **Flash only:** use *Run As → STM32 C/C++ Application*, or STM32CubeProgrammer with the `.elf`/`.bin`.

> [tip] Optimisation levels | The *Debug* build configuration uses `-Og`/`-O0` so variables are inspectable. The *Release* configuration uses `-Os`. Switch to Release to measure real code size and speed, but debug with Debug.

## 2.8 Hands-On Lab 2: First CubeMX Project

```c Lab 2 - heartbeat and greeting in USER CODE sections
/* USER CODE BEGIN Includes */
#include <string.h>
#include <stdio.h>
/* USER CODE END Includes */

/* ... inside main(), in USER CODE BEGIN 2 ... */
const char *hello = "STM32F446RE ready\r\n";
HAL_UART_Transmit(&huart2, (uint8_t *)hello, strlen(hello), HAL_MAX_DELAY);

/* ... inside while(1), in USER CODE BEGIN 3 ... */
HAL_GPIO_TogglePin(LD2_GPIO_Port, LD2_Pin);
HAL_Delay(500);
```

Q: Where must your own code be placed in generated files?
- Anywhere, CubeMX merges it | Incorrect. It overwrites everything outside markers.
+ Between USER CODE BEGIN and USER CODE END markers | Correct! Only these regions are preserved on regeneration.
- Only in the `.ioc` file | Incorrect. The `.ioc` is configuration, not C code.
- Only in the Drivers folder | Incorrect. Those are vendor files.
Q: Which file is the single source of truth for the hardware configuration?
- `main.c` | Incorrect. It is generated from the .ioc.
+ The `.ioc` file | Correct! Everything else can be regenerated from it.
- `startup_stm32f446retx.s` | Incorrect.
- `stm32f4xx_hal_conf.h` | Incorrect. It only selects HAL modules.
Q: What does `HAL_UART_Receive_IT()` do?
- Blocks until the buffer is full | Incorrect. That is `HAL_UART_Receive()`.
+ Starts reception and returns immediately; a callback is called when done | Correct!
- Uses DMA | Incorrect. That is `_DMA`.
- Sends data | Incorrect.
