Chapter 08 • Debugging

ST-LINK, SWD, GDB, Logic Analyzer & Fault Diagnosis

Stop guessing. Understand the ST-LINK and SWD link, drive GDB from the command line, watch buses with a logic analyzer, and decode HardFaults register by register.

⏱️ Reading Time: 60 minutes
🛠️ Lab: Debug the broken firmware
🎯 Topics: ST-LINK, SWD, GDB, Faults

8.1 The Debug Chain: ST-LINK and SWD

Every Nucleo board carries an ST-LINK/V2-1 probe. It is a second small MCU that talks USB to your PC and SWD (Serial Wire Debug) to the target STM32. It also provides the Virtual COM Port (USART2) and a mass-storage drag-and-drop programmer.

Signal Pin (F446) Purpose
SWDIO PA13 Bidirectional data
SWCLK PA14 Clock from the probe
SWO PB3 Optional trace output (printf over ITM)
NRST NRST Reset line, needed for "connect under reset"
GND / VDD - Reference and target voltage sense
Do not repurpose PA13/PA14
If CubeMX or your code reconfigures PA13/PA14 as GPIO, the debugger loses the chip. Recover with Connect under reset in STM32CubeProgrammer (hold NRST, then connect).

SWD uses only two wires and gives you: halt/run/step, read and write memory and registers, flash programming, hardware breakpoints (6 on Cortex-M4 FPB) and watchpoints (4 on the DWT unit).

Debug configuration in CubeIDE

  1. Run Debug As > STM32 C/C++ Application once; CubeIDE creates a launch configuration.
  2. In Debugger select *ST-LINK (ST-LINK GDB server)*, interface SWD, and enable SWV if you want ITM printf.
  3. Set the core clock in the SWV settings to your real SYSCLK (e.g. 180 MHz) or the trace timestamps will be wrong.
C Retarget printf to ITM (SWO) 
#include <stdio.h>

int _write(int fd, char *ptr, int len)
{
    (void)fd;
    for (int i = 0; i < len; i++) {
        ITM_SendChar((uint32_t)ptr[i]);
    }
    return len;
}

8.2 GDB from the Command Line

CubeIDE drives GDB for you, but knowing the raw tools makes you independent of any IDE. With OpenOCD as the GDB server:

BASH Start OpenOCD and GDB 
# Terminal 1 - GDB server
openocd -f interface/stlink.cfg -f target/stm32f4x.cfg

# Terminal 2 - client
arm-none-eabi-gdb build/app.elf
(gdb) target extended-remote :3333
(gdb) monitor reset halt
(gdb) load
(gdb) break main
(gdb) continue
Command Meaning
break file.c:42 / tbreak fn Breakpoint / one-shot breakpoint
watch counter Stop when the variable changes (uses a DWT comparator)
rwatch / awatch Stop on read / on any access
info registers Core registers (pc, lr, sp, xpsr)
x/8wx 0x40020014 Examine 8 words of memory - peripheral registers included
p/x GPIOA->ODR Print a peripheral register using SVD-aware symbols
bt Backtrace of the current call stack
finish / step / next Run to return / step in / step over
monitor reset halt Reset the target and stop at the first instruction
GDB Conditional breakpoint and commands 
(gdb) break sensor_read if channel == 3
(gdb) commands
> silent
> printf "ch=%d raw=%d\n", channel, raw
> continue
> end
Optimisation and debugging
Build the Debug configuration with -Og -g3. With -O2 variables are optimised away ("value optimised out") and stepping jumps around. Only switch to Release for final timing tests.

Reading peripherals without code

x/wx on a register address is the quickest hardware check. For example, to confirm that PA5 is an output: x/wx 0x40020000 returns GPIOA->MODER; bits 11:10 must equal 01.

8.3 Watching the Wires: Logic Analyzer

A debugger shows what the CPU believes. A logic analyzer shows what the pins really do. Use it for every bus bring-up.

  1. Connect the analyzer GND to the board GND first, then probes to the signals.
  2. In PulseView/sigrok pick the sample rate at least 4x (preferably 10x) the signal frequency.
  3. Set a trigger (e.g. falling edge on CS or I2C start condition).
  4. Add a protocol decoder: I2C, SPI, UART, CAN (via a transceiver RXD pin).
Symptom on the analyzer Likely cause
I2C: address followed by NACK Wrong 7-bit address (shifted by one bit), device unpowered
I2C: slow rising edges Pull-ups too weak or bus capacitance too high
SPI: data shifted by one bit Wrong CPOL/CPHA mode
UART: framing errors Baud rate mismatch (check clock tree) or wrong stop bits
PWM: wrong period PSC/ARR computed from the wrong timer clock
CAN: no ACK bit No other node on the bus or missing termination
Toggle a spare pin as a timing probe
Set a GPIO high at the start of a function and low at the end. The analyzer then shows the exact execution time and jitter without any debugger intrusion. This is the cheapest profiler you will ever have.

8.4 Fault Diagnosis: Decoding a HardFault

When the core executes something illegal it raises a fault. On Cortex-M4 there are four: HardFault, MemManage, BusFault and UsageFault. If the specific ones are not enabled they escalate to HardFault.

Common cause Typical fault bit
NULL or wild pointer dereference BFSR.PRECISERR / IACCVIOL
Stack overflow Often STKERR or a corrupted return address
Unaligned access with UNALIGN_TRP UNALIGNED (UFSR)
Divide by zero (when trapped) DIVBYZERO (UFSR)
Executing data / bad function pointer INVSTATE or IACCVIOL
Accessing a peripheral with its clock disabled PRECISERR bus fault
C HardFault handler that captures the stack frame 
volatile struct {
    uint32_t r0, r1, r2, r3, r12, lr, pc, psr;
    uint32_t cfsr, hfsr, mmfar, bfar;
} g_fault;

void HardFault_Handler(void)
{
    __asm volatile(
        "tst lr, #4        \n"
        "ite eq            \n"
        "mrseq r0, msp     \n"
        "mrsne r0, psp     \n"
        "b hardfault_c     \n");
}

void hardfault_c(uint32_t *sp)
{
    g_fault.r0 = sp[0];  g_fault.r1 = sp[1];
    g_fault.r2 = sp[2];  g_fault.r3 = sp[3];
    g_fault.r12 = sp[4]; g_fault.lr = sp[5];
    g_fault.pc = sp[6];  g_fault.psr = sp[7];
    g_fault.cfsr  = SCB->CFSR;
    g_fault.hfsr  = SCB->HFSR;
    g_fault.mmfar = SCB->MMFAR;
    g_fault.bfar  = SCB->BFAR;
    __BKPT(0);                 /* halt here when a debugger is attached */
    for (;;) { }
}

The stacked PC is the address of the faulting instruction. Convert it to a source line:

BASH Find the faulting line 
arm-none-eabi-addr2line -e build/app.elf -f -p 0x080012A4
# -> sensor_read at ../Core/Src/sensor.c:57
Enable the detailed faults
In main() set SCB->SHCSR |= SCB_SHCSR_USGFAULTENA_Msk | SCB_SHCSR_BUSFAULTENA_Msk | SCB_SHCSR_MEMFAULTENA_Msk; and SCB->CCR |= SCB_CCR_DIV_0_TRP_Msk;. You then get the precise fault handlers rather than everything landing in HardFault.

Stack overflow detection

  • Fill the stack with a known pattern (0xDEADBEEF) at start-up and check the high-water mark periodically.
  • Place the stack at the bottom of RAM so an overflow hits a fault instead of silently corrupting globals.
  • Avoid large local arrays and deep recursion; keep ISRs lean.

A systematic method

  1. Reproduce - find the minimum steps that trigger the problem.
  2. Observe - debugger for the CPU view, logic analyzer for the pin view, UART log for the timeline.
  3. Hypothesise - one cause at a time; write it down.
  4. Test - change one thing, re-measure.
  5. Lock in - add an assert or a test so it cannot return silently.
