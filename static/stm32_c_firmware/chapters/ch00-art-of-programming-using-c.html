Art of Programming using C

Learn to write, build, inspect and debug portable C programs on Ubuntu Linux before moving on to STM32 firmware. Follow a source file through GCC, inspect its ELF executable, use GDB, and apply the same disciplined habits to embedded and automotive code.

⏱️ Reading Time: 75 minutes
🛠️ Lab: Build, inspect and debug a C program
🎯 Topics: C, GCC, ELF, GDB, Linux

0.1 The C Programmer's Toolkit

C is a small, compiled language that gives you direct control over data representation and resource use. On Ubuntu, GCC turns source code into Linux executables; the same core language skills transfer to cross-compilers and microcontrollers. Learn to reason about types, memory, interfaces and failures rather than relying on code that only happens to work on one machine.

Priority Topic Why it matters
Essential Source files, headers, functions and the compile/link process Lets you build programs larger than one file and understand build errors
Essential Types, expressions, control flow, functions and scope The everyday tools for expressing correct behavior
Essential Arrays, strings, pointers and const C APIs and data structures depend on understanding addresses and bounds
Essential struct, enum, bitwise operations and fixed-width integers Models protocols, registers, messages and state machines

A productive learning loop
Read a small piece of code, predict what it does, compile with warnings, run it, inspect it in GDB, then change one thing and repeat.

0.2 Set Up C on Ubuntu

Open a terminal and install the compiler toolchain and debugger:

BASH Install GCC, Make and GDB 
sudo apt update
sudo apt install build-essential gdb binutils
gcc --version
gdb --version
make --version

build-essential installs GCC, the C library development files, make and related tools. binutils supplies utilities such as readelf, objdump, nm and size. These commands build and inspect native programs for your Ubuntu computer; an STM32 needs a separate ARM cross-compiler such as arm-none-eabi-gcc.

Create a working directory and a source file:

BASH Create and build hello.c 
mkdir -p ~/c-labs/hello
cd ~/c-labs/hello
C hello.c 
#include <stdio.h>

int main(void)
{
    const char *name = "Ubuntu";
    printf("Hello, %s!\n", name);
    return 0;
}

Line by line:

  • #include <stdio.h> asks the preprocessor to make the standard input/output declarations, including printf, available.
  • The blank line separates the include from the program; it has no effect on compilation.
  • int main(void) defines the program entry point. It returns an integer status to the operating system and takes no arguments.
  • { begins the function body.
  • const char *name = "Ubuntu"; defines a pointer to a string literal. const prevents this code from modifying the literal through name.
  • printf("Hello, %s!\n", name); prints formatted text. %s expects a pointer to a null-terminated character string; \n ends the line.
  • return 0; reports successful completion to the operating system.
  • } ends the function body.

Build and run it:

BASH Compile and run hello.c 
gcc -std=c17 -Wall -Wextra -Wpedantic -g3 -O0 hello.c -o hello
./hello
echo $?

The expected output is Hello, Ubuntu!; the exit status printed by echo $? is 0. -o hello names the executable. If you omit it, GCC normally writes an executable named a.out.

0.3 What Happens When GCC Compiles C

The command gcc is a driver: it coordinates the preprocessor, compiler, assembler and linker. A normal build runs these stages in order:

Stage Input and work Typical output
Preprocessing Expands #include, macros and conditional compilation Preprocessed C source
Compilation Checks C syntax and types, then translates C into assembly Assembly source
Assembly Converts assembly instructions into machine-code sections Relocatable object file such as hello.o
Linking Combines object files and libraries, resolves symbols and lays out an executable ELF executable such as hello

Run each stage separately to see its output:

BASH Inspect each GCC stage 
gcc -std=c17 -E hello.c -o hello.i
gcc -std=c17 -S hello.i -o hello.s
gcc -c hello.s -o hello.o
gcc hello.o -o hello

-E stops after preprocessing, -S stops after compiling to assembly, and -c stops after assembling to an object file. The final command links the object into an executable. You can also ask GCC to keep intermediate files during a normal build:

BASH Keep intermediate files 
gcc -std=c17 -save-temps=obj -Wall -Wextra -g3 hello.c -o hello

In a multi-file project, each .c file is compiled independently and the resulting object files are linked together. Headers declare interfaces; they are included by source files, not normally compiled into separate object files.

C include/app.h 
#ifndef APP_H
#define APP_H

int app_message(void);

#endif
C src/app.c 
#include <stdio.h>
#include "app.h"

int app_message(void)
{
    return puts("Application started");
}
C src/main.c 
#include "app.h"

int main(void)
{
    return app_message() < 0;
}

Compile and link the project from its root directory:

BASH Build a two-file program 
gcc -std=c17 -Wall -Wextra -Wpedantic -g3 -Iinclude \
    src/main.c src/app.c -o app
./app

-Iinclude adds the project header directory to the include search path. A missing declaration often produces a compiler diagnostic; a declared function with no definition usually produces an undefined-reference error from the linker. Keep declarations in headers and provide each external function definition in one source file.

0.4 Useful Compiler Flags

Use a consistent warning and debug baseline while learning:

BASH Recommended learning build 
gcc -std=c17 -Wall -Wextra -Wpedantic -Wformat=2 \
    -Wstrict-prototypes -g3 -O0 hello.c -o hello
Flag Purpose
-std=c17 Selects the C17 language standard instead of a compiler-specific default
-Wall -Wextra -Wpedantic Enables a broad set of useful diagnostics; the names do not literally mean every possible warning
-Wformat=2 Checks printf/scanf-style format strings more strictly
-Wstrict-prototypes Warns about old-style function declarations without a parameter prototype
-g3 Adds detailed source-level debug information and macro information
-O0 Disables most optimization, making early GDB stepping easier
-O2 Optimizes a release build; source stepping and variable visibility may differ
-c Compiles/assembles a source file without linking
-Ipath Adds a directory to the header search path
-DNAME=value Defines a preprocessor macro for this build
-Lpath -lname Adds a library search directory and links a library
-Werror Treats warnings as errors; useful in controlled CI after the warning baseline is understood
-fsanitize=address,undefined Adds runtime checks for many memory errors and undefined operations in test builds

For a debug build, use -g3 -O0. For an optimized build, use -O2 and retain useful warnings. Do not assume that -O0 makes undefined behavior safe, or that a clean build proves the program is correct. Sanitizers are testing tools; they do not replace tests or fix design errors.

BASH Build with AddressSanitizer and UndefinedBehaviorSanitizer 
gcc -std=c17 -Wall -Wextra -Wpedantic -g3 -O1 \
    -fsanitize=address,undefined -fno-omit-frame-pointer \
    hello.c -o hello-sanitize
./hello-sanitize

Add hardening options when building a Linux application, after checking compatibility with the target system:

BASH Linux application hardening example 
gcc -std=c17 -O2 -D_FORTIFY_SOURCE=2 -fstack-protector-strong \
    -Wall -Wextra -Wpedantic hello.c -o hello

_FORTIFY_SOURCE depends on the C library and optimization settings; it is not a substitute for bounds checks. Embedded cross-compilers, bootloaders and bare-metal projects use target-specific flags and linker scripts, so do not copy Linux hardening or library flags blindly into a firmware build.

0.5 Inspect the Executable and ELF Format

On Ubuntu, a native executable is commonly an ELF (Executable and Linkable Format) file. ELF describes a file's target architecture, entry point, loadable segments, sections, symbols and optional debug information. Object files are also ELF files, but they are relocatable and still need linking.

BASH Inspect an executable and its object file 
file hello hello.o
readelf -h hello
readelf -S hello
readelf -l hello
nm hello
size hello
objdump -d -Mintel hello
  • file gives a quick identification, such as 64-bit x86-64 ELF executable or relocatable object.
  • readelf -h displays the ELF header: class, byte order, machine architecture, type and entry point.
  • readelf -S lists sections such as .text (program instructions), .rodata (read-only data), .data (initialized writable data), .bss (zero-initialized storage) and .debug_* (debug information when present).
  • readelf -l lists loadable segments used by the loader; sections are an organization for linking and inspection, while segments describe what is mapped at runtime.
  • nm lists symbols. A symbol marked U is undefined in that file and must be supplied elsewhere during linking or dynamic loading.
  • size summarizes text, data and BSS storage. For firmware, the cross-toolchain's size output helps estimate Flash and RAM use.
  • objdump -d disassembles machine instructions. objdump -d -S hello can interleave source lines when debug information is available.

To inspect a dynamic executable's shared-library dependencies, use ldd hello. Use ldd only on trusted executables; for untrusted files, inspect metadata with readelf -d instead. These commands report a host Linux binary. An STM32 .elf has a different machine architecture, and should be inspected with the matching arm-none-eabi-* tools.

0.6 Debug a C Program with GDB

GDB is the GNU debugger. Compile with debug information (-g) and a low optimization level (-O0) to make the source easier to follow. This small program has a helper function we can stop inside:

C average.c 
#include <stdio.h>

static int average(int total, int count)
{
    return total / count;
}

int main(void)
{
    int result = average(84, 4);
    printf("Average: %d\n", result);
    return 0;
}

Build and launch the debugger:

BASH Start GDB 
gcc -std=c17 -Wall -Wextra -Wpedantic -g3 -O0 average.c -o average
gdb ./average

At the (gdb) prompt, work through the program:

GDB Inspect program execution 
break average
run
list
print total
print count
next
print result
continue
quit

break average sets a breakpoint at the function, and run starts the program. list shows nearby source. print total and print count inspect function parameters. next executes the current source line without entering another function; after it returns to main, print result inspects the value assigned by the call. continue runs to the next breakpoint or program exit, and quit leaves GDB.

Other commands worth knowing:

  • start begins execution and stops at the start of main.
  • step enters a function called on the current line; next steps over it.
  • finish runs until the current function returns; backtrace (or bt) prints the call stack.
  • frame 1 selects a stack frame; info locals lists local variables in that frame.
  • display value prints an expression after each stop; undisplay removes it.
  • watch value stops when a variable changes; hardware watchpoint availability and size are limited.
  • x/16bx address examines 16 bytes in hexadecimal; inspect help x for GDB's memory examination syntax.
  • catch throw, info breakpoints and delete 1 help with exceptions in C++ or breakpoint management; ordinary C programs mainly use break, watch and catch signal.

For an interactive source view, start GDB with gdb -tui ./average. If a program crashes, run it in GDB and use backtrace to find the call path. On Ubuntu, core dumps may be enabled for a shell session with ulimit -c unlimited; a core file can be opened with gdb ./average core.

0.7 Types, Expressions, Control Flow and Functions

Choose a type that represents the data and its valid range. int is useful for ordinary calculations; use size_t for object sizes and array indexes, and types from <stdint.h> such as uint32_t when an exact-width representation is part of an interface. Check conversions at boundaries: a value that fits in one type may overflow or change meaning when converted to another.

C classify.c 
#include <stdbool.h>
#include <stdio.h>

static bool is_in_range(int value, int low, int high)
{
    return value >= low && value <= high;
}

int main(void)
{
    int temperature_c = 24;
    if (is_in_range(temperature_c, -40, 85)) {
        puts("Temperature is within the example range.");
    } else {
        puts("Temperature is outside the example range.");
    }
    return 0;
}

This example uses a function with explicit parameter types and a bool result. The if/else branches make the control flow visible, and && means both comparisons must be true. The range is only an example; a real sensor or product must use its own documented operating limits.

Core language topics to practice:

  • Operators and precedence; use parentheses when they improve clarity.
  • if/else, switch, for, while and early return.
  • Function declarations, definitions, parameters, return values and local scope.
  • enum for a fixed set of named states, and struct for related fields.
  • const to express read-only access; static to limit a file-scope name or retain a local value between calls.
  • sizeof for object sizes, not assumptions about the sizes of pointers or int.

0.8 Arrays, Pointers and Strings

An array stores elements next to each other; a pointer stores an address. C does not automatically check that an index or pointer stays within a valid object. Always carry a length with a buffer, and do not read or write past its bounds.

C array_sum.c 
#include <stddef.h>
#include <stdio.h>

static int sum(const int values[], size_t count)
{
    int total = 0;
    for (size_t i = 0; i < count; ++i) {
        total += values[i];
    }
    return total;
}

int main(void)
{
    const int readings[] = { 12, 15, 13 };
    size_t count = sizeof readings / sizeof readings[0];
    printf("Total: %d\n", sum(readings, count));
    return 0;
}

In a function parameter, const int values[] is adjusted to a pointer parameter; it does not carry the array length. count supplies that length explicitly. sizeof readings / sizeof readings[0] computes the number of elements here because readings is still an array in main.

Strings are character arrays terminated by the null character '\0'. A destination string needs room for that terminator as well as its visible characters. Prefer bounded interfaces, check return values, and avoid unsafe copies such as strcpy when the input length is not known.

C string_length.c 
#include <stdio.h>
#include <string.h>

int main(void)
{
    char label[16] = { 0 };
    const char source[] = "engine";
    int written = snprintf(label, sizeof label, "%s", source);
    if (written < 0 || (size_t)written >= sizeof label) {
        fputs("Label did not fit\n", stderr);
        return 1;
    }
    printf("%s has %zu characters\n", label, strlen(label));
    return 0;
}

snprintf writes no more than the destination size, including the terminator. Its return value tells you how many characters it wanted to write, so checking it detects truncation. Never pass an untrusted format string as the first argument to printf; use printf("%s", text) or fputs(text, stdout).

0.9 Structures, Enums and Bitwise Operations

Use a struct to keep fields that describe one value together; use an enum to make a state machine's states readable. Bitwise operators manipulate individual bits and are common in hardware registers and protocol flags.

C status.c 
#include <stdint.h>
#include <stdio.h>

enum drive_state {
    DRIVE_OFF,
    DRIVE_READY,
    DRIVE_FAULT
};

typedef struct {
    uint32_t identifier;
    enum drive_state state;
    uint8_t fault_flags;
} drive_status_t;

int main(void)
{
    drive_status_t status = { .identifier = 7, .state = DRIVE_READY, .fault_flags = 0 };
    status.fault_flags |= (uint8_t)(1u << 2);
    if ((status.fault_flags & (uint8_t)(1u << 2)) != 0u) {
        puts("Over-temperature flag is set.");
    }
    return 0;
}

1u << 2 creates a mask with bit 2 set. |= sets those bits without changing other bits; & tests whether a bit is set. On a real device, consult the reference manual for register semantics: write-one-to-clear and read-only bits cannot be handled like ordinary RAM.

0.10 Memory, Ownership, Files and Errors

Automatic local variables usually live for the duration of their block; static objects live for the whole program; dynamically allocated objects remain valid until released. Give every allocated object one clear owner and a defined release point. Check allocation and I/O results, and never use a pointer after its object has ended or been freed.

C read_file.c 
#include <stdio.h>

int main(void)
{
    FILE *file = fopen("input.txt", "r");
    if (file == NULL) {
        perror("input.txt");
        return 1;
    }

    char line[128];
    if (fgets(line, sizeof line, file) != NULL) {
        fputs(line, stdout);
    }
    if (ferror(file)) {
        perror("reading input.txt");
        fclose(file);
        return 1;
    }
    if (fclose(file) == EOF) {
        perror("closing input.txt");
        return 1;
    }
    return 0;
}

fopen can fail, so check for NULL before using the stream. fgets reads at most the buffer size and null-terminates data it successfully reads. perror reports the operation with the system error description. Production code should also decide how to handle long lines and whether the file must contain exactly one line.

Dynamic allocation uses malloc/calloc and must be paired with free; check for allocation failure and avoid arithmetic overflow when calculating allocation sizes. Prefer automatic or static storage when their lifetime and size are appropriate.

0.11 Build a Small Project with Make

As programs grow, split them into modules with a header for the public interface. A Makefile records the build command and dependencies so you can rebuild consistently:

MAKEFILE Makefile 
CC = gcc
CFLAGS = -std=c17 -Wall -Wextra -Wpedantic -g3 -O0
CPPFLAGS = -Iinclude
SOURCES = src/main.c src/app.c
OBJECTS = $(SOURCES:.c=.o)

app: $(OBJECTS)
	$(CC) $(OBJECTS) -o $@

src/%.o: src/%.c include/app.h
	$(CC) $(CPPFLAGS) $(CFLAGS) -c $< -o $@

.PHONY: clean
clean:
	rm -f $(OBJECTS) app

Run make to build and make clean to remove generated objects and the executable. Make recipes must begin with a tab. Add headers to prerequisites so changes to an interface rebuild dependent files. For larger projects, learn automatic dependency generation, separate debug/release configurations and a build system appropriate to the product; keep compiler options visible and repeatable.

0.12 Testing, Diagnostics and Safer C

Treat compiler warnings as actionable feedback. Use small functions with clear inputs and outputs, validate external input before using it, and make error cases explicit. A test should check both normal behavior and boundary cases.

C test_range.c 
#include <assert.h>
#include <stdbool.h>

static bool is_in_range(int value, int low, int high)
{
    return value >= low && value <= high;
}

int main(void)
{
    assert(is_in_range(0, 0, 10));
    assert(is_in_range(10, 0, 10));
    assert(!is_in_range(-1, 0, 10));
    assert(!is_in_range(11, 0, 10));
    return 0;
}

Compile and run the test with sanitizers during development:

BASH Compile and run a test 
gcc -std=c17 -Wall -Wextra -Wpedantic -g3 -O1 \
    -fsanitize=address,undefined test_range.c -o test_range
./test_range

AddressSanitizer can identify many out-of-bounds accesses and use-after-free errors; UndefinedBehaviorSanitizer detects selected undefined operations. assert is useful for internal test expectations, but it may be disabled by NDEBUG and should not be used as runtime validation of untrusted input. Also consider Valgrind (valgrind --leak-check=full ./program) when installed, and static-analysis tools such as cppcheck or GCC's -fanalyzer.

Habits that prevent common defects:

  • Initialize variables and check all function results that can fail.
  • Match each allocation with one owner and one free; do not return pointers to expired local variables.
  • Check array lengths and integer ranges before indexing, converting or allocating.
  • Use size_t for sizes, and avoid signed/unsigned comparisons without checking the conversion.
  • Keep functions small, prefer explicit interfaces, and compile every source file with the same warning policy.
  • Do not assume volatile makes shared data atomic or thread-safe. It mainly tells the compiler that accesses are observable; synchronization needs the correct atomic or interrupt-safe design.

0.13 C in Embedded and Automotive Systems

The same C fundamentals are used in firmware, control units, test tools and Linux-based vehicle gateways. Embedded code must additionally account for hardware timing, interrupts, memory limits, watchdogs, startup code, linker scripts and the exact peripheral/reference-manual behavior. Automotive software also needs documented requirements, defensive error handling, traceable tests and safety/security processes appropriate to its product.

For protocol data, do not cast an arbitrary byte pointer to a multi-byte integer pointer: it can violate alignment and aliasing rules, and the wire byte order may differ from the processor. Decode each byte explicitly according to the protocol:

C Decode a signed little-endian CAN signal 
#include <stdbool.h>
#include <stdint.h>

static bool decode_temperature_tenths(const uint8_t data[2], int16_t *result)
{
    if (data == 0 || result == 0) {
        return false;
    }

    uint16_t raw = (uint16_t)data[0] | (uint16_t)((uint16_t)data[1] << 8);
    int32_t signed_value = raw <= INT16_MAX ? (int32_t)raw : (int32_t)raw - 65536;
    *result = (int16_t)signed_value;
    return true;
}

This example assumes a two-byte, little-endian, signed two's-complement signal whose unit is 0.1 degrees C; that assumption must come from the message specification. The intermediate int32_t makes sign extension explicit before the value is narrowed to int16_t. A real CAN receiver must first verify the frame identifier, payload length, signal scaling, timeout and validity rules.

A small explicit state machine is often safer to review than deeply nested conditionals:

C Simple controller state machine 
enum controller_state {
    STATE_INIT,
    STATE_ACTIVE,
    STATE_FAULT
};

static enum controller_state next_state(enum controller_state state, bool input_valid)
{
    if (!input_valid) {
        return STATE_FAULT;
    }
    if (state == STATE_INIT) {
        return STATE_ACTIVE;
    }
    return state;
}

This is only a teaching example, not production automotive control logic. Real systems need requirements-defined state transitions, timing analysis, diagnostics, safe-state behavior, hardware protection and verification. On STM32, later chapters apply these C concepts to registers, GPIO, timers, interrupts, buses, sensors and debugging.
