Chapter 05 • Language

Lifetimes & Their Embedded Implications

Understand lifetime annotations, 'static data and why DMA buffers and long-lived peripherals care about them.

⏱️ Reading Time: 35 minutes
🛠️ Lab: Lifetime puzzles
🎯 Topics: Lifetimes

5.1 What a Lifetime Is

A lifetime is the span of code during which a reference is valid. Every reference has one; most are inferred. Lifetimes are checked at compile time and do not exist at run time - they add no code and no RAM.

The rule they enforce: *a reference must never outlive the data it points to.* That is the dangling-pointer bug, eliminated.

RUST A dangling reference is a compile error 
fn pick<'a>(a: &'a [u8], b: &'a [u8]) -> &'a [u8] {
    if a.len() >= b.len() { a } else { b }
}

let result;
{
    let short_lived = [1u8, 2, 3];
    result = pick(&short_lived, &[9, 9]);
}   // short_lived dies here
// use(result);   // ERROR: `short_lived` does not live long enough

The 'a in the signature says: "the returned slice is valid only as long as both inputs are". The caller's code is checked against that promise.

5.2 Lifetime Elision

You rarely write lifetimes. Three elision rules cover common cases:

  • Each reference parameter gets its own lifetime.
  • If there is exactly one input lifetime, outputs use it.
  • If one input is &self or &mut self, outputs use its lifetime.
RUST Elided lifetimes 
fn first_word(s: &str) -> &str { s.split(' ').next().unwrap_or("") }   // output tied to the input

5.3 Structs That Hold References

RUST A frame parser borrowing the receive buffer 
struct Frame<'a> {
    id: u16,
    payload: &'a [u8],     // points INTO the buffer - no copy
}

fn parse(buf: &[u8]) -> Option<Frame<'_>> {
    if buf.len() < 3 { return None; }
    let id = u16::from_be_bytes([buf[0], buf[1]]);
    let len = buf[2] as usize;
    let payload = buf.get(3..3 + len)?;     // bounds-checked
    Some(Frame { id, payload })
}

Zero-copy parsing is fast and safe: the compiler guarantees the Frame is not used after the buffer is reused or freed. In C the same code is "fast and hope".

5.4 'static: Data That Lives for the Whole Program

'static means "valid until power-off". String literals, static items and leaked allocations have it. It matters in embedded for two reasons:

  • Interrupt handlers and DMA hardware can run at any time, so anything they refer to must outlive every scope - it must be 'static.
  • Tasks in RTIC/Embassy are 'static by construction.
RUST Giving a buffer a 'static lifetime 
use cortex_m::singleton;

// Returns Some(&'static mut [u8; 64]) the first time, None after that
let rx_buf: &'static mut [u8; 64] = singleton!(: [u8; 64] = [0; 64]).unwrap();

The singleton! macro makes a hidden static and hands out exactly one &'static mut to it - so DMA can write into it for the rest of the program while the compiler still knows there is a single exclusive owner.

Why DMA wants 'static
If you gave DMA a pointer to a local array and then returned from the function, the DMA controller would keep writing into stack memory that has been reused. Requiring 'static buffers (or buffers owned by the transfer object) makes that bug impossible. Chapter 21 uses this.

5.5 Reading Lifetime Errors

Typical messages and what they mean:

Message Meaning Fix
borrowed value does not live long enough The reference outlives its owner Move the owner to a longer scope, or own the data
lifetime may not live long enough Your signature promises more than it can deliver Relate the lifetimes in the signature
cannot return reference to local variable Returning a pointer to the stack Return the value, or take a buffer from the caller
argument requires that ... is borrowed for 'static Interrupt/DMA/task needs permanent data Use singleton!, StaticCell or a static
When in doubt, own it
If lifetimes get tangled, copy the 8 bytes. Copy data like a Frame with an inline [u8; 8] has no lifetime at all and is often the right choice on small payloads such as CAN.
